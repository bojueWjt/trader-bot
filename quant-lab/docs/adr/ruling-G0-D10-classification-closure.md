## 6. 更正与补证（G0 自审，2026-09-11 R80）

**本节更正本裁定的两处事实陈述。裁定结论不变（分类终裁 pass），但其中一格原先没有被证明。**

### 6.1 更正：open 项不是 3 条，是 7 条

本文件抬头写「open 项收敛至 W01–W03」。**该句只描述了 r5 新增的必修项，不是 r5 的剩余集。** `review-G1-P1-r5.md` 末行逐项计数为
`S/T/U/V 闭合数：13/16、4/4、1/1、3/4；新增必修 3 条（W01–W03）`，即 **S08、S13、S14、V01 四条仍 open，加 W01–W03 共 7 条**。

按 §25.11 **A42**：效力在逐项计数，不在摘要句。**以 7 条为准**，`INTEGRATION_REPORT.md` 已知缺口表按 7 条列。

### 6.2 补证：三条 open 项落在**可复算性**这一必闭合类，而 §2 的该格没有覆盖它们

S08 / V01 / W02 同一根因：**录制 JSON 经 float 解码，高精度经济量被静默改值后写入 EX/CP**。这属于用户标准里的**可复算性**——五类必闭合之一。

**§2「可复算性」格当时的判据是**：`gold/episode` 经济量叶列全为 `decimal128(38,12)`、字段路径无 `float(`、逐字源串断言通过。**它检验的是「落盘列的类型」与「parser 是否逐字往返」，不是「有没有任何有损转换能进入声明精度的路径」。** 录制解码路径不在其覆盖内。**这一格当时未被证明，是通过的假象。**（形状见 contracts/README §25.9 **A41**：一个字段只能回答它自己的那个问题。）

**现补上判别性实跑**（G0 `.venv-g0`，针对 `RecordedClient.from_file` 真实路径，源串 `60000.123456789123`）：

| | 结果 | 与源串逐字相等 |
|---|---|---|
| 现状（`json.loads(..., parse_float=Decimal)`，`llm.py:111`、`llm.py:338`） | `Decimal('60000.123456789123')` | **是** |
| 突变（摘掉 `parse_float`，同一文件同一路径） | `60000.12345678912` | **否**，静默改量 `-3E-12` |

**判别性成立：门去掉即变红。** 故**可复算性一格现已被证明闭合**——由 G1 对 W02 的修复（两处解码入口均 `parse_float=Decimal`）达成，**不是由本裁定 §2 原判据达成**。

### 6.3 结论

分类终裁 **pass 维持**：五类必闭合项现全部有判别性证据，其中可复算性一格的证据由本节补上。**残余口径更正为 7 条**（S08、S13、S14、V01、W01–W03），按 §4 带声明进 P2，不阻断 P1。
