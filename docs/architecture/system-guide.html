主路径

现役生产在 jp-24。HK 旧交易栈已于 2026-08-23 停用；旧脚本里的 hk 名称不代表当前部署地点。

信号主路径是：Telegram 频道 → 信号接入 → Hermes → 控制面意图/风控/授权 → 四账户 Nautilus → Binance USDT-M。主图把 Watcher 与持久投递画成一个「信号接入」节点；内部仍是独立组件。

信号接入内部

  • trader-watcher-1 按白名单收频道消息，写入 Watcher SQLite。
  • feeder 读 SQLite 游标，先把每条消息提交规范 PostgreSQL ingress（POST /telegram/raw，同事务写 raw_message 与 queued_for_hermes outbox），才允许 Hermes 处理。
  • 随后 feeder 创建一次性 Hermes cron job（v3-trader skill）。feeder 只运输，不做交易判断。投毒消息在有限重试后跳过，避免卡住队列。

Hermes 把频道文本变成结构化决策，经 v3-trader 调用控制面。LLM 不直接握交易执行权，也不直连交易所。节点 inbox/stash 用于幂等恢复，不宣称 exactly-once。「已提交」只表示控制面受理，不是交易所成交；成交靠执行事件与交易所对账回流。

App / 看板在生产边界外：读 operator-query 投影，并可通过 POST /v1/operator/orders 提交手动平仓、止损等管理命令。这是独立入口，不经过频道信号链。

控制面

同一套 API 按角色拆成三个 systemd 服务，数据库角色与连接池隔离：

角色职责
operator-query看板/App 读模型；POST /v1/operator/orders、POST /v1/commands
node-control心跳、意图拉取、命令 ACK、节点事故
event-ingest执行事件入账

四账户边界

A–D 是同一 jp-24 上的四个独立执行容器（trader-v3-node-a … d），不是四台物理主机。各账户有独立密钥、独立 spool、独立 health 端口。主图「执行与租约域」是逻辑分组：Redis 是共享实例，不在四个节点容器里；账户之间靠租约命名空间隔离。节点启动为 HALTED，不会自动变成 ACTIVE。

授权、减仓与订单身份

  • 机器人 clientOrderId 匹配 ^B[0-9a-f]{32}[0-9]{2}$。
  • aos_ / stToAg_ 是用户手动单。任何自动化不得撤销，也不得用它们当机器人仓。
  • user 与 channel 权限分开，不能把 channel 提升为 user。
  • channel 减仓基数是 min(robot_owned, 新鲜同侧 venue)；user 基数是新鲜同侧 venue。owned 是账户/品种/方向级，不是 per-channel。无 owned 时 channel 请求拒绝。
  • 比例减仓只提交结构化 fraction，乘基数后按 step 向下取整。工程量化例：venue 9.890 / owned 0.308 / 30% / step 0.001 → 0.092。

运维边界

HALT 可以走安全方向。RESUME / 开闸交易只能由用户明确指令触发。部署预检门禁必须在停节点之前全部完成；失败则保持原版本，禁止把舰队留在停机态。维护流程会重建 A–D。验收要查新审计和递增心跳，不采信转述。
