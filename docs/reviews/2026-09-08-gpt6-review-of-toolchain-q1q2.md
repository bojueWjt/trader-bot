审稿日期：2026-09-08  
审稿范围：报告 §1、§2、§3 的 Q1/Q2、§4–§6，以及指定六份研究证据。  
结论等级：必修=不修不应以当前方案开工；应改=应在 PoC 前修正；建议=不阻塞开工但应补强。

引用说明：报告行号对应 `docs/research/2026-09-07-quant-toolchain-selection/2026-09-07-quant-toolchain-selection-report.md`；`research/` 均相对该报告目录。没有操作 Telegram 账号、调用付费模型或安装标注服务；以下实测要求不是实测结果。必修共 6 项，其中涉及实验设计的修订须在该阶段执行前完成，不要求先取得 PoC 才能产生的实测结果。

## 总裁定

Q1/Q2 的方向可以保留，但当前报告不能按“证据强度高、方案已经闭环”理解。Q1 可以作为低风险 PoC 的起点，前提是把 TDesktop 导出定义为一次性规范快照，而不是自动化全量采集器，并先完成规模、媒体、断点与对齐验收。Q2 可以作为抽取与确认 PoC 的起点，但必须把“一致”降级为待抽审样本，不得把确定性解析器 + LLM 组合表述成已经证明的去相关方案。

当前最严重的共同缺口是：报告把“尚未实跑”与“高置信推荐”并置。报告 §2 lines 28–32 明确列出 TDesktop 字段、Label Studio Repeater 尚未核验，但 §1 lines 11–12 仍给 Q1/Q2 标为高证据强度。应将高置信改为“方向性高、可执行性待 PoC”。

## 1. Q1：TDesktop 规范全量 + Telethon 补拉

### Q1-必修-1：未证明五频道数万条消息的导出窗口与媒体体积可接受

定位：报告 §3 Q1 lines 53–57、§5 PoC 1 lines 179–180；证据 `research/r1a1-telegram-harvest.md:18`、`research/r2-telegram-verify.md:22–31`。

报告只说“大频道可能耗时数小时”，却把“五频道全量 JSON（含媒体）”安排为 1 天，并没有给消息总数、媒体类型/数量、下载并发、磁盘上限、导出是否支持断点、失败后是否需要重做。数万条含图消息的风险不在 JSON，而在媒体总字节数、客户端导出阶段和重复下载。

具体修法：PoC 先分离“JSON 元数据快照”和“媒体物件归档”。记录每频道消息数、媒体文件数、总字节数、最大单文件、导出墙钟时长、失败点和可恢复性；按频道逐个导出，预留至少 2 倍预计媒体空间。成功判据改为“可重跑、可续传、目录清单与 JSON 一一对应”，不再用“1 天”作为隐含可行性证明。

数量级示例（假设，非测量）：50,000 条 × 40% 含图 × 每图 0.5–2 MB = 10–40 GB；10 Mbps 有效链路仅传输就约 2.2–8.9 小时，尚未计等待、重试和客户端处理。官方说明新登录可能需等 24 小时，也可由另一设备确认立即开始；不能写成所有导出固定等 24 小时。[S1]
补验：选择单频道导出、全部日期和正确媒体类别，记录单文件大小阈值；“超大小跳过/类型未勾选/不可用”不是下载成功。保留原始 JSON 和目录，再生成规范化视图，不能用重导出覆盖原快照。[S2]

### Q1-必修-2：规范全量与 Telethon id 对齐缺少确定性键与缺失分类

定位：报告 §5 PoC 1 lines 179–180；报告 §3 Q1 lines 53、57；证据 `research/r1a1-telegram-harvest.md:18,80`。

“消息 id 集合一致率 ≥99%”过于粗糙。Telegram 消息 id 通常只在频道内有意义，需用 `channel_id + message_id`，并明确服务消息、已删除消息、相册/媒体组、转发、线程回复、置顶服务条目如何计数。TDesktop 只保留最终编辑版本，Telethon 也不能回溯编辑历史；因此 edit_date 只能做最终状态字段对比，不能证明版本一致。

具体修法：定义规范主键 `peer_id/message_id`，另存 `grouped_id`、`date`、`edit_date`、`reply_to_message_id`、`media_relpath`。对齐报告必须分别输出：仅 TDesktop、仅 Telethon、字段不一致、媒体缺失、重复/相册拆分、已删除/不可见；99% 只能用于可比消息 id 集合，字段一致率另设门槛。对最终编辑版写明“无编辑历史保证”。

固定每频道上界 id、时区和两次采集时间，统一裸频道 id 与客户端带前缀的 peer 表示；引用父消息还要记录所属 peer，禁止跨频道凭同号关联。[S3]
定义集合指标为 `|A∩B|/|A∪B|`，同时逐项解释差集；50,000 条的 1% 是 500 条，不能容许 500 条未解释信号缺失。两客户端共享 Telegram 源，集合一致也不能证明不存在已删除的历史。
更关键的是时点泄漏：最终编辑正文不能回填到原始发布时间参与研究。对编辑过且无原始版本证据的信号，隔离或做敏感性分析；从现在起追加存储编辑/删除事件、观测时间和内容哈希。旧版本不可恢复不是换库能解决的。[报告 §3 Q1 line 53；S7]

### Q1-应改-3：TDesktop 不是持续全量源，增量职责没有落地

定位：报告 §1 line 11、§3 Q1 lines 53–57；证据 `research/r1a1-telegram-harvest.md:18,80`。

TDesktop 官方导出适合作一次性基准快照，但不能按 id 精确重取、不能脚本化增量，且账号端可能有等待/人工交互。报告把它称“规范全量”，却没有定义快照时间、水位和后续增量的交接方式。

具体修法：区分“初始基准：TDesktop JSON”“按 id 补拉”“持续更新观测”，tdl 只在证明媒体缺口后引入。`max_message_id` 只能覆盖新消息，不能发现旧消息编辑/删除；需要更新流及断线补差，并周期重查旧 id。若无可用次号，则降级为手工周期快照，保留未核差异，不能称为等价增量链路。[S7]

### Q1-应改-4：未知 constructor 的恢复策略不够安全

定位：报告 §3 Q1 line 55；证据 `research/r3-adversarial.md:13–15`。

“外套 TypeNotFoundError 跳过并记录”可能造成静默漏数，尤其错误发生在分页游标中间时。仅跳过异常对象不能证明后续页和游标仍完整。

具体修法：按固定 id 区间分片抓取；每片记录请求范围、返回最小/最大 id、数量、异常类型和重试次数。遇到解析异常时保留原始 TL/响应上下文，标记该区间为未验证并停止将其纳入规范快照。恢复后必须重新抓该区间并做集合校验。

### Q1-应改-5：账号隔离结论正确，但“次号可用”仍是门槛，不是默认前提

定位：报告 §3 Q1 lines 48–57、§6 lines 190–193；证据 `research/r1a1-telegram-harvest.md:59–74`、`research/r2-telegram-verify.md:87–92`。

证据同时承认 FloodWait 的 2025 年后实测值缺失、次号是否可用待确认。故“Telethon 次号补拉”不能写成已选定能力。

具体修法：PoC 0 先验收账号、频道可见性、API 登录和独立 session；任何冻结、重新登录失败或超过预设等待即停止。不要使用生产 watcher 的账号、auth key 或 session；把“无次号”直接映射到 TDesktop-only 降级方案。

### Q1-建议-6：被漏掉的更稳方案应进入比较，不必立即采用

定位：报告 §3 Q1 lines 40–45；证据 `research/r1a1-telegram-harvest.md:18–19`。

真正漏列的是官方 Takeout API：Telegram 文档给出频道、媒体、文件上限和分页导出流程，Telethon 已有 `client.takeout()`，且文档说明部分调用限流更宽松。它比另引 TDLib 更值得先试，但仍有初始化等待、权限和账号风险，不能保证更快或不冻结。[S2][S4]

具体修法：先比较 TDesktop 与 Telethon Takeout 的同频道小样和断点；再决定是否需要 TDLib。保留 TDesktop 作为原始证据是合理选择，但规范化格式应由项目定义，避免绑定 GUI 字段。TDLib 已在候选表，不属于漏列方案；没有本项目实测不能断言它更稳。

## 2. Q2：LLM + 确定性解析器 + 人工确认

### Q2-必修-1：“去相关”结论被过度表述

定位：报告 §1 line 12、§3 Q2 lines 73–78；证据 `research/r3-adversarial.md:19–29`、`research/round3-findings.md:32–35`。

确定性解析器只对它能覆盖的语法提供不同错误机制；它不等于与 LLM 独立，也不能处理“关注区域”“分批止盈”“图中文字与正文冲突”等语义缺省。若解析器先消费 LLM 输出，二者甚至共享同一上游错误。证据支持“增加异质性”，不支持“已经去相关”。

具体修法：把表述改为“异质校验路径，待实测估计相关性”。解析器必须直接读取原始文本/图像 OCR 中间产物，不能读取 LLM 草稿；LLM 输出必须保留原文 span、图像坐标或证据片段。按字段测量两路径的错误共现率、漏报率、拒答率，并区分文本字段、价格字段、方向字段和多档止盈字段。

### Q2-必修-2：一致集抽审 10% 没有统计依据，也没有最小抽样数

定位：报告 §3 Q2 line 78、§5 PoC 3 lines 181–182。

10% 是操作比例，不是误差或置信度设计。若一致集只有 100 条，抽 10 条无法稳定估计低错误率；若一致集有数万条，固定 10% 又可能显著浪费人工。更重要的是，随机抽一致集会漏掉高风险字段和同模板批次错误。

具体修法：先做分层随机抽样，层按频道、文本/图片、信号模板、模型版本、字段类型和置信度划分。预先规定绝对最小样本数与停止规则，报告每层一致集错误率及 Wilson/Clopper–Pearson 区间。对低置信、价格字段、解析器边界和新模板做 100% 或高比例复核；10% 只能作为初始预算，不得作为质量证明。

量化例：固定样本、独立 Bernoulli 假设下，零错误时单侧 95% 上界 `1−0.05^(1/n)`；n=10 约 25.9%，n=100 约 2.95%，n=299 才低于 1%。这是公式推导，不是对本语料的保证。有限总体应用超几何设计；重复模板/相册/回复链按簇处理，分层汇总按总体权重，不能把稀有层过采样后的简单平均当总体错误率。

### Q2-必修-3：论文外推错误，且“抽审通过”与“人工真值”未区分

定位：报告 §1 line 12、§3 Q2 lines 76–78；证据 `research/r3-adversarial.md:21–29`。

论文摘要说的是一个 leaderboard 上“两模型都错”的条件下约 60% 答案一致，任务包括榜单和简历筛选，不是 Telegram 模糊交易信号。报告 §1 line 21 把它直接改写成交易信号结论，证据不支持；论文也没有测量此项目 parser 与 LLM 的共错率。[S5]

具体修法：先建不展示预测的人工金标集，再做模型评测，防预填锚定。明确 `human_verified`、`auto_accepted_under_audit`、`ambiguous`；抽审达标可以支持自动接受一层，不必全量人工，但未抽记录不能冒称人工真值。两路都空或共享 OCR 不得算强一致；无法解析、原文模糊和图文冲突必须弃权，不允许补默认价。

### Q2-应改-4：PoC 质量指标与止损阈值不完整

定位：报告 §5 PoC 3 lines 181–182、§6 line 191；证据 `research/r1a2-extract-labeling.md:32–39`、`research/r2-labeling-verify.md:37–41`。

“图片字段纠错率 ≤30%”只覆盖一个聚合指标，没有定义分母、字段级准确率、拒答率、漏字段、数值容差、方向反转和跨字段一致性。对交易信号而言，一个止损价格错位可能比多个普通字段错误更严重。

具体修法：至少验收 exact match、数值相对/绝对误差、方向准确率、必填字段召回率、拒答率、跨字段约束违规率，并按文本/图片分开。把“方向反转、止损/止盈数量级错误、时间窗口错配”设为零容忍或人工全返工条件，而不是被 30% 平均值掩盖。

### Q2-应改-5：人工确认工具的选择合理，但版本与导出能力不能提前算作已证实

定位：报告 §3 Q2 lines 63–70、78；证据 `research/r2-labeling-verify.md:22–29`。

Label Studio 1.23.0、predictions、Repeater 和社区版 history/diff 的组合方向可行，但证据明确说 Repeater 未实抓，社区版对比可视化属于 Enterprise，diff 需要离线计算。报告仍把“结构可表达、导出 diff”写入高置信结论。

具体修法：PoC 4 作为 Q2 的前置门禁，固定 3 档和 5 档样例，验证导入 JSON、Repeater 展开、保存/重开、导出 predictions 与 annotations、离线 diff、删除/重做和 SQLite 备份恢复。失败时应直接切自建审核页，不要等到数据已进入锁箱后再迁移。

补测“预填 3 档但真值 5 档”和反向删档；按输入数组展开不等于可由标注者增删项。社区版的最终 annotation 元数据不等于不可变修改历史，导出选项须按锁定版本实跑；官方导出文档也应作为验收依据，而非只看 PyPI 发版。[S6]
建议先试固定上限槽位 + 启用标记，或受 schema 校验的 TP 数组文本框，能避免立刻自建 UI。Streamlit 仅在动态档位/多消息上下文无法表达时再用，仍需跳过、回看、进度、图片放大及原子保存；不是“一行 append”即可靠。§4 对 doccano 的不匹配理由可保留，Argilla 的维护断言只作待核记录，不影响本次门禁。

### Q2-建议-6：更省事/更可靠的锁箱替代应按目标拆分

定位：报告 §3 Q2 lines 70、74、78；§4 lines 161–162；§6 line 191；证据 `research/r1a2-extract-labeling.md:64–70`、`research/r2-labeling-verify.md:43–47`。

JSONL + sha256 可查内容变化；OpenTimestamps 证明数据在某个时间之前已存在，不证明准确性、作者身份、唯一预注册，更不阻止研究者提前看留出集。本地 Git/tag/签名同样不是独立时间或访问隔离证明；不能用“客户端久未发布”直接推断协议失效。[S8][S9]

具体修法：最省事的内容归档为原始快照 + 明确 UTF-8/换行/排序/数值编码的 JSONL + 覆盖图片和 schema 的 manifest + 异地备份 + 验证脚本。需要外部时间证明时保留 OTS，验收 `stamp → upgrade → verify`，不能只保存 pending `.ots`；确认后的证明应可独立验证。[S8][S9]
若“锁箱”含留出集防偷看，则升级本项为实施阻断：另设加密与外部密钥保管/受控评估入口、访问记录和冻结分割清单；同一人保管密钥只能自律，不能称强隔离。需要禁止删除/覆盖时另评估不可变存储，不能靠哈希替代。上述机制各司其职，无需为小项目默认引入 DVC/MLflow。

## 3. 评分、PoC 与待确认项自洽性

### 必修-7：Q1/Q2 总分与评分表没有可复算关系

定位：报告 §2 line 25；§3 Q1 lines 38–45、Q2 lines 61–67；`research/round3-findings.md:3–5,9–16,24–30`。

报告声明权重为 30/25/20/15/10。独立复算：TDesktop=75.00（报告76），Telethon=79.75（四舍五入80正确），Label Studio=82.75（报告81.8）。R3 原 Telethon 成熟75时为82.25（写83）；TDesktop 能力50时为69.00（写68）。不能将真实修订与算术错误混为一谈；组合80没有独立评分公式，Q2确认工具分也不能代表抽取/锁箱整条链路。

具体修法：统一一张评分源表，所有总分用脚本计算并四舍五入；组合方案另设“组合评分”公式，明确候选单项分不能直接推导组合分。删除无法追溯的高置信数字，或补充分维度证据和计算表。

### 应改-8：Q1 主次排序在证据与表格之间不一致

定位：报告 §1 lines 9–12、§3 Q1 lines 40–45、§5 line 179；`research/round3-findings.md:11–20,94–108`。

R3 先给 Telethon 90、TDesktop 68，并称“裁决 Telethon 主抓取器”；对抗轮又接受 TDesktop 规范全量、Telethon 补拉，最终组合分 80。这个组合结论可以成立，但必须把“规范快照”“增量”“媒体补齐”三个职责作为系统方案评分，不能让读者误解为 TDesktop 能完成自动全量。

具体修法：把评分对象改为三段式管道，分别列成功判据和失败降级；Q1 的 PoC 1 先做单频道，再扩展五频道。若没有次号，§6 的降级必须同步改写 §1/§3/§5。

### 应改-9：Q2 的“第二家 LLM 裁决”与“确定性解析器去相关”角色未定义

定位：报告 §1 line 12、§3 Q2 lines 76–78；`research/round3-findings.md:94–108`。

当前文字同时出现“双厂商 Batch”“分歧交第二家 LLM”“确定性解析器 + LLM”“一致集 10%”，但没有说明第一家、解析器、第二家各自处理什么、裁决输入是否包含前序答案、分歧结果是否必须人工确认。

具体修法：写出状态机：原文 → LLM-A 与 parser 并行 → 一致则 proposed-consensus → 分歧送 LLM-B 且隐藏 A/parser 答案 → 高风险或 B 不确定则人工 → accepted。所有状态和原始证据进入锁箱。

### 建议-10：§6 待确认项应增加“决策闸门”，而非只列技术细节

定位：报告 §6 lines 187–193。

应增加：五频道规模/媒体字节/可恢复性、`peer_id/message_id` 对齐报告、次号可用性、解析器与 LLM 字段级共错率、分层抽审误差区间、Label Studio 导出/备份恢复、锁箱重验脚本。这些比 OpenAI 价格或 teleproto npm 数据更直接决定 Q1/Q2 是否能开工。

## 4. 最小修订后的 PoC 门禁

1. Q1 单频道小样：TDesktop JSON+媒体、Telethon 分片、可恢复性和主键对齐报告先通过。
2. Q1 五频道扩展：输出规模、耗时、字节、缺失分类和 FloodWait；任一不可恢复区间不得进入规范样本。
3. Q2 先做带真值的分层样本；LLM 与 parser 原文并行，记录字段级共错，不先承诺 10%。
4. Q2 Label Studio 3/5 档、导出 diff、备份恢复通过后，才导入全量预测。
5. 锁箱验证脚本能从 JSONL、manifest、签名和可选 `.ots` 重建并失败即报错。

## 最终裁定：能否作为 PoC 开工依据

**可以作为受限 PoC 的开工依据；不能作为无条件的全量实施依据。**  
开工范围限于：Q1 单频道可恢复性/对齐实验，Q2 带真值小样本/人工确认工具实验。完成上述必修项并更新评分、抽审与锁箱规则后，才可把 Q1/Q2 作为五频道全量与研究数据入库的依据。
