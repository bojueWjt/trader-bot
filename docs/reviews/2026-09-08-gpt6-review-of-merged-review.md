# 对 `channel-seed-to-quant-merged-review` 的对抗审查

日期：2026-09-08  
审查对象：`docs/plans/2026-09-06-channel-seed-to-quant-merged-review.md`  
审查范围：合并 review §1–§10、两份 Codex 对抗 review、两版 Codex v2、`AGENTS.md`、`v3-trader/SKILL.md`

## 先行结论

结论不是“正文有几处措辞残留”，而是当前文档不能无条件作为 M0 派发依据。

必修项：6 条。  
应改项：5 条。  
建议项：2 条。

最严重的自相矛盾：§9.1 说 M0-T1~T4 “与六项只读证据闸门一一对应，T1 加生命周期审计后完全覆盖”，但六项中至少“research protocol”和“shadow boundary”没有 M0-T1~T4 的独立产出、判据或责任人；而且 §8.1 的 T1 原文并未写入 §9.1 声称已经加入的订单生命周期审计表。

因此，§10 只能作为“受限的 M0 任务草案”依据，不能作为已经满足六项前提的完整派发依据。派发前必须修正路线表、任务书和授权文字，并把未覆盖的前提改成明确的后置闸门或新增 M0 任务。

## 必修

### 必修-01：必修-07 的收回没有落实到 §8.1 的 T1 任务书

章节与引文：

- 合并 review §9：`“生产 execution_events 机器人订单：411 OrderFilled / 118 intent / 657 reject+cancel，校准底子够。”`
- 合并 review §9.1：`“处置：M0-T1 增加订单生命周期审计表……覆盖率未达预设值前保真度只出描述报告。”`
- 合并 review §8.1：T1 仅写 `“JSONL + manifest + 字段覆盖矩阵 + 断链分类；禁止跑 trade_outcomes.py 的 main”`。

问题：§9.1 正确收回了“事件量足以校准”的过度声明，但新增要求没有进入实际任务书正文。按 §8.1 “四份任务书原文……直接引用”的派发方式，执行者不会被要求串联 `clientOrderId → intent → episode`，也不会报告重复、孤儿、join failure、状态覆盖率。

具体修法：把 §8.1 M0-T1 的“内容”整段改成：

`JSONL + manifest + 字段覆盖矩阵 + 信号/decision/intent/order/position/episode 断链分类；禁止运行 trade_outcomes.py 的 main；新增订单生命周期审计表，按机器人 clientOrderId、intent、账户、symbol、position side、事件时间串联，报告各状态覆盖率、重复事件、孤儿事件、join failure、未观测状态和右删失；覆盖率未达到预注册阈值时，M3-E 只允许工程描述，不得出保真度或收益结论。`

同时把 §9.1 的“已增加”改成“已拟增加，尚未进入 §8.1 任务书”；完成正文同步后再称已落实。

### 必修-02：六项前提与 M0-T1~T4 的“一一对应”是错误判断

章节与引文：

- 合并 review §9：`“开工依据是 Codex v2 §6 的 M0-T1~T4 四份任务书（全部只读、零生产改动），恰好落在 review 六项前提允许的范围内。”`
- 合并 review §9.1：`“这六项与 v2 的 M0-T1~T4 一一对应，T1 加生命周期审计后完全覆盖。”`
- 合并 review §10：`“可立即派发……M0-T1、M0-T4、M0-T3。”`

问题：六项前提是 provenance、episode+gold、execution contract、event calibration、research protocol、shadow boundary。T1 主要覆盖 provenance 与部分 event calibration；T2 覆盖时间证据；T3 覆盖 execution contract；T4 覆盖 K 线覆盖/前视。episode+gold 在 M1，research protocol 在 M2，shadow boundary 在 M4。四个 M0 任务没有给出三者的产出、验收、阻断条件或责任人。因此“一一对应”和“完全覆盖”均不成立。

这不是把后续工作提前到 M0 的要求，而是必须区分“允许开始 M0 数据盘点”和“允许开始研究/影子/灰度”的前提。当前文字把不同阶段混为同一开工门。

具体修法：将 §9 终裁段改为：

`M0-T1~T4 只覆盖 M0 阶段允许的 provenance、时间证据、执行契约候选、K 线/前视风险；episode+gold、research protocol、shadow boundary 仍分别由 M1/M2/M4 闸门验收。M0 派发不等于六项前提全部满足，且不得据此启动 M1 研究、M3 政策选择、M4 shadow 或 M5 canary。`

将 §10 的“可立即派发”后面补：

`本次派发仅授权只读证据盘点；不表示六项前提已通过，不得把任务输出解释为研究、shadow 或交易授权。`

### 必修-03：§5 路线表没有落实采纳的 M3-E/R/P

章节与引文：

- 合并 review §8：`“最终裁决：采纳。§5 M3 行改为三层。”`
- 合并 review §5：仍只有一行 `M3 无前视配对回测`，产出和判据把“模拟器、四基线、网格、L3a、触发模型”放在同一里程碑。
- 合并 review §9.1：`“两份 review 的 M0 裁定一致……M1 回测器仍应先作为 OHLC 反事实模型验收，M2 才能研究政策，M3 之后才讨论……灰度。”`

问题：§8 的裁决声称覆盖 §5，但 §5 未改写。读者按路线表执行时仍会把 M3 当一个阶段，无法知道 M3-E 只证明可重放、M3-R 只作探索性估计、M3-P 才允许有限晋级申请，也无法知道 M3-E/R/P 的分母和禁止结论。

具体修法：删除 §5 当前 M3 单行，替换为三行：

`M3-E 工程门：≥20 个唯一可归属纯机器人 episode，覆盖 long/short、market、limit/zone、未成交、右删失；只验轨迹、撮合、费用、拒因、回放哈希；禁止收益优越性主张。`

`M3-R 探索门：≥120 个 A_content_and_time 且结构完整的计划、45 个自然日、20 个独立事件簇；报 N_plan/N_episode/N_cluster、逐层损耗、宽 CI 和证据等级；只能写探索性方向估计、无优势或不可判断。`

`M3-P 晋级门：≥200 个可评估新鲜计划、60 个自然日、30 个事件簇、三段 walk-forward、保守成交、成本压力、簇 bootstrap 95% CI 和最终 holdout；只允许提出有限候选晋级申请，不等于生产上线。`

并在 §5 表增加 `capability_status`，L3a/L3b 本期均为 `research_only`，M4 为 `shadow_only`，M5 才在用户授权和门禁通过后写 `production_allowed`。

### 必修-04：§6 的 GramJS 授权仍是被收回前的旧说法

章节与引文：

- 合并 review §6：`“三个授权：生产库只读导出到本机；用 watcher 会话重拉历史消息的发布时间（只读 Telegram API，不发消息）；影子进程部署到 jp-24（M4 时再问）。”`
- 合并 review §8：`“不得共用生产 watcher 活动 session……用户授权项相应改为‘复制会话材料到隔离只读目录’而非直接用生产会话。”`
- v2-gpt6 §6：`“不得直接复用生产 watcher 的活跃 session”`，且要求隔离、方法白名单、FloodWait 立即停批。

问题：§6 仍把“用 watcher 会话”写成用户授权对象，且只说“不发消息”，没有表达会话复制、隔离目录、只读方法白名单、FloodWait 停批、不得持有 operator token。按 §10 派发时，执行者可能直接接触生产活动 session，违反已采纳的安全收紧。

具体修法：将 §6 第二项整条替换为：

`复制经用户明确授权的 watcher 会话材料到隔离的只读运行目录；不直接使用生产 watcher 活跃 session。探查进程仅允许按 channel+message id 读取消息/实体并读取 date，禁止发送、转发、处理 ingress、调用 Hermes/operator API 或任何写路径；遇 FloodWait 立即停批；session 不入 repo、shadow、普通日志，探查进程不得持有生产 operator token。`

### 必修-05：§2 C3 与 §8 的 GramJS 结论存在旧说法残留

章节与引文：

- 合并 review §2 C3：`“可行补救：用 watcher 的 GramJS 会话按 channel+message id 重新拉取原消息拿 date，作为 M0 第一项探查。”`
- 合并 review §8：`“替换 §2 C3 与 §6 中‘重拉即可补齐’的表述。”`
- 合并 review §2 C3 的结尾仍把 `“重新拉取原消息拿 date”` 写成补救主句，没有写内容同一性、时间同一性和失败分级。

问题：这里没有完全保留 §8 的收紧。`date` 能读到不等于原始内容和原始版本可证明；v2-gpt6 明确只有 `A_content_and_time` 才能进入严格 M3-R，`A_time_only` 只能敏感性分析，B/C/D 不能伪装发布时间恢复。

具体修法：将 §2 C3 的补救句改为：

`M0 仅探查可恢复性，不承诺补齐。先查 watcher sqlite/备份，再用隔离会话对 20 个已执行和 10 个失败样本做只读查询；按 A_content_and_time、A_time_only、B_watcher_archive、C_ingest_only、D_unavailable 分级。只有 A_content_and_time 可进入严格 M3-R；其余只能进入敏感性分析或缺口账本。`

### 必修-06：§10 的“可立即派发”缺少授权闸门和停止语义

章节与引文：

- 合并 review §8.1 T2：`“需用户授权会话材料复制。”`
- 合并 review §10：`“可立即派发（需用户点头）：M0-T1……M0-T4……M0-T3。”`
- `AGENTS.md`：`“部署门禁校验必须全部完成于停节点之前；门禁失败=中止部署并保持原版本运行。”`
- `AGENTS.md`：`“RESUME/开闸交易只能由用户明确指令触发。”`

问题：§10 把 T1 的生产库导出和 T2 的会话材料复制并列为“可立即派发”，但没有把每个授权作为执行前硬闸，也没有写任何失败出口。T1 虽是只读，仍涉及生产访问；T2 涉及可发送能力的 session。更重要的是，§10 的“需用户点头”容易被理解为对整组任务的一次性批准，而不是按敏感动作单独授权。

具体修法：将 §10 的派发段改为：

`T3/T4 可先做本地静态与离线工作。T1 只有在用户明确授权生产库只读导出后派发；T2 只有在用户另行明确授权复制会话材料后派发，且复制失败、FloodWait、权限不足或内容同一性不足时立即停止，不改用生产 session、不绕过分级。任何部署、重启、RESUME、风险预算/乘子变更仍不属于 M0 授权。`

## 应改

### 应改-01：§8 “覆盖 §4/§5 中冲突之处”与实际未改写相冲

章节与引文：

- §8 表头：`“最终裁决，覆盖 §4/§5 中冲突之处。”`
- §5 仍保留旧的单一 M3 行，且没有 `capability_status` 列。

修法：把“覆盖”改为“拟覆盖”，直到 §5 正文完成替换；或者直接同步改写 §5，并在文档末尾列出已同步章节。

### 应改-02：§9 的必修-07 表述仍留下“校准底子够”

章节与引文：

- §9 必修-07：`“生产 execution_events……校准底子够。”`
- §9.1：`“411/118/657……不能证明 join 完整性、状态分母或保真度。”`

问题：后文已经承认前文关键前提不成立，但“校准底子够”仍会被单独引用为正面依据。

修法：删除“校准底子够”，改成：

`这些数字只证明存在若干不同实体/状态的事件；在生命周期审计完成并证明 join、分母、孤儿率和删失规则前，不构成事件校准样本量。`

### 应改-03：§9.1 对两份 review 的“六项一致”缺少对照表

章节与引文：

- §9.1：`“两份 review 的 M0 裁定一致……六项只读证据闸门。”`

问题：两份 review 的六项前提是“启动受限 M0”的边界，而不是“任务全部覆盖六项”的证明。当前没有列出每项前提的阶段、产出、阻断条件，导致语义漂移。

修法：在 §9.1 增加四列对照：前提、首次验收阶段、当前 M0 任务覆盖、失败出口。对 episode+gold 标 M1；research protocol 标 M2；shadow boundary 标 M4；均不得标为 M0 已满足。

### 应改-04：§5 的阶段编号与 §9 终裁阶段编号不一致

章节与引文：

- §5 使用 M0、M1、M2、M3、M4、M5。
- §9 的应改项改成 `M0a/M0b/M1a/M1b/M1c/M2/M3/M4`。

问题：同一合并 review 同时存在两套里程碑语义，§10 又回到 M0-T1~T4。派发者无法判断任务属于哪一套门禁。

修法：选一套规范编号。建议保留 M0-T1~T4 作为任务编号，保留 M0/M1/M2/M3-E/R/P/M4/M5 作为阶段编号，并在 §5 开头明确映射；删除未落地的 M0a/M0b 等旧编号，或补完整映射表。

### 应改-05：§10 没有把 `AGENTS.md` 的手动单隔离写进 M0 验收

章节与引文：

- §10 只写 `“当前路由/所有权快照”`。
- `AGENTS.md`：机器人订单匹配 `^B[0-9a-f]{32}[0-9]{2}$`；`aos_`/`stToAg_` 等手动单不得撤销、不得报警骚扰。
- `v3-trader/SKILL.md` 铁律 12、13：管理动作必须按原开仓 intent/ref 核验频道归属，查不到或归属不符不得动。

问题：所有权快照若只记录账户和频道，不足以证明事件审计不会把手动订单纳入 episode，也不足以证明后续 shadow/回放不会发出管理动作。

修法：在 T1 或 T3 验收中明确：按 clientOrderId 正则分离机器人/手动订单；报告手动订单被误 join 的数量；按账户、symbol、position side、entry ref 做归属校验；任何无法归属的管理事件标 unresolved，不得进入训练、回测或自动化动作。

## 建议

### 建议-01：给所有“采纳”增加正文同步状态

§8 多次使用 `“采纳”`，但没有说明“已同步到哪一段”。建议每项增加 `落点：已同步/待同步/后置闸门`，避免再次出现 §6、§2 C3、§5 的旧文字残留。

### 建议-02：在 §10 末尾加入单一停止声明

建议加入：

`任何 T1/T2/T3/T4 失败均只产生缺口账本和停止建议；不得以 Hermes 建议、配置灰度、operator dry_run、写 trade_intents、部署 shadow 或 RESUME 绕过失败。生产原版本保持运行，安全方向 HALT 仍按 AGENTS.md 处理。`

## 最终裁定

该合并 review **目前不能作为无条件的 M0 派发依据**。

在以下前提满足后，可以作为“受限 M0 证据盘点”的依据：

1. 把必修-01 的订单生命周期审计真正写入 §8.1 T1；
2. 把必修-02 的六项前提映射改成分阶段闸门，不再声称 T1~T4 已完全覆盖；
3. 把 M3-E/R/P 正式写入 §5 路线表，并补齐分母、禁止结论和 `capability_status`；
4. 删除 §2 C3、§6 中所有可被理解为“直接用生产 watcher session/重拉即可补齐”的旧说法；
5. 将 T1、T2 的生产访问和会话复制改成分别、明确、执行前取得的用户授权；
6. 写明所有失败只停在证据缺口，不触发研究、shadow、灰度、RESUME、风险预算变更或任何生产写路径。

满足上述条件后，T3/T4 可先行，T1 在只读生产授权后执行，T2 在独立会话材料授权后执行。即便 M0 全部完成，也只允许进入对应的 M1/M2 闸门，不得把 M0 结果解释为 M3-P、M4 或 M5 的授权。
