# Titan 双入场修复方案

状态：**修正后的实现已完成于本地，尚未部署。** 2026-09-11。用户最终裁决为“两腿同等金额”，覆盖之前的“各一半风险”。实现与验收见 [修复记录](2026-09-11-titan-two-entry-implementation.md)。以下保留首版及其未通过的 [评审报告](2026-09-11-titan-two-entry-plan.review.md) 供追溯；首版中的风险权重、市场腿改型等建议不代表最终规则。本文不是生产配置，也不构成历史补单授权。

评审修正：现有多档入口与单笔入口的仓位校验不一致；保护同步使用同方向整仓数量、会替换旧来源记录；空仓会清理保护上下文，尚未证明剩余入场腿及部分提交恢复正确。先验证并修复这些共享基础，再接入双腿。首版中的新计划状态、动态预留预算、market 改 IOC 均不作为已批准设计；不新增一套计划管理系统。

## 问题与已验证事实

Titan 的同一条信号包含首入和第二入场。最近七天 7 条双入场信号中，6 条只生成 e1；GRASS 两腿均生成意向但无执行事件。FET m4471 审计理由明确引用“铁律15”跳过第二腿。

目前规则把执行能力缺口转化为策略限制：

- `hermes-profile/skills/trading/v3-trader/scripts/v3_trade.py:506` 的 `cmd_open` 固定发送 `open_position`。
- `services/control-plane/api/read_api.py:5764` 的 `_OPERATOR_ACTIONS` 未包含 `add_position`。
- 控制面的定量、来源等分支仍有 `action == open_position` 特例；只加白名单无法完成接入。
- `services/nautilus-node/strategy/intent_execution_planner.py:927` 的 `_validate_position` 拒绝已有仓位再次 open，基础 planner 的 add 则要求已有同向仓位。
- `_size_open_order` 每次按有效权益和品种风险比例独立定量。两个独立请求不能表达一个计划的总风险上限。
- 生产提示词要求第一腿成交后跳过第二腿。旧文档虽标注“用户裁决 β”，本轮未找到用户原始确认，不能据此认定为用户约定。

## 推荐设计：一个计划包含两条入场腿

Hermes 一次提交完整计划，使用一个稳定来源 ref。服务端一次审批总预算，节点为两腿生成同一 intent 下的不同订单 ID（序号 01/02）。首腿成交不会把第二腿重新当成一次独立 open。

增加显式的分批计划类型（暂名 `entry_batch`），不把两个离散价格转成 zone。zone 的三档价格和 55/30/15 权重不适用于 Titan 的两个明确点位。

外部语义字段包含：来源、账号、品种、方向、两腿类型和原始价格、共同止损、止盈、分配策略版本、计划有效期。内部执行计划另包含固定数量、总预算、市场腿执行价格边界和每腿稳定序号。精确 schema 在实现时与现有 strict contracts 一同更新。

首腿按信号语义支持 market 或 limit；第二腿保持指定 limit 价格。两腿整体校验和持久化后提交。交易所不提供跨订单原子成交，必须显式管理部分提交和结果未知状态。

### 风险与定量

1. 总风险沿用当前账号权益口径和品种风险比例，每个计划只计算一次。保存当时权益、风险比例与策略版本，后续恢复不能按新权益重算数量。
2. 设总预算 R、每腿风险权重 w、止损距离 d，则每腿数量向下取交易所精度：`q_i = floor_to_step(R * w_i / d_i)`。两腿合计的计划止损损失不得超过 R；合计名义金额、杠杆和可用保证金同时受现有限制。
3. 权重是待确认产品参数。信号明确比例时按经校验的比例；未明确时不让模型临时猜。可以提出 50/50 风险份额，但不能写成用户已同意的规则；50/50 风险不等于等数量或等名义本金。
4. 市价腿必须有可强制执行的价格/滑点边界，用该边界预算；仅用 mark price 估算不能保证成交后的预算。若需要用带价格上限的 IOC 表达，要明确其可能未完全成交的行为。不能通过回退无界市价单消除失败。
5. 已成交风险与未成交腿预留风险共同计入计划占用；止盈或移损不自动释放预算用来扩大第二腿。预算不足应结构化报错，不能静默降级为单腿。
6. 首版限定新信号完整计划。历史 e1 不能直接补 e2，因为已有 e1 可能已经用完单计划预算；历史仓处理需另外核对当前风险和有效性。

### 生命周期与归属

- 首腿部分成交：立即按已成交的本计划净数量建立保护；第二腿只使用原批准的剩余预算。
- 第二腿成交：复用现有保护单同步机制，依据本计划累计净成交量重整 SL/TP；不得按交易所同品种整仓数量接管手动仓或其他频道仓。
- 同一计划重复接收/超时重试/节点重启：恢复原数量和原订单 ID，先查交易所结果，禁止换 ref 再下。
- 首腿已成交而第二腿拒绝或提交状态未知：记录部分执行；保留已成交仓位保护，未知状态完成对账后才决定重试。
- HALT 到达两腿之间：停止尚未发送的新增风险，遵守当前 HALT 语义；不得自动 RESUME。已在交易所的未成交腿由既有撤单政策和计划状态共同管理。
- 计划被明确取消、止损平仓或已终结：撤销本计划剩余入场腿；撤单与成交竞争时仍须接收迟到成交并补齐保护，避免平仓后意外重开。
- 部分止盈后是否保留第二腿、有效期、首腿无成交是否允许第二腿独立成交，需要明确记录策略；不得由实现自行猜测。
- 新计划准入沿用现有仓位校验；不同计划共存、手动同品种仓位兼容属于另一个问题，本次不全局移除 `position_exists`。

## 实现路径

1. Contracts：新增明确的双腿语义及执行 schema、版本、正反例；验证腿序号唯一、两腿同方向、价格/数量/止损合法。禁止未知版本退回单腿。
2. 控制面：新增计划定量与预算逻辑；稳定幂等覆盖两腿和分配版本；审批后执行数量不可在读取时按行情重新生成。持久化计划状态与订单状态的对应关系。
3. 节点：从 `_zone_ladder_order_plans` / `_handle_zone_ladder` 提取可复用多腿提交逻辑，保留原 zone 行为；显式增加 market/limit 混合能力，而不是只把固定三档改成两档。
4. 预算：扩展 `_zone_ladder_dynamic_budget_denial` 同类校验，使市场腿也有可验证的保守估值；在最终订单精度处理后复核合计预算。
5. 生命周期：核对并补齐多腿恢复、终结撤单和本计划成交归属；复用保护单同步，不新增另一套按整仓管理的逻辑。
6. CLI/Hermes：提供一次提交两腿的接口和可读执行回执；能力生效后再替换铁律 5.3/15 与示例。不得先放开提示词，让生产继续尝试不兼容动作。

## 验收

用 Titan ICP m4486（market + limit 2.662、SL 2.58）与 BTC m4487 构造固定行情的离线回放，不连接下单端点。另覆盖两腿 limit。

- 原始双入场到执行提交恰好两腿，参数未丢失；第一腿即时成交后第二腿仍存在。
- 两腿最坏计划损失、最终精度后合计名义金额满足审批预算；预算不足不悄悄改单腿。
- 重复请求、先成交后崩溃、第二腿提交超时及恢复不重复下单。
- 部分成交、多次成交回报、第二腿迟到成交后的保护数量正确。
- 第一腿提交后 HALT，第二腿不新增提交；止损/终结与第二腿成交竞争可恢复。
- 手动订单及其他频道订单不被撤销或纳入本计划保护数量。
- 既有单腿和 zone 三档行为保持通过。

本轮只运行了现有基础测试：重复 open 的仓位拒绝、多档合计额度拒绝、持久化多档只提交一次、第一档后 HALT 阻止后续档。结果 **4 passed, 117 deselected**。这些证明可复用基础存在，不代表双腿功能已经实现或验收。

部署需先完成版本兼容与回滚门禁；新类型只路由到支持它的节点。存在在途双腿计划时，旧版本不能盲目接管；回滚策略必须保留处理在途计划的能力。本文未修改生产状态、未补单、未执行部署。
