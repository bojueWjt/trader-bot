## 背景与前提变化

现有选型报告把建模样本当成系统库里的约 350 条计划，因此把首轮特征压到不超过 10 维、只做固定规则基线。这个前提错了：五个 Telegram 信号频道（舒琴/Titan/Gauls/坚果TV/TraderCash）从 2024 年起的完整聊天记录都可以导出，信号量估计在几千条量级（这是估计，未实测）。前提变化带来三件事要重新设计：

1. 样本规模与证据分级要重估（历史消息只有最后一次编辑时间；删帖不可见，有幸存者偏差；watcher 上线后的消息才有删除记录）。
2. 把几千条消息整理成可读的交易 episode（入场信号 → 管理更新 → 结果）需要一条以 LLM 为主的产线，人工只能分层抽审，现有设计是按几百条规模写的。
3. 样本上了量级后，因子挖掘和表达式搜索从"必然过拟合"变成可行，需要一层表达式 DSL / 算子引擎 / 事件级评估器，现有报告没有选型。

## 要交付的内容（章节编号必须严格按 A–E，便于并排 review）

**A. 样本规模与证据分级重估**
- 给出信号量的估算方法和它依赖的假设；列出 PoC 1a（单频道全量导出）必须实测的量：消息数、信号数、编辑比例、图片比例、回复/引用比例、跨年分布。
- 定义历史消息的证据等级（至少区分：从未编辑 / 编辑过只知最后编辑时刻 / 删帖不可见），每一级允许用于什么（行为特征学习、结局统计、时间严格评估），不允许用于什么。
- 说明怎样用 watcher 时代的删除率给历史时代的幸存者偏差定界。

**B. Episode 组装产线（几千条规模）**
- 分级流水线：消息版本归一 → 规则链接（回复关系、引用、同品种同方向时间窗等） → LLM 裁决歧义 → 生命周期状态机校验 → 分层抽审。每级的输入输出、失败模式、拒答出口。
- episode 的 schema：生命周期事件、每个事件的来源消息 id 与版本可用时刻、证据等级、未观测/右删失标记。
- 人工工作量的上限设计：金标集按 episode 而不是按消息计；分层抽审的层、最小样本、停止规则、Wilson 区间；哪些类别必须人工签字。
- 成本估算表（模型、消息数、含图比例、单价、总价），标明单价的来源与日期。

**C. 表达式引擎 / 因子挖掘选型（作为报告新增 Q6）**
- 至少比较四个候选，必须包含：自写 polars 薄表达式层；AlphaGen expression.py 改造为单标的；Qlib 表达式引擎 ops；遗传编程框架（gplearn 或 DEAP）。可加 PySR 等。
- 评分用现有报告同一公式 S=(30×能力+25×成熟+20×TCO+15×对接+10×退出)/100，逐项给分并给证据（版本、发布日期、许可证、URL）。
- 必须回答：每个算子的前视安全契约怎么验收（截断重算、NaN 注入）；评估器为什么是事件级而不是横截面 IC，事件级评估器的定义；表达式搜索的预算记账（每次尝试记录、多重比较校正、DSR 或等价）；与 walk-forward 主评估怎么衔接；LLM 提假设、人工提假设、遗传搜索三种来源怎么共用同一 DSL。
- 给出推荐，并说明推荐在什么实测结果下会翻转。

**D. 分档建模协议**

- 阈值要么给出统计依据，要么明确标为预注册选择；两者都要说明 events-per-variable 类启发式的局限。
