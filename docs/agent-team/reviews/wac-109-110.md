## 3. 分级意见

### 🔴 Blocker

**🔴-1（wac-109，红线 7）`f6775cb` 的 EXIT trap 让 `apply_rollback_test.sh` 在打印 `APPLY_ROLLBACK_TEST_OK` 之后仍以退出码 1 结束，并且不删 `$WORK`。`run_all.sh` 在有 Caddy 和无 Caddy 两种模式下都是 EXIT=1，caddy_real_test 与 PLAN_MODE 根本没有在 run_all 里运行。**

- 位置：
  - `scripts/ops/o0/tests/apply_rollback_test.sh:43`：`trap '[ -z "$FAKE_PID" ] || kill "$FAKE_PID" 2>/dev/null; rm -rf "$WORK"' EXIT`；
  - `:858` 已经 `kill`/`wait` 过同一个 PID，但没有把 `FAKE_PID` 清空。
- 机制：
  - 退出时 trap 再 kill 一个已经回收的 PID，返回非零；
  - `a || b` 中 b 的失败会触发 `set -e`（该文件 :36 设置了 `set -eo pipefail`）；
  - 结果是脚本退出码被改成 1。在真实运行中 `rm -rf "$WORK"` 也没有执行：三次运行留下 3 个 `o0-rollback.*`。
  - `run_all.sh` 用 `bash … | tail -n 1` 加 pipefail 调用它，于是中止。
- 证据：
  - §1 第 1–3 行：两次 run_all 都是 EXIT=1，单独运行退出码 1，TMPDIR 有残留；
  - §1 第 4 行：`3153652` 上退出码 0；
  - 用 `/bin/bash` 3.2 最小复现：原 trap 得 rc=1，改为 `kill … 2>/dev/null || true` 后 rc=0。
- 为什么是 blocker：run_all 的最后一行是这套离线门禁唯一的通过信号。它现在是红的，但前面的每一行都显示 OK，很容易被读成"通过"。执行者自报的"run_all 真实 Caddy OK"无法复现。
- 修法（任选其一，一行）：
  - 在 :858 之后加 `FAKE_PID=""`；
  - 或者把 trap 改成 `… kill "$FAKE_PID" 2>/dev/null || true; rm -rf "$WORK"`。
  - 修完在合并态重跑 `run_all.sh`（带与不带 `O0_CADDY_BIN` 各一次），要求末行分别是 `ALL_O0_OFFLINE_CHECKS_OK real_caddy=ok` 和 `O0_OFFLINE_CHECKS_OK_WITHOUT_REAL_CADDY`，并且 TMPDIR 没有 `o0-rollback.*` 残留。
  - 本次已单独补跑 caddy_real_test（299/299）和 plan 模式，修复之后预期整体为绿。

**🔴-2（wac-110，红线 5）勘误一有两条写成了与实现相反的规则。它自称"只是把已实现的内容补齐"，这个前提因此不成立。**

- (a) **G-46 占位符集合**：
  - 位置：`contracts/backend-api.md:860`（I-2 (4)"`{env.*}`、`{system.*}` 以外的任何占位符"即 FAIL）、:866（`UPSTREAM_UNRESOLVED` 只留给这两类）、RS-12（:1368）、§9.16 G-46 行（:1508）；
  - 实现：`o0_caddy_watcher_routes.py:1648` 把 `file.`、`time.` 也当作非请求占位符。真实 Caddy 实测 `reverse_proxy 127.0.0.1:{time.now.year}`、`127.0.0.1:{file.port.txt}` 都是 0F 1U，verify 通过，而按契约这两例必须 FAIL；

### 💭 Nit

- 💭-1 G-44 (iii) 的依据是"已被兜底与守卫的 404 截断，其后 I-2 保证没有 8186"。这是一处有明确理由的"无法比较不阻断"。建议在契约里把这个理由写在 (iii) 旁边，免得以后被当成"无法比较＝通过"的先例。

- 💭-3 `shared_tree_check` 算漂移时的 sha，与随后 `--snapshot-out` 的全量快照分两遍读盘。两遍之间文件如果又变了，快照记录的是新内容，而用户接受的是旧内容。窗口很小，而且后续的"前后逐项相同"门禁仍然生效。可以改为从快照中派生漂移清单，一遍读完。

- 💭-5 回滚在 `rm` 单元文件并 reload 之前，没有 `reset-failed`。apply 若在 start 后失败，单元可能残留为 not-found/failed 条目。这不影响 NeedDaemonReload 判定，属于整洁性问题。
