## 🔴 Blocker

### 🔴1 媒体 data URI 的内存失控路径：没有字节上限，组件 state 持有的 data URI 没有条目上限，缩略图按原图分辨率解码

**位置**

- `SignalsScreen.tsx:19`、`:21-32`、`:36-39`：`uri` 存在每一行的 state 里。行滚出视口时（`visible=false`），cleanup 只做 abort，`uri` 不清除，`<Image>` 继续渲染。
- `SignalsScreen.tsx:39`：`<Image>` 没有设置 `resizeMethod`。
- `SignalsScreen.tsx:262`：FlatList 用默认的 `windowSize=21`。
- `watcherMediaQueue.ts:13-20`：`readAsDataURL` 之后没有调用 `blob.close()`。
- `watcherMediaQueue.ts:101-107`：缓存上限只作用于内部 Map，而且是 FIFO（命中时不刷新顺序），不是 LRU。
- `watcherApi.ts:253-256`：`mediaBlob()` 没有大小上限，只靠服务端的 20 MB（§9.9）。

**为什么是失控路径**

1. **"缓存上限 2"是假上限。** 真正决定内存的是挂载着的行组件持有的字符串。FlatList 默认 `windowSize=21`，会保留上下各约 10 屏的行。平板横屏左栏 400dp，每屏约 8–10 行，所以 200 条几乎全部处于挂载状态。每张加载成功过的图，它的 data URI 都会一直留在 JS 堆上，同时留在原生 Image 的 prop 里。M10（把缓存改为无上限）存活，也印证了缓存上限本身不起作用。
2. **每张图有多份拷贝。** 设原文件大小为 S，按 RN 0.82 的实现，一次加载的路径是：
   - 原生 BlobModule 里的 `byte[]`：S
   - `FileReaderModule.readAsDataURL` 的 base64：Java String 为 UTF-16，约 2.67S；StringBuilder 过程中还有一份临时拷贝，约 2.67S
   - 进入 Hermes 的字符串：约 1.33S
   - 作为 `<Image>` 的 uri prop 回到原生：Java String 约 2.67S
   - Fresco 解码 base64 得到的 `byte[]`：S
   - 最后是位图

   单张的瞬时峰值约 10S。S=20 MB 时约 200 MB；并发 2 张就是 400 MB 以上，已经超过 §5.2 的 300 MB 预算。清单没有设 `largeHeap`，Java 堆上限由设备的 `dalvik.vm.heapgrowthlimit` 决定，平板通常为 256–512 MB，这种情况下有 OOM 风险。
3. **缩略图不缩放。** `ReactImageView.kt:574-576`：`resizeMethod=AUTO` 只对 `content://` 和 `file://` 生效，data URI 不会被缩放。一张 2560×1920 的 Telegram 原图，在 80×80 的缩略图里会按 ARGB 解码成约 19.7 MB 的位图，一屏 8–16 张就是 160–315 MB。更大的图还可能触发 Android 的 "Canvas: trying to draw too large bitmap" 崩溃。
4. **200 条常规图片的估算。** 按每张 300 KB 计算：JS 字符串约 80 MB，原生 prop 字符串约 160 MB，再加上一屏的全尺寸位图 160–315 MB。合计明显超过 300 MB。§5.2 的性能验收（"内存峰值 < 300 MB"）按目前的实现可以预期会失败。

**建议修法与阈值**（都不需要改原生代码，也不需要新增依赖；另附一个需要 Planner 裁定的长期方案）

1. **字节上限在服务层判定，不读 body。** 给 `mediaBlob(filename, {signal, maxBytes})` 增加 `maxBytes` 参数。拿到 200 响应后先读 `Content-Length`（§9.9 响应头白名单里有这个头，网关按整文件大小判定）。头缺失、不是合法整数、或超过上限时，abort 同一个 controller，抛出客户端的 `media_too_large`，不调用 `blob()`。
   - 列表缩略图：`maxBytes = 1 MiB`（1 048 576）。超过时显示占位"图片较大，点开查看"。
   - 详情大图：`maxBytes = 8 MiB`（8 388 608）。超过时显示占位"图片过大，暂不预览"。
2. **强制缩放解码。** 缩略图和详情大图都设 `resizeMethod="resize"`（这样 data URI 也会走 Fresco 的 ResizeOptions）。缩略图位图就降到约 200×200 px 的量级（约 160 KB）。
3. **行组件在不可见时释放 uri。** 在 `visible=false` 的 cleanup 里执行 `setUri(false)`；或者组件只保存文件名，渲染时向缓存取值。这样 JS 持有的 data URI 条数就等于可见行数。同时给这个 FlatList 设 `windowSize` 为 5–7。
4. **缓存改为真正的 LRU，并设字节预算。** 命中时刷新顺序。缓存总量按 data URI 字符数计算，不超过 24 MiB，条目不超过 60。单条超过 2 MiB 的（详情大图）不进缓存，只在详情页打开期间持有。这样最坏情况下，JS 端约为 24 MiB 缓存加上可见行的约 16 × 1.4 MiB，原生端的 prop 字符串约为它的 2 倍，位图因为有缩放可以忽略。合计在 100 MB 以内，300 MB 预算有余量。
5. **读完立即释放 Blob。** FileReader 完成或失败后调用 `blob.close()`，不要等 GC 通过 BlobCollector 回收。转换完成后，如果 signal 已经 abort，就不要写进缓存。
6. **测试（与上面几条一起补）：**
   - `Content-Length` 超过上限时不调用 `blob()`，并且 signal 被 abort
   - 头缺失时拒绝
   - 缓存超过字节预算或条目上限后，最久未用的条目被淘汰，命中的条目会刷新顺序
   - 行组件 `visible` 从 true 变为 false 后，不再渲染 `signal-media`
   - `<Image>` 带有 `resizeMethod="resize"`
7. **长期方案（需要 Planner 裁定，因为要改 `android/` 的 manifest，超出本任务范围）：** 注册 RN 的 `BlobProvider`，改用 `URL.createObjectURL(blob)`，或者落盘后用 `file://`。这样可以彻底避开 base64 带来的 4–5 份拷贝，`AUTO` 模式也会自动缩放。

## 🟡 建议

1. **30 秒轮询会把已经翻出来的旧页截回首页。** 位置 `SignalsScreen.tsx:114`、`:117`：非追加刷新时执行 `reconcileRows(previous, parsed)`，parsed 只有最新 500 条。用户翻到第 2 页后，下一次轮询就会把列表缩回 500 条，FlatList 内容跳动，正在看的行会消失。建议：轮询只刷新首页，按 id 与已有的旧页合并（`mergeRows`），并保留已加载的游标深度；或者在用户已经翻页时，只把轮询结果并到顶部。
2. **一次瞬时失败会让整个列表消失。** 位置 `SignalsScreen.tsx:124`、`:262`：`listError` 的渲染优先级高于已有的行，一次 30 秒轮询失败（比如 `gateway_busy`）就会把整个列表换成错误文案，要等到下一次成功才恢复。另外 `Promise.all` 把 status 和 list 绑在一起，status 失败会连带丢掉 list 的结果。建议：已有数据时保留列表，只在状态条或列表顶部显示错误（计划里状态条的"接口失败"本来就是用来表达这个的）。
3. **状态条永远不会显示"正常"。** 位置 `signalModel.ts:109-128`、`SignalsScreen.tsx:247`：只要活性正常就显示"静默"，完全没有用到 `last_message_ingested_at`。§5.1 对"静默"的定义是"活性正常但**无新消息**"，§5.2 也要求"断网、静默频道、正常三种情形分别显示正确状态"。现在消息持续进来时状态条也显示"静默"，与定义不符。建议由 Planner 裁定：活性正常、并且 `last_message_ingested_at` 在某个窗口内（例如 300s 或 30 分钟）时显示"正常"，否则显示"静默"。两者都不算故障。同时补上状态条文案的渲染测试（M30 存活）。
4. **BackHandler 和轮询不看焦点。** 位置 `SignalsScreen.tsx:188-201`、`:157-176`：Tab 屏幕一直处于挂载状态。compact 下打开信号详情后切到交易 Tab，或者 push 到 `PositionDetail`，第一次按返回键会被信号页的监听器吞掉（RN 的 BackHandler 先调用后注册的监听，而它比 NavigationContainer 注册得晚），用户看到的是返回键"没反应"。同样地，离开信号 Tab 之后，每 30 秒仍然会发 status 请求和最多 500 行的列表请求，占用网关的 config 预算。建议：用 `useFocusEffect` 或 `useIsFocused` 包住这两段逻辑。
5. **媒体失败会一直保持，也没有手动重试。** 位置 `watcherMediaQueue.ts:27`、`:39-41`、`:110-112`，`SignalsScreen.tsx:20`、`:22`：`timeout`、`gateway_busy`、`watcher_unavailable`、`network_error` 这类瞬时错误也会被永久记进 `failed`，队列的生命周期约等于整个应用，所以一次网络抖动后，受影响的图片在整个使用过程中都不会再显示。"不自动重试"不等于"永不重试"。建议：只有 404、416、`media_too_large`、非法文件名才永久失败；瞬时错误显示"点按重试"，并在下一次状态回读成功后清掉瞬时失败记录。`failed` 集合也要设上限。
6. **测试缺口**（代码是正确的，但下列变异存活）：
   - M1（卸载时不 abort）、M28（已开始的任务在最后一个观察者离开后不 abort）、M29（去掉可见性门控）：约束 (a) 要求的"卸载或滚出视口时 abort"在组件层和队列的"已开始任务"这一层都没有测试。建议加两个用例。第一个：渲染一行带 `media_filename` 的消息，mock 住 `mediaBlob` 并捕获 signal，先把行设为可见，再设为不可见，最后卸载，分别断言 signal 被 abort。第二个在队列层：2 个任务已经开始后，abort 它们唯一的观察者，断言对应的 `mediaBlob` signal 被 abort，并且排队中的第 3 个任务开始执行。

## 💭 Nit

1. M15b：把 disconnect/reconnect 的请求期限改成 1s 仍然全绿。N19 用例只推进了 5 001 ms，能证明期限不超过 5s，但没有锁住下限。可以参照 N14，先推进 4 999 ms 断言请求还没被 abort。
2. M14 虽然被抓住了，但失败方式是进程级的 unhandled rejection 崩溃（`watcherApi.test.ts` 的 60 秒用例在推进时钟之后才挂上 `rejects`），而不是断言失败。建议在推进时钟前先写 `const settled = expect(result).rejects.toMatchObject(...)`，推进之后再 `await settled`。
3. `media()`（`watcherApi.ts:249`）仍然公开返回裸 Response，调用方可以在定时器之外读 body，这和约束 (b) 的"不得在服务层之外读裸 Response body"有张力。目前没有调用方。建议限定为 HEAD 专用，或者改成私有。
4. `parseMessages` 遇到一行时间格式不合法就会让整页失败（`signalModel.ts:68`）。可以只丢弃这一行，并计数。
5. 订单详情用 `${row.entry_price ?? '未知'}` 直接插值（`signalModel.ts:85-88`），值是对象时会显示成 `[object Object]`。
6. `rightPane.maxWidth` 复用了断点常量 `EXPANDED_MIN_WIDTH`（`SignalsScreen.tsx:308`），把"断点"和"详情最大宽 840dp"耦合在了一起。建议单独定义 `DETAIL_MAX_WIDTH`。
7. `completeSignalAction` 在组件卸载后仍会轮询最多 60 秒（`signalConnection.ts:29-51`）。可以传入 signal 提前结束。
8. `onEndReached`（`SignalsScreen.tsx:262`）以 `current.length >= 500` 为条件，没有 hasMore 标记。翻到底之后，每次滚到末尾都会再发一次同一个游标的请求。
9. 队列的 `media()` 和 `dataUri` 转换在 60 秒定时器之外（`watcherMediaQueue.ts:98-99`）。转换期间 abort 不会生效，转换完成后结果照样写进缓存。这一条与 🔴1 第 5 点一起修即可。

## 做得好的地方

- `mediaRequest` 把非 2xx 的错误体读取和 `consume` 都放进了同一个 race，所以同一个 60 秒定时器真正覆盖到了 body 读完为止。测试用的是永不 resolve 的 `blob()`，没有依赖 polyfill 的缓冲行为，这正是上轮 🟡1 要求的形态。
- 用 `cancelledPromise` 让外部取消立即决胜，`cancelled` 不会被误报成 `timeout` 或连接失效。上轮的 N14、N15、N19 这次都有精确的测试。
- 队列按观察者集合计数：同一个文件有多个观察者时，只有最后一个离开才会取消。这比简单的 Map 去重更正确（快速滚动时同一张图会出现在列表和详情两处）。
- `completeSignalAction` 的重放用例同时断言了两次 write 的 client_ref 都是原值（M9、M9b 都被抓住）。确定性失败时不轮询，结果未知时才回读，分支设计清晰。
- 请求期限只对"带 client_ref 的 disconnect/reconnect"用 5 秒，其他请求仍是 12 秒，没有误伤。
- `reconcileRows` 复用了未变化行的引用，数据没变时也保持列表数组的引用，给 memo 打好了基础。
