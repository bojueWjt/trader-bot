## 5. 分级意见

### 🔴 blocker

无。

### 🟡 建议

**🟡-1 清单里的 `*` 放进 Caddy 的 `path` 匹配器后是"前缀匹配"，不是"一个段"。这条写给 O-0 和 WGW-1.0.2 勘误，不是执行者的问题：执行者完全按 §9.14.3 的写法实现。**

我读了 Caddy master 的 `modules/caddyhttp/matchers.go`（`MatchPath.MatchWithError`，约 `:429-535`；`Provision` 在 `:410-420`；`CleanPath`/`cleanPath` 在 `caddyhttp.go:279-308`），又把非 `%` 分支逐行移植成 Go 程序实测，结论如下：

1. **`*` 在末尾时按前缀匹配，会跨段。** 模式里只有一个 `*` 而且在结尾时，Caddy 执行 `strings.HasPrefix(cleanedPath, pattern[:len-1])`。实测 `/m/v1/watcher/trading/accounts/*` 能命中：
   - `/…/accounts/`（空段）
   - `/…/accounts/a/b/c`（多段）
   - `/…/accounts/a%2Fb`（`r.URL.Path` 已解码成 `a/b`）
   - `/M/V1/WATCHER/TRADING/ACCOUNTS/x`（大小写不敏感）

   本清单的 4 个带 `*` 的行都属于这种情况。只有 `*` 出现在中间时，Caddy 才走 `path.Match` 的单段通配（实测 `/accounts/*/x` 不会命中 `/accounts/a/b/x`）。本清单没有这种行。
2. **所有行都会先做规范化再匹配**：路径转小写；`path.Clean` 合并 `//`、解析 `..`，保留结尾斜杠。实测结果：`/m/v1/watcher/x/../status` 和 `/m//v1/watcher/status` 都能命中精确行 `/m/v1/watcher/status`，而 `/m/v1/watcher/status/` 和 `/…/orders/active`（对 `orders` 行）不会命中。但是 `reverse_proxy` 转发给上游的是原始路径，不是规范化之后的路径。
3. **为什么不是红线**：Caddy 只是第一层。真正的边界是 operator-query 的前缀中间件：它按 `(method, raw_path)` 精确匹配生成物，匹配不上就自己返回 404/405（§9.4）；§9.14.5 还有 `%2F`、`%2e`、`//`、大小写、尾斜杠等独立负例。所以 Caddy 放得宽，只会让一些垃圾请求打到网关再被拒绝，不会越过鉴权，也不会进入 watcher。
4. **O-0 把清单并入真实 Caddyfile 时必须做到**：
   - (a) **不要把 `{param}` 原样贴进 Caddyfile。** Caddy 会先对模式做 `repl.ReplaceAll(pattern, "")`，未知占位符会被替换成空串，`/accounts/{account_id}` 就变成对 `/accounts/` 的精确匹配。生成器改写成 `*` 正是为了避免这个问题。
   - (b) 每一行都用 `path` 加 `method` 组成的具名匹配器（`@x { path …; method … }`）。`path` 本身不管方法。媒体行的 HEAD 要显式列出。
   - (c) 如果想让 Caddy 层也只放行单段，把这 4 行改用锚定的 `path_regexp`，例如 `^/m/v1/watcher/trading/accounts/[^/]+$`，可以直接写成 YAML 里对应的 `gateway_pattern`。注意 `path_regexp` 区分大小写，作用对象是解码并 clean 之后的路径（`matchers.go:812-823`），`symbol` 的 `^[A-Z0-9]{2,32}$` 会因此不再匹配小写。如果接受前缀语义，就在 O-0 文档里写明"Caddy 只做粗筛，精确边界在网关"。
   - (d) `/m` 的 `handle_path`/`handle` 块里，不允许出现兜底的 `reverse_proxy` 到 operator-query；清单之外的路径应落到 404 或其他既有路由。
   - (e) 建议 O-0 写一个核对脚本：解析 adapt 之后的 Caddy JSON，抽出 `/m/v1/watcher/` 下的全部 `(path, method)`，与本清单逐行比较，对称差必须为空，且比较行数大于 0。不要靠人工肉眼核对。
   - (f) 上面的行为以 Caddy master 源码为准。path cleaning 是 #4407 引入的。O-0 应确认生产 Caddy 的版本（`caddy version`），版本过旧时要单独复核第 2 点。
   - (g) 沿用 wac-007 🟡-3：browser 凭据在 Caddyfile 里用运行时占位符 `{env.WATCHER_BROWSER_PROXY_TOKEN}`，不要用 `{$VAR}`。
5. **建议 WGW-1.0.2 勘误**（与 A-6 召回、R14 合并）：在 §9.14.3 写明清单中 `*` 的语义是"恰好一个非空段"，并规定 O-0 的翻译方式（`path_regexp`，或者接受前缀并注明）。这样清单才是规范性的，不会因为 Caddy 语义被理解成前缀。
