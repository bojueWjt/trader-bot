## 3. 真实 uvicorn 验证

`read_api` 依赖 fastapi 和 psycopg，只装了 uvicorn 的解释器里导不进来。所以用了等价方式：在 scratchpad 里写一个最小 ASGI 包装模块，在 lifespan startup 时调用 `watcher_config_snapshot.start_if_enabled()`，**连续调用两次**（read_api 本身在 `read_api.py:10684-10685` 把它注册成 on_startup）。另起一个本地假快照源，要求带假 Bearer，返回带哨兵值的 revision 7。然后用 `python -m uvicorn wrapapp:app` 启动，**不带 `--log-config`**，与 `scripts/jp24-p1-control-plane.sh:304` 的启动方式一致。stdout 和 stderr 分开收集。

## 5. 🔴 blocker

### 🔴-1 `test_start_emits_stderr_under_uvicorn_defaults` 在控制面全量中 5 个用例全部失败

- 位置：`tests/control-plane/api/test_watcher_config_snapshot_logging.py:148`（`sys.path[:0] = {sys.path!r}`）与 `:154`（子进程里 `from test_watcher_config_snapshot import Clock`）。
- 现象：全量跑时子进程返回 1，traceback 如下：
  ```
  File "tests/control-plane/api/test_watcher_config_snapshot.py", line 11  (import read_api)
  File "services/control-plane/api/read_api.py", line 114
  File "services/control-plane/settings/service.py", line 10
  ImportError: cannot import name 'record_settings_audit' from 'audit' (.../services/control-plane/security/audit.py)
  ```
- 原因：子进程原样复制了父进程的 `sys.path`。全量收集时，各目录的 conftest 累积插入了几十个路径，其中 `services/control-plane/security` 排在 `services/control-plane` 前面，于是一个新进程里 `import audit` 会先命中 `security/audit.py`，而不是 `audit/` 包。父进程没有出问题，是因为 `audit` 早就在 `sys.modules` 里了。子进程又通过 `test_watcher_config_snapshot` 间接导入了整个 `read_api`，所以踩到了这个坑。单独跑三个文件时 sys.path 很短，所以是绿的。
- 后果：合入后集成分支的全量基线从 858 passed + 5 失败变成 863 + 10。之后每个任务的审查都要人工把这 5 个剔掉，真正的回归会被淹没。这正是红线 7 “测试”要防的情况：验证只在一个挑过的子集里是绿的。
- 修法（只改测试文件）：
  1. 子进程不要继承父进程的 `sys.path`，只放它真正需要的一个目录：`services/control-plane/api`。`watcher_config_snapshot.py` 只依赖标准库。
  2. 子进程不要导入 `test_watcher_config_snapshot` 和 `test_watcher_config_snapshot_logging`，因为它们会连带导入 read_api 和 pytest。把 `Clock`、payload 构造、`_TOKEN` 内联进脚本，或者把它们放到一个不导入 read_api 的小 helper 模块里，由父进程通过 `-c` 参数传入。
  3. 验收：`set -o pipefail; .venv-arch/bin/python -m pytest tests/control-plane -q -p no:cacheprovider` 结果为 **868 passed, 5 failed**，并且 5 个失败全部是 `test_frozen_stage_verification_*`。

## 6. 🟡 建议

- **🟡-1（沿用上轮 🟡-4，未修，不阻塞）** `start()` 在 `refresh()` 抢不到 `_flight` 时会误报 `result=cold`（`watcher_config_snapshot.py:499-506`）。正常启动路径下不会触发，可以在修 🔴-1 时一并处理，也可以另开任务。

## 7. 💭

- 💭-1 M2 是靠 `:208` 的结构断言 `logger.propagate is False` 抓住的，没有从行为上证明“以后 root 被配置时不会重复输出”。可以在子进程里 start 之后再调用 `logging.basicConfig()`，然后刷新一次，断言这一行在 stderr 里只出现一次。
- 💭-2 `_ensure_info_logging` 每次调用都会无条件执行 `_LOG.setLevel(logging.INFO)`（`:549`）。如果将来运维通过 `--log-config` 有意把这个 logger 设成 WARNING，会被覆盖。可以只在 `_LOG.level == logging.NOTSET` 时设置。生产目前没有 log-config，所以不影响本次。
- 💭-3（沿用上轮 💭-2）`role=operator-query` 仍然是硬编码（`:502`）。
- 另外，挂上去的 handler 没有设 formatter，输出的行没有时间和级别前缀。journald 会补时间戳，runbook 用 grep `snapshot_warmup` 就能取到，所以这样可以接受。

## 9. 表扬

- `_ensure_info_logging` 沿祖先链查找生效的 handler，同时遵守 `propagate=False` 截断，并排除 `NullHandler` 和级别高于 INFO 的 handler。“已有可用 handler 就不挂”的判断是准确的。参数化的 5 种拓扑（none / module / root / blocked_root / null）把每条分支都覆盖到了，M1、M7 靠它们才被抓住。
- 子进程加 `capfd` 的做法选得对：dictConfig 会关闭已有 handler，放在子进程里做可以不污染 pytest 自己的日志，而且测的是真实文件描述符上的输出，正好补上了上轮 caplog 遮住的那个缺口。缺的只是 sys.path 隔离。
- `test_refresh_failure_logs_expiry_without_state_read` 全程不读 `.state`，准确锁住了上轮 🟡-1 所说的后台路径。
