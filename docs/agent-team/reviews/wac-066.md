## 3. 核对明细

### 3.1 游标语义与 app 一致

- 字段名：app `cursorFor`（`signalModel.ts:101-107`）发送 `before_created_at`、`before_id`，与 YAML `query_params` 一致。
- 格式与时区：服务端 `created_at` 由 SQLite `datetime('now')`（`trading-api.js:82,281`）或 `db_manager.py:_now()`（UTC `%Y-%m-%d %H:%M:%S`）写入，两个写入者格式相同。app 把原字符串 `encodeURIComponent` 后回传（空格变 `%20`，不会出现 `+`），服务端按原文比较，不做时区换算。app `utcMillis` 补 `Z` 后按 UTC 解析，排序 `createdAtMs DESC, id DESC` 与服务端文本序等价。
- 严格小于：`trading-api.js:381,412` 用行值比较 `(created_at, id) < (?, ?)`。better-sqlite3 11.10.0 自带 SQLite 3.49.2，支持行值比较。`before_id` 绑定为 Number；我另做了传字符串的变异（C5），结果同样全绿，说明整数亲和性生效，不存在"999" > "1000"这类字典序问题。
- 并列：探针 E1 用 5000 行，按 37 行一组共用同一秒（不同秒数 < 200），而且插入顺序打乱，保证 id 顺序 ≠ 时间顺序。每页 500 行，页边界必然落在并列组中间。结果无重、无漏，顺序与 `ORDER BY created_at DESC, id DESC` 的真值逐项相等。

### 3.2 hours 窗口与 R18 / R21

- app 翻页和轮询都不传 `hours`（`SignalsScreen.tsx:132-134`），两者都用缺省 24 小时窗口。`trading-api.js:376,401` 的缺省值与 YAML 一致，而且窗口条件在带游标时同样生效（`:379,405`）。
- E3：24 小时内 50 行、窗口外 50 行。游标停在窗口内最旧一行时返回 `[]`，不会漏出窗口外的行；加 `hours=48` 后返回那 50 行。所有行老化出窗口后，轮询返回 `[]`，app 的 `mergePolledPage` 把列表清空（R21）。
- E2（R18）：先翻 3 页得到 1500 行；再插入 10 行（其中 5 行与现存最新一秒并列、id 更大），轮询结果与已加载行有交集，合并成 1510 行，继续翻页后得到完整集合。随后 3 秒内突发 600 行，轮询页与已加载行无交集，列表被替换为 500 行；从新列表继续翻页，最终得到全部 5610 行，无重无漏。

### 3.3 limit、非法参数、白名单

- `limit` 缺省 500（`:377,402`），上限 500 由 YAML `max: 500` 在校验层拒绝。E4：700 行时不传 limit 返回 500 行，`limit=501` 返回 400。
- 非法参数（E5，gateway 与 browser 两种身份各跑一遍，共 20 种写法）：`hours=0/169/abc/-1/%2024`、`limit=0/1e2/501`、重复键、未知键、大小写不同的键、`hours[]`、单独的 `before_id` 或 `before_created_at`、`T` 或 `Z` 格式时间、`before_id=0/-1/1.5`、briefings 上的 `channel`、`status`。全部返回 400 `invalid_query`，`message` 取自固定文案；browser 身份带 `error`（等于 `message`），gateway 身份不带，符合 §9.5。
- 白名单：messages 为 `[channel, hours, limit, before_created_at, before_id]`，briefings 为 `[hours, limit, before_created_at, before_id]`。服务端由生成的路由表逐行校验，与 YAML 一致。watcher 层自己也拒绝未知参数，不依赖网关先过滤。
- `channel` 由 `if (channel)` 改为 `!== undefined`（`:407`）。空的 `channel=` 以前等于不过滤，现在会被校验层以 400 拒绝。这与契约一致，站点和 app 都不传该参数，没有兼容影响。E6：按 channel 过滤后带游标翻完 1200 行，没有混入其他频道的行。

## 🟡 建议

1. **仓库分页测试抓不住"只按 id 翻页"**（`__tests__/read-model.test.js:99-100`）。夹具先插入较旧的行、再插入较新的并列行，id 顺序与时间顺序完全一致，所以 C3、C4 两种错误游标都能通过全部仓库测试。生产中 briefings 的 `created_at` 由 Python 客户端时钟写入，watcher 的 messages 也可能在时钟回拨时出现 id 与时间不一致，这时错误实现就会丢行或重复。建议：夹具里插入一批 id 更大但 `created_at` 更早的行（或像探针那样打乱插入顺序），然后断言翻页结果等于 `ORDER BY created_at DESC, id DESC` 的真值。
2. **"以自己为父账号"用例测的不是这个分支**（`__tests__/trading-api.test.js:511`）。它在创建路径上提交 `parent_account_id = account_id`，但此时该账号还不存在，即使删掉 `config-store.js:214` 中的 `parentId === row.account_id`，请求也会在下一步因"父账号不存在"返回 400，所以 S1 存活。自指只有在更新已有主账号时才能到达：`PUT /api/trading/accounts/<已有 main>`，body 为 `{account_type:"subaccount", parent_account_id:"<自身>"}`。我在副本中验证过，这条用例在 NOOP 下通过，在 S1 下失败（S1 下服务端返回 200 并写入自指行，之后 `config-snapshot` 的 `:607-608` 会判定快照无效）。非法 account_type 那条（`:510`）有 CHECK 约束兜底，行为上已经锁住，不需要改。

## 💭 Nit

1. `telegram_messages` 和 `briefings` 没有 `(created_at, id)` 索引，每页都是全表扫描加临时 B 树排序。我在 10 万行上实测约 34 ms/页，按 7 天保留期估算可以接受。以后如果频道量上来，可以考虑加索引；那属于 watcher schema 变更，不在本任务范围内。
2. `trading-api.test.js:596-614` 先停用 `main-live`，结尾再重新启用；中间任何断言失败都会让后续用例在错误状态下运行。可以改用独立账号，或放进 `try/finally`。
3. `deployment-guide.md:47,64,191` 仍然写着"访问 `http://localhost:9100`"。W-0 之后，直连 9100 没有 Caddy 注入的 proxy 头，会返回 401。这几处不是 curl，不在 wac-075 🟡-2 的字面范围内，但属于同一类文档漂移，建议下次改文档时一并改成"经站点入口登录"。
