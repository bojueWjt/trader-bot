## 总评

这份草案整体质量很高，方向正确，下面几点值得点名表扬：

- 脚本默认只打印计划，`--execute` 必须同时满足 root、`/srv/trader-v3` 标记、`/srv/trader-staging/o0-*` 目录和 auth-id 格式（本机实测：plan 模式下四个脚本都没有执行任何动作）。
- 现场核对脚本从 stdin 进入，每条子命令都接了 `</dev/null`；env 文件只打印变量名；`env-exec` 不经 shell 展开加载 `v3.env`；浏览器凭据用 `{env.X}` 占位符。
- 凭据比较全部用摘要。manifest、sums、catalog、Caddy 模拟器都把 "compared=0 / 模拟器看不懂" 判为失败，不当作通过。
- Caddy 核对工具 14 种变异全部抓到；JS 数字格式跨语言核对了 3008 个数；泄露测试首轮抓到一个真实的重定向泄露并已修复。
- Caddy restart 之后舰队状态变化时只停下、不回滚。这个取舍是对的：回滚会再 restart 一次，而是否 RESUME 只由用户决定。
- 回退数据的定义与计划 §4.1 一致（回退那一刻经校验的真库一致快照，不是 09-06 文件，也不是 30 天备份）；"开关开着时先关开关再回滚 watcher"的顺序规则写对了。
- 部署顺序 Caddy → watcher → operator-query 的中间态分析成立，每个服务只重启一次（回滚除外），不重启 node-control / event-ingest。

阻断集中在五处：舰队守卫可以空转通过、auth-id 和阶段没有绑定、apply 不依赖 preflight 的结论、基线工具看不到 WAL、JSON 脱敏只挡已知形状。每一处都有本机复现。修法都很小，但这些是生产 runbook 的安全机制本身，按最高标准不能带着合入。

## 2. 🔴 Blocker

### 🔴-1 舰队"变化即停"守卫可以空转通过，也看不见冻结的心跳

位置：`scripts/ops/o0/o0_common.sh:117-133`（`o0_fleet_state_cmd`、`o0_record_fleet_state`、`o0_compare_fleet_state`）；各阶段调用点在 `o0_deploy_caddy.sh:100-101`、`o0_deploy_watcher.sh:162-163`、`o0_deploy_operator_query.sh:131-132`。

问题：
1. 查询返回 0 行时，两个空文件 `diff` 相等，输出 `FLEET_STATUS_UNCHANGED`。这正是"无法比较当成相等"。
2. 只比较 `status` 列，`hb_age` 被 `awk '{print $1,$2}'` 丢掉了。`docs/agent-operations.md` §0 原文是"心跳冻结(age 大)= 节点死了而不是'没变化'"。Caddy restart 切断的正是节点到控制面的心跳通道，这时 DB 行里的 status 仍是旧值。
3. `after-*` 快照紧跟在 `systemctl restart caddy` / `is-active` 之后，没有等待窗口。节点 fail-closed HALT 要等通道恢复后的下一次心跳才会写回 DB（记忆 jp24-trader-ops-entrypoints：08-30 restart 一瞬即全舰队 HALT），立即采样会与之竞速。
4. apply 用的 `before-*` 是 preflight 时记录的，可能已是几小时前；中间用户自己的状态变化会被算到部署头上，反之亦然。

本机复现：空文件对空文件 → `FLEET_STATUS_UNCHANGED`；`account-a ACTIVE hb_age=1.0` 对 `account-a ACTIVE hb_age=412.7` → `FLEET_STATUS_UNCHANGED`。

修法：
- 采样时断言行数等于期望节点集（a–d 四行，node_id 集合一致），否则判 UNCOMPARABLE 并退出。
- 比较时同时断言 after 中每个节点 `hb_age` < 阈值（建议 10s）。
- after 采样前等待一个稳定窗（例如 ≥ 3 个心跳周期，轮询直到全部 hb_age 新鲜或超时判失败）。
- 每个 apply 的第一步重新记录 `before-*`，preflight 的快照只用于门禁。

### 🔴-2 auth-id 只校验格式，不与阶段绑定；破坏性 restore-db 的授权号根本用不了

位置：`o0_common.sh:104`（正则 `^O0-A[0-9]{2}(-…)?$`）；`o0_deploy_watcher.sh:183-191`（`phase_restore_db`）；`docs/agent-team/release/o0-runbook-deploy.md:86`（W-6 写的是 `--auth-id O0-A07R`）；`o0-authorization-list.md:32`。

问题：
- 本机实测 `O0-A07R` 被正则拒绝，所以 runbook W-6 的命令照抄执行不了。执行者最自然的"修复"是改成 `--auth-id O0-A07`，而脚本会接受：破坏性换库就这样挂在"上线"授权下执行，`authorizations.log` 里的记录也会是错的。
- 任何阶段都接受任何格式合法的 ID。例如 Caddy apply 可以带 `O0-A01`（只读核对的授权）执行。这样"执行需 `--auth-id O0-Axx`"只是一个形式门，授权清单与脚本之间没有任何可验证的对应。

修法：每个脚本内置 `phase → 允许的授权 ID` 表，例如 caddy `apply|rollback → O0-A05`；watcher `build → O0-A04`、`apply|rollback → O0-A07`、`restore-db → O0-A07R`；oq `apply|rollback → O0-A08`；preflight/verify 允许所属阶段的 ID。正则改为允许 `O0-A07R` 这类后缀字母。restore-db 另加一个显式确认参数（例如 `--i-understand-data-loss`）。

### 🔴-3 apply 不依赖 preflight/build 的结论：门禁在停服务之前完成只靠自觉

位置：`o0_deploy_caddy.sh:86-102`（`:87` 只是 NOTE）；`o0_deploy_watcher.sh:125-164`（`:126` 只是 NOTE）；`o0_deploy_operator_query.sh:90-113`（`:91` 只是 NOTE）。

AGENTS.md 铁律："部署门禁校验必须全部完成于停节点之前；门禁失败 = 中止部署并保持原版本运行"。现在的 preflight 和 apply 是两次独立调用，apply 不检查 preflight 是否跑过、是否通过、是否针对同一份候选：

- Caddy apply 不复核候选 Caddyfile 是否就是 preflight 验证过的那一份（没有 sha 绑定），安装后在 restart 之前也不重跑路由 verify，只做了 `caddy validate`。
- watcher apply 不检查 bundle 完整性、`deploy_candidate`、线上源码仍等于基线、凭据 check、`MIGRATION_DRYRUN_OK`，也不检查候选镜像是否存在。如果 build 没跑，`docker tag "$CAND_IMAGE"`（`:149`）会在 env_file 与源码已经写入之后才失败。ERR trap 回滚接着会执行 `up --force-recreate`（`:119`），凭空多出一次 watcher 重建，也就多出一段信号空窗。
- operator-query apply 不检查 venv 版本、基线 manifest、import 冒烟是否通过。

修法：preflight（watcher 还包括 build）成功时写 `evidence/<stage>.gate.ok`，内容为 bundle tgz sha、`RELEASE.json` candidate、候选 Caddyfile sha / 候选镜像 ID、凭据集 watcher.env 摘要、时间。apply 的第一步校验该文件存在、字段一致、足够新鲜（参考 AGENTS 证据新鲜度门，建议 ≤ 1h），并重跑廉价门禁：SHA256SUMS、`deploy_candidate`、live == baseline manifest、`docker image inspect $CAND_IMAGE`、`grep MIGRATION_DRYRUN_OK`。任何一项不满足，就在任何写入之前 die。

### 🔴-4 基线工具以 `immutable=1` 打开数据库，看不到 WAL；W-2 迁移演练的迁移后分析测不到迁移

位置：`scripts/ops/o0/o0_watcher_config_baseline.py:104-110`（`open_copy` 用 `?mode=ro&immutable=1`）；`o0_deploy_watcher.sh:93-108`（演练容器用 `docker rm -f` 即 SIGKILL 结束，随后 `:103-108` 在同一个 `dryrun.db` 上做迁移后分析）。

事实：watcher 以 WAL 模式打开数据库（`auto/wac-011:lib/trading-api.js:48` 的 `journal_mode = WAL`）。演练容器被 SIGKILL，没有正常关闭，迁移写入（`config_revision`、`config_audit`、可能的表重建）停留在 `dryrun.db-wal` 里。`immutable=1` 会让 SQLite 忽略 WAL，只读主文件。

本机复现（scratchpad/walt）：子进程在 WAL 库里建表写行后 `os._exit`，此时 `immutable=1` 看到 `tables ['a'] rows 1`，`mode=ro` 看到 `tables ['a','config_revision'] rows 2`。

后果：迁移后分析看到的是迁移前的库。`:106` 的 `assert revision == 0` 会因 `revision=None` 必然失败，于是 W-2 这一步按现在的写法永远过不了。如果有人为了"跑通"去掉这个断言，三表比较就会给出 `UNCHANGED`，而且是基于根本没看到的数据。这就是"为绕开报错改造输入"的前兆。wac-011-r3 🟡-1 要求的"在一致快照副本上跑一次初始化确认能以 0 结束并通过"，这份证据现在测不到它声称要测的东西。另外，作者自报的"与 makeSnapshot 逐字节一致"是在手工建的库上验证的，没有走过这条演练路径。

修法（任选其一，建议两个都做）：
- `open_copy` 去掉 `immutable=1`，改用 `mode=ro`；或者发现 `<db>-wal` 非空时拒绝并提示先做 `sqlite-backup`。
- 演练容器改为 `docker stop`（触发 `server.js:45` 的 SIGTERM graceful shutdown），迁移后分析前先对 `dryrun.db` 再做一次 `o0_tool.py sqlite-backup`（backup API 会读到 WAL），在新副本上分析。
- 在 selftest 里补一个"WAL 未检查点"用例。

### 🔴-5 JSON 脱敏只处理 `password` 与头的 `set/add`，完整 Caddy 配置中其他位置的字面秘密会原样输出

位置：`scripts/ops/o0/o0_site_check.sh:113`（S-03）、`:127`（S-04）内联的 `r()`；`scripts/ops/o0/o0_tool.py:297-313`（`redact-json`）。

S-03/S-04 会把 jp-24 **整份** Caddy 配置（所有站点、所有路由）写进本机文件。脱敏按字段名做"黑名单"，只处理 `password` 和 `headers.*.set/add`。本机复现（把以下三处放进 JSON 后送入 `o0_tool.py redact-json`），三个哨兵全部原样输出：

- 头匹配器 `match[].header.Authorization: ["Bearer <literal>"]`（用静态 bearer 保护某个入口是常见写法）；
- 头操作 `replace`；
- `static_response.body`。

泄露测试之所以 0 泄露，是因为它只覆盖了已知形状。全队铁律 3 和红线 2（日志 / 证据中出现 token）是零容忍。

修法：JSON 脱敏改成两层。第一层保持现有的结构化规则，并补上 `match[].header`、`replace`、`body`、`vars`、`forward_auth`/`transport` 下的字符串。第二层对**所有**字符串值再过一遍 `o0_tool.redact_line` 的 bearer / bcrypt / LONG_OPAQUE 规则，占位符 `{…}` 除外。同时把三个哨兵形状加进 `site_check_leak_test.sh` 的 `ADAPTED_JSON`。

## 3. 🟡 建议（不单独阻断，但建议随本轮修复一起收掉）

1. **watcher 候选镜像的构建方式与生产镜像血统不一致**（`o0_deploy_watcher.sh:67-80`）：用仓库的 `docker/watcher/Dockerfile` 做完整 `docker build`，会联网执行 `apt-get update`、`pip3 install`、`npm ci`，依赖版本会浮动；另外它把整棵线上源码树（除 `node_modules`、`config.json`）烤进镜像，线上多出来的未知文件也会进去（manifest-verify 只比清单内文件，`o0_tool.py:120-143` 不报 live-only）。仓库已有离线、白名单式的 `scripts/build_immutable_watcher_image.py`（G4 核对的正是它的白名单）。建议用 S-05 的 labels 确认线上镜像血统：若带 `org.trader.*` 不可变标签，就用该构建器，以运行中镜像为固定基础做 overlay；否则至少在报告中列出 live-only 文件并要求人工确认。
2. **Telegram 采集恢复没有断言**（`o0_deploy_watcher.sh:169-170` 以 `|| true` 结尾）：W-4 声称"Telegram 连接与入库日志计数"是验证项，但这一步永远通过。重启后采集没恢复正是 09-04、09-25 漏信号的根因形状。建议断言连接成功的日志行存在，并按 `docs/agent-operations.md` §1 给出重建窗口的漏信号核对命令，结果写进 evidence。
3. **sha 校验没有覆盖全部落盘文件**：watcher 的 compose 安装后（`:147`）没有 `manifest-verify compose-live-vs-candidate`；Caddyfile 安装后（`o0_deploy_caddy.sh:95`）没有与 preflight 记录的候选 sha 比对；env 文件安装后没有复跑 `check`（可以用 `--holder-env` 验证，不输出值）。
4. **G10 禁用词表太窄**（`o0_common.sh:67`）：没有 `systemctl (restart|stop) trader-v3-controlplane-(node-control|event-ingest)`、`docker compose (down|restart)`、`/v1/commands`。本机实测 `systemctl restart trader-v3-controlplane-node-control` 不会被抓到（当前脚本确实没有这类命令）。另外只扫 `o0_*.sh`，没扫 Python 工具和 runbook。
5. **打包时工具取自当前工作树，不是候选提交**（`o0_package.sh:175`、`:207`）：bundle 里的 `tools/` 来自执行打包的那个 worktree，可能带未提交改动，与 `RELEASE.json.candidate` 不对应。本任务合入后，应从 `$OUT/src/scripts/ops/o0` 取，并把工具 sha 写进 `RELEASE.json`；G10 也应扫这一份。
6. **轮换 R-2/R-3/R-5 与快照切换 3.2 / §4 / §5 都是手工命令序列**（`o0-runbook-credentials.md:54-58`，`o0-runbook-snapshot-switch.md:47-77`）：没有 auth-id 记录、没有前后舰队快照（runbook 自己要求"每一步后都记录舰队状态"）、没有自动回滚。建议包成 `o0_rotate.sh`、`o0_snapshot_switch.sh`，复用 `o0_common.sh`。
7. **回滚 5.2 在 watcher 不可达时让用户决定"未互证继续"**（`o0-runbook-snapshot-switch.md:74`）：计划 §4.1 要求回退数据"经校验"。有一条不依赖 watcher 的校验路径：同一窗口对真库做一次 `sqlite-backup`，在副本上跑 baseline 得到 `content_sha256`，再与 5.1 写出的副本的 baseline 摘要比对，加上 5.1 自带的 `--check unchanged`。建议把它写成默认路径；只有这条路径也无法比较时，才上报用户。
8. **5.3 整份还原 env 备份**（`o0-runbook-snapshot-switch.md:75`）：切换之后如果做过轮换（例如 R-3 换了 gateway 值），整份还原会把 token 退回已撤销的旧值，网关随之 503。建议用 `apply` 只改开关与三个别名这几个键。
9. **S-09 在"只读核对"里直接执行主机上的 `sync_operator_risk_db.py --check`**（`o0_site_check.sh:155`）：主机版本未经 sha 核对，"只读"依赖的是一份未知代码。建议先打印它的 sha256，与仓库基线一致才执行 `--check`，否则跳过并记为待核。
10. **"每个进程只持自己需要的那一个"没有现场核对项**：S-10 应断言 node-control / event-ingest 的 EnvironmentFiles 不包含 `operator-query.env`。否则 O-2 写入的 `WATCHER_GATEWAY_TOKEN` / `WATCHER_SNAPSHOT_TOKEN` 会被另两个进程持有（计划 §2.1）。
11. **Caddy 探针 r7 打的是 `127.0.0.1:8080`**（`o0_deploy_caddy.sh:55`）：节点通道是 `172.30.1.1:8080`。如果 Caddy 只绑定该地址，r7 得到 000，verify 失败，按 runbook 就会触发回滚，多一次 restart。地址应取自 S-06 的监听结果。
12. **`GATEWAY_STARTUP_CLEAN` 是"没看到就算过"**（`o0_deploy_operator_query.sh:110-111`）：`watcher gateway disabled` 是每请求才记的警告（`watcher_gateway.py:312`），重启后 3 分钟内没有请求就一定 grep 不到。建议在 apply 内（ERR trap 仍有效时）直接跑一次 `SYSTEM_OBSERVER_TOKEN` 网关探针，期望 200，这样 gateway_disabled 或 watcher_unavailable 能触发自动回滚。`--since '-3 min'` 建议改成重启前记下的 `@epoch`。
13. **restore-db 安装后没有校验**（`o0_deploy_watcher.sh:187-190`）：没有与备份比对 sha，也没有 `integrity_check`，开关状态只写了 NOTE。建议加 sha 比对，并断言 operator-query env 中开关为 0 / 未设。
14. **watcher 回滚不处理 env_file**（`o0_deploy_watcher.sh:111-123`）：旧 compose 不引用它，所以无害，但凭据文件会留在 `/srv/trader-secrets`。建议回滚时还原或删除，或在 runbook 里写明保留理由与清理项（O0-A18）。
15. **脚本里的 catalog 只传了 `operator-query.env`**（`o0_deploy_caddy.sh:67`、`o0_deploy_watcher.sh:61`、`o0_deploy_operator_query.sh:59`）：runbook I-2 要求把其他控制面 env（含 `NAUTILUS_NODE_AUTH_JSON` 的那份）逐个追加。建议增加可重复的 `--catalog-env` 参数，并在 runbook 中给出由 S-10 推导的文件清单。
16. **"gateway 值被接受"只看 400**（`o0-runbook-credentials.md` §2 第一行）：探针缺 `--expect-code invalid_actor_headers`，其他原因的 400 也会被当成"接受"。
17. **preflight 的脱敏 diff 以 `; true` 结尾**（`o0_deploy_caddy.sh:64`）：`redact` 失败会被吞掉，留下一个空证据文件却显示通过。去掉 `; true`，改为只容忍 `diff` 的退出码 1。

## 5. runbook 审查结论

- **门禁顺序**：runbook 层面全部排在停服务之前，每个阶段都是 preflight 只读、apply 失败自动回滚。脚本层面的强制缺失见 🔴-3。
- **前后舰队比对与"变化即停"**：每个阶段都有，退出码 3，不 RESUME，不回滚 Caddy，设计正确；比对本身的缺陷见 🔴-1。轮换与切换的手工步骤缺比对，见 🟡-6。
- **部署顺序 Caddy → watcher → operator-query 与每服务只重启一次**：合理。中间态逐一核过：C 之后旧 watcher 忽略注入头，`/m/v1/watcher/*` 落到旧 operator-query 得 404；W 之后旧 operator-query 仍读副本；O 之后网关只打到已鉴权的 watcher。app 不部署。
- **快照切换与回滚**：与计划 §4.1 一致。回退数据是回退那一刻用 `sync_operator_risk_db.py` 从真库在一个读事务里生成的副本（DELETE 日志模式，immutable 读取对它无害），不是 09-06 文件。校验路径的改进见 🟡-7、🟡-8。第 3 步"所有 worker 预热并记录 revision"在 C-0 现实现下做不到，runbook 如实写成 P-10 前置或由用户接受抽样（D-06），没有把"无法证明"写成通过。
- **凭据轮换与撤销**：顺序与计划 §2.1 一致（watcher 接受新旧 → 持有方切新 → 确认 → 撤旧）；snapshot 身份"R-3 不得早于 R-2、R-5 不得早于 R-3"的警告正确；browser 轮换带 Caddy restart 风险，已单列；紧急撤销单列并标明需要用户单独决定。
