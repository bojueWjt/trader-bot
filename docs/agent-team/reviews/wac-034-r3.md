## 🟡 建议

### 🟡1 两次轮询之间新增超过 500 条时，会产生隐藏的中段缺口（本轮修法带来的回归，低概率）

**位置**：`SignalsScreen.tsx:334-336`，调用处 `:152`、`:155`

**原因**：轮询只取最新 500 条。如果 `next` 和 `old` 没有任何交集（`next` 里最旧的一行仍然比 `old` 里最新的一行新），两者之间就有未知数量的消息没有拿到。无条件合并会把两段拼在一起，看起来是连续的，但 `cursorFor` 取的是最旧一行，这段缺口永远不会被补回来。上轮在 ≤500 行时直接替换，所以没有这个问题（V3 在 16333e2 上通过）；翻过页的情况在上轮也有同样的问题。

**触发条件**：焦点或 AppState 恢复时，`:216`、`:222` 会立即刷新；如果这时离上一次成功轮询已经积累了超过 500 条新消息，就会触发。前台每 30 秒一次的轮询不可能触发。按 09-05 watcher 库 id 约 1100 的量级粗估，大约要在后台存活数天才会遇到；但如果频道突发刷屏，或者后续增加了频道，会提前遇到。进程被系统回收后重新挂载，会从头加载，不受影响。

**建议修法（1 行判断，放进 wac-057）**：轮询返回满页（`next.length >= 500`），并且与 `old` 没有交集（可以用"next 中最旧一行的排序键严格大于 old 中最新一行"来判断，也可以用 id 集合判断）时，直接 `return next`。这样丢弃的是用户已翻出的旧页，用户能看到，也能重新滚动加载，不会留下隐藏缺口。有交集时继续按 `mergeRows` 合并。测试用 V3 的形状：首页 500 行，轮询返回 1600..1101，断言结果恰为 1600..1101，并且下一页游标为 `ts(1101)/1101`。

   - 或者先发 HEAD
