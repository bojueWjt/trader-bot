## 2. 重点核实

### 2.1 KeyboardAwareScrollView

**(a) 覆盖量计算：🔴-1，见 §3。** 下面是证据链，全部取自 RN 0.82.1 源码（`apps/attention-android/node_modules/react-native`）。

1. `keyboardDidShow.screenY`：`ReactAndroid/.../ReactRootView.java:908-940`（API 30+ 分支）的取值是 `getWindowVisibleDisplayFrame().bottom`。这是**屏幕绝对坐标**，即 IME 顶边。
2. `measureInWindow`：
   - `ReactCommon/react/renderer/dom/DOM.cpp:534-537` 调用时带 `includeViewportOffset = true`。
   - 这个偏移由 `RootShadowNode.cpp:37-38` 加到结果上。
   - 偏移的取值见 `runtime/ReactSurfaceView.kt:101-112`：`locationOnScreen - visibleWindowFrame.top`。
   - 所以 `measureInWindow().y = 屏幕 y - visibleDisplayFrame.top`。
3. 目标平板的状态栏高度：wac-063 的 `logcat-full.txt` 里有 `statusBars:[0,82…`，uiautomator 的 `cta_content` 顶边也在 y=82。所以全屏时 visibleDisplayFrame.top = 82px = **32.8dp**。

用 wac-063 的 l19 场景代入（设置页的控制面地址输入框；以下都是屏幕 dp）：
- 输入框实际位于 675–723，IME 顶边 609。
- `measureInWindow` 返回 642.2。代码算出的 overflow = 642.2 + 48 − (609 − 24) = 105.2，于是滚动 105.2。
- 滚动后输入框底边实际在 723 − 105.2 = **617.8，比键盘顶边低 8.8dp**。
- 350ms 的二次校正按同一套坐标重新测量，得到 overflow = 0，不会再滚。
- 预留空间按 covered = 876.2 − 609 = 267.2 计算（实际被遮 300），所以页尾按钮在滚到底时同样会被键盘盖住约 9dp。
- 上下分屏的下半窗：visibleDisplayFrame.top 约等于窗口在屏幕上的顶边（数百 dp），算出的 overflow 与 covered 都是大负数，**完全不避让**。

**(b) 聚焦滚入、350ms 二次校正、字段切换、键盘关闭恢复：** 在同一坐标系的前提下，逻辑都是对的：
- `onInputFocus` 在键盘已打开时立即 reveal。
- 预留空间提交后，由 `revealTick` 的 effect 触发一次 reveal。
- 二次校正已经可见时不再滚动（测试覆盖了）。
- `keyboardDidHide` 时清零预留、清掉定时器；卸载时清理 listener 和定时器。

但有一个在代码层面确定存在的缺口（🟡-1）：API 30+ 只在 IME 可见性**翻转**时发 `keyboardDidShow`（`ReactRootView.java:915-916`），键盘高度变化时不发事件。wac-063 实测，小米键盘在普通字段与密码字段之间的顶边相差 111dp（1445px 对 1167px）。如果切到密码字段时 IME 没有先隐藏再显示，`keyboard.current.screenY` 就会停在旧值，token 框会被完全遮住。这正是 wac-063 报告里最坏的那个场景，现有测试直接发 `keyboardDidShow(467)`，没有模拟这种切换。

**(c) 不引入原生依赖：** 成立。`package.json` 没有改动，只用了 RN 自带的 `Keyboard` 和 `measureInWindow`。

**(d) Setup 页 Android 不给 `KeyboardAvoidingView` 设 behavior 的偏离：** 理由成立。KAV 用 `onLayout` 帧（相对父视图）与 `screenY` 比较，本身就有同类坐标偏差。如果同时开 KAV 和预留空间，同一块被遮区域会被补偿两次。只保留一套机制是对的，前提是这套机制的坐标算对（见 🔴-1）。

**(e) 仍会缩窗的旧设备（非 edge-to-edge 且 adjustResize 生效）：** 无副作用。
- 根视图在状态栏下方，visibleTop 等于状态栏高度，viewportOffset 为 0。窗口缩小后滚动容器的底边就是 IME 顶边，算出的 covered 为负，预留空间为 0。
- 字段的 overflow 只有在字段离键盘小于 (24 − 状态栏) 时才会为正，实际不会发生。
- 旧的 legacy 分支（API < 30）在键盘高度变化时也会发事件。

## 3. 问题清单

### 🔴

**🔴-1 键盘覆盖量把屏幕绝对坐标（screenY）和"可见区相对坐标"（measureInWindow）混用，偏差等于 visibleDisplayFrame.top**
- 位置：`src/ui/KeyboardAwareScrollView.tsx:99`（`overflow = y + height - (metrics.screenY - KEYBOARD_MARGIN)`）、`:131`（`apply(y + viewHeight - screenY)`）；`SetupScreen.tsx` 的注释（"measures in window coordinates"）前提不成立。
- 证据：§2.1(a) 的 RN 源码三处，以及 wac-063 logcat 里的 statusBars 82px。
- 后果：
  - 目标平板横屏全屏时，聚焦的输入框和页尾按钮仍被键盘盖住约 9dp（32.8 − 24）。
  - 手机上状态栏越高，盖住越多。
  - 上下分屏的下半窗完全不避让。
  - §7A.2 要求"横屏打开键盘时输入框不被遮挡"，这一条不满足。
- 测试为什么没发现：`__tests__/keyboardAvoidance.test.tsx:78` 的 `measureStubs` 让 `measureInWindow` 直接返回屏幕坐标（`:138`、`:291`，注释写的是"field at 1688px (675dp)"）。也就是说，测试把"两套坐标相同"当成了前提，而不是去验证它。
- 修复方向（执行者任选一种，不引入新的原生依赖）：
  1. 把 IME 顶边换算到与 `measureInWindow` 同一坐标系。在 App 根部放一个铺满窗口的参照 View，用 `measureInWindow` 取它的 y0 和高度 H；IME 顶边 = y0 + H − (endCoordinates.height + 安全区 bottom)。`endCoordinates.height` 等于 IME inset 减去系统栏 bottom，是相对窗口的量，和屏幕位置无关。偏移同时作用在字段和参照上，互相抵消。
  2. 或者改用已安装的 `react-native-reanimated` 4.2.1 的 `useAnimatedKeyboard()`，它实时给出 IME 高度，高度变化也会更新，能顺带解决 🟡-1；字段位置仍按方案 1 用相对根视图的差值计算。
- 必须补的用例：
  - mock 的 `measureInWindow` 带非零 viewport 偏移（例如 −32.8，以及下半窗约 −700），断言滚动后字段的**真实**底边 ≤ IME 顶边 − margin。
  - 预留空间在同样偏移下也要足够。
- 真机：修复后由 Tester 在全屏横屏、左右半屏、上下分屏的下半窗各测一次（Setup 的 token 字段、设置页控制面地址、页尾按钮）。
