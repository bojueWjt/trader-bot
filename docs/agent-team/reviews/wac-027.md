## 🟡 建议（建议在 A-1/A-2 接入之前补上）

1. **`invalid_token` 的 `status` 仍是 403，而交易页判断"连接失效"用的是 `status === 401`。** `watcherApi.ts:94-98` 把 403 `invalid_token` 的 `code` 映射为 `unauthorized`，但保留了 `status=403`；写禁用之后 `write()` 抛出的却是 `status=401`（`:199`）。交易侧现有的判定都按状态码：`PositionDetailScreen.tsx:545`、`:726`，以及 `tradingApi.ts:510` 的 `shouldRetryOperatorWrite`。A-1/A-2 如果照抄这种写法，`invalid_token` 就进不了连接失效入口。契约自身也有歧义：§9.5 表格写的是 403 `invalid_token` 走连接失效入口，而表下 A-3 条款写的是"401 仍是唯一触发'交易服务连接失效'的状态"。建议：在 `watcherApi.ts` 导出一个判定函数 `isConnectionInvalid(error)`（按 `code === 'unauthorized'` 判断），并要求后续屏幕只用它；同时请 Planner 在 WGW-1.0.1 勘误中统一这两句话。
2. **非 JSON 的 503 没有归到 `watcher_unavailable`。** `readPayload` 先检查 content-type（`:321-323`），之后才进行状态码分流，所以非 JSON 的 503（例如中间层返回的 HTML）会显示"服务返回了非 JSON 数据"。A-3 的规定是"503 且 code 不在上表 → 一律按 `watcher_unavailable` 处理"，没有 code 的 503 也属于这种情况。写请求仍然标记为结果未知（`:323`），所以一致性没有受损，只是提示文案分错了类。建议：`status === 503` 且 body 不是 JSON 或无法解析时，走 `mapError(503, {})`。
3. **"写路径结果未知"这条规则只锁住了一种形状。** `watcherApi.test.ts:76-80` 只检查错误对象上的 `clientRef`。静默换号重试（M2b）、`db_busy` 或 `watcher_unavailable` 被标记为结果已知（M11、M12）、条件写缺 `expected_revision`（M10），这几种都不会让测试失败。建议补充：超时用例断言 `fetchImpl` 恰好被调用一次，并且每次请求 body 里的 `client_ref` 都等于原值；对写请求逐一验证 `db_busy`、`watcher_unavailable`、`gateway_busy`、未识别的 503、`invalid_json`、`body_timeout`，都应当 `outcomeUnknown === true` 且 `clientRef` 为原值；对 409 `revision_conflict` 和 `idempotency_conflict` 断言 `outcomeUnknown === false`；对三个资源的条件写各加一条缺 `expected_revision` 的用例，断言请求不会发出。
4. **写禁用只断言了标志位，没有断言写请求真的被拦住。** `:53-59` 只检查 `isWriteDisabled()`。`write()` 忽略禁用（M9）、`invalid_token` 不触发禁用（M8，`:293-295`）、媒体 401 不触发禁用（M14，`:245-247`），这三种都会存活。建议：401 之后调用 `write()`，断言它以 `unauthorized` 拒绝，并且 `fetchImpl` 的调用次数没有增加；`invalid_token` 和媒体 401 各补一条同样的用例。
5. **设置页测试只覆盖正常路径，也没有断言"无输入项"。** `settingsWatcherStatus.test.tsx:55` 只检查字符串"配置 watcher"不存在。在区块里加 `TextInput`（M16）或把出错时的状态行改成空串（M17），测试都不会失败。建议：断言 `section.findAllByType(TextInput)` 的长度为 0；再加三条出错路径的渲染用例，分别是 `fromStorage` 返回 `false`（显示"交易服务未配置"）、401（显示"交易服务连接失效"）和 503（显示"采集服务不可达"）。
6. **没有测试确认 token 不会进入错误对象。** 代码目前是干净的，但 M15（把 token 拼进超时文案）会存活。建议加一条扫描用例：对各种错误路径，断言 `error.message` 和 `JSON.stringify(error)` 都不包含夹具 token `fixture-token`。
7. **`media()` 在客户端没有超时。** `:233-237` 没有 `AbortController` 和 signal。RN 的 `fetch` 没有默认超时，服务端虽然有 60 秒总时限，但网络本身卡住时这个 Promise 永远不会结束。媒体组件在 A-1 才会接入，建议在那之前让 `media()` 接受调用方传入的 `signal`，或者设置一个与 §9.7 媒体预算一致的总时限。

## 💭 Nit

1. 存储键测试只对 `TRADING_KEYS` 常量做了快照。如果以后另起一个 `watcherStorage` 模块，这个测试拦不住。可以考虑 spy `attentionNative` 的写接口，断言调用次数为 0，这样更直接。
2. `getStatus()`（`:165-172`）没有校验 `last_telegram_activity_at` 和 `last_message_ingested_at` 的类型；如果它们是数字，会原样渲染出来。
3. 网关的三个 503 码被折叠成 `code='watcher_unavailable'`（`:118-121`），原始码只能从 `details` 里间接看到。建议保留 `rawCode` 字段，方便排障。
4. 设置页直接显示 ISO 时间串（`SettingsScreen.tsx:209-211`），这属于展示层的事，可以留给 A-2 统一格式化。计划 §2.1 说"采集服务不可达"只在信号页和交易配置页提示；设置页这里是状态值而不是提示，我认为可以接受，但 A-2 做文案时请统一口径。
5. `load`（`SettingsScreen.tsx:71-92`）把采集状态请求串在 `captureCapabilities()` 后面。如果后者抛错，采集状态行会一直停在"读取中"。这是沿用了原有写法，不是本任务引入的问题。

## 做得好的地方

- 与服务端的对齐是逐码核对过的：`UNAVAILABLE_CODES` 恰好是网关能产生的全部 503 码，再加上 A-3 的兜底，没有多也没有少。
- `send()` 在读 body 之前就处理 401（`:288`），所以连接失效的判定不依赖错误体能否解析。
- 读 body 超时有独立的定时器，并且用假时钟做了真实的超时测试，而不是只 mock 一个 AbortError。
- 媒体测试精确断言了请求头集合，因此"走 `send()`"和"token 进 URL"两类变异都被抓住了。
