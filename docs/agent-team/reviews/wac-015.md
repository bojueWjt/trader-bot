## 4. 🔴 Blocker

**🔴-1 reentrant 写入口的 409 `idempotency_conflict` 缺少契约规定的 `details: {client_ref, operation}`**
- 位置：`lib/reentrant-write.js:32`（查审计时发现冲突）与 `:63`（在途合并时发现冲突），两处都是 `failure(409, 'idempotency_conflict', …)`，没有 details。
- 契约：§9.12"**409 `idempotency_conflict`**：`details: {"client_ref", "operation"}`，不回显原请求或原响应"。同一文件族的 transactional 路径已经这样实现（`config-store.js:455-457`）。
- 实测：真实进程中 gateway 与 browser 用同一 `client_ref` 提交不同 groups，响应分别是 `{"code":"idempotency_conflict","message":"client_ref used with different request"}` 与 `{…,"error":…}`，都没有 details。
- 为什么算 blocker：红线 5 要求实现与 `backend-api.md` 一致；网关会原样透传 409 的 details（§9.6），app 与站点展示依赖这个结构。同一个错误码在两条写路径上形状不同，属于契约漂移。`reentrant-write.test.js` 只断言状态码 409，所以没有发现这个问题。
- 修法：`failure()` 增加第四个参数 details，两处传 `{ client_ref: body.client_ref, operation }`（`sendError` 已经会透传 details）。补一条测试：reentrant 三行的 409 details 与上面的形状逐键相等，并断言不含原请求或原响应的内容。

## 5. 🟡 建议（修复轮建议与 🔴-1 一并处理 🟡-1、🟡-2）

**🟡-1 站点新增了没有确认的"断开监听"按钮，误点会静默停止信号采集**（`public/index.html:706-707`、`:1179-1191`）
- 基线站点没有 disconnect 调用点（只有登录后自动 reconnect，`:1108`），任务书要求的是"这三处带 client_ref"。执行者把"三处"理解为需要一个 disconnect 入口，于是新增了两个按钮，放在"保存选择"旁边。契约 §9.13 第 6 项也把 disconnect 列为站点写请求，所以这种理解有依据，不按越界判 🔴。
- 风险在于：`/api/disconnect` 会设置 `watcherMonitoring=false`（`server.js:870-878`），此后 120 秒断连告警与 20 分钟无更新探针都不再运行。一次误点就会让交易信号采集停止，而且没有任何告警，直到有人点"重新连接"。对这个系统来说，这正是"漏单"类事故的形状。
- 建议：由 Planner 在二者中选一。一是移除这两个按钮（app 的 P1 断开/重连另有状态机设计）；二是保留按钮，但 disconnect 加 `confirm()` 二次确认，并在页面上常驻显示"监听已停止"。无论选哪种，都补一条测试锁定该行为。

**🟡-2 七个存活变异对应的测试缺口**（逐条给出可执行的补法）
1. M03c：把最小长度从 32 改成 16，没有测试失败。在 T0-1 的非法值表中加入一个 31 字节的可打印 ASCII 值（当前值与 PREVIOUS 各一次）。
2. M08：未知键只按 deny 过滤，仍然存活。原因是没有字段定义的键会在类型检查时被拦下，所以测试只断言了 code。建议用一个"有字段定义、但不在本行 allow 中"的键（例如对 gw risk POST 提交 `channel_id`，或对 groups 提交 `symbol`），并断言 `details.unknown_fields`。
3. M12b：幂等键去掉 actor 后仍然存活。补法：browser 与 gateway 用同一 `client_ref`、相同请求体各写一次，应得到两条审计、两次 `replay:false`。
4. M20b：同一身份内部短路（`digests.some`）后仍然存活。wac-009 🟡-1 要求"对每个已配置摘要各调用一次、没有短路"。补法：配置三组 PREVIOUS，用当前值和旧值各请求一次，断言 `timingSafeEqual` 共被调用 4 次，调用次数与命中哪一个无关。

## 6. 💭 Nit

1. `bytes_sent` 统计的是从文件读出的字节数（`media.js:126`），不是写到 socket 的字节数；60 s 超时截流时 reason 记为 `stream_error`，没有记 `timeout`。
2. `routeMatches`（`auth.js:107`）与 `validValue`（`request-validation.js:85`）每个请求都 `new RegExp`，可以在加载时预编译（wac-009 💭-2 仍未处理）。
3. `config-store.js:5` 仍然保留手写的 `CLIENT_REF` 正则（不带 `u`），可以改用 `PAYLOAD.body_fields.client_ref.pattern`。
4. `safe-log.js:1` 的 `SENSITIVE_KEY_PATTERN` 与生成物的秘密谓词不同（缺少 `phone`、`api_id`）。它用于日志与响应脱敏，不是 W-0b 的第二份正则，但建议以后统一。
5. reconnect 改为不等待以后，reconnect 后紧接 disconnect 可能留下一个已连接但不处理消息的 client（`server.js:439-442` 连接后发现 `watcherMonitoring=false` 直接 return）。状态以回读为准，影响有限。
6. 站点的 `pendingConfigWrites` 在网络失败后保留 `client_ref`。如果中间隔了一个不同的操作（disconnect → reconnect → 再 disconnect），第三次会复用旧 ref，可能拿到重放而没有真正执行。toast 已提示"以刷新结果为准"。
7. 测试名"including unequal token lengths"言过其实：比较的双方都是 32 字节摘要，长度永远相等。
8. 运行时是 `node:22-slim`，`readable.iterator()` 在 22 中仍标为实验性，本机是 24。建议在 O-0 镜像冒烟里跑一次 W7 的 413 与 GET 带 body。
9. `loadConfig()` 吞掉所有读错误并返回 `{}`（`server.js:234-240`，预存）。groups 写入如果恰好遇到读失败，会用 `{watchGroups}` 覆盖整个 config.json，抹掉 Telegram session。groups 已经可以经 app 调用（P2），建议以后区分 ENOENT 与解析错误，并改为原子写入。
