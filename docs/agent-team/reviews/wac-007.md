## Planner 已接受的三条解读：复核结论是都属于 fail-closed，没有不可接受的副作用

1. **schema_mismatch 算 invalid**。这是 fail-closed：schema 不认识时立即拒绝开仓，而不是再用旧快照 60 秒。副作用是一条部署顺序约束：watcher 升级快照 schema 之前，控制面必须已经认识新版本，否则开仓立即 503。这正是我们想要的行为，建议 O-0 的发布顺序写明"先控制面后 watcher"。
2. **快照端点的 403 等同 401（unauthorized）**。`WATCHER_SNAPSHOT_URL` 是 `127.0.0.1:9090` 直连，不经过 Caddy，所以 403 只可能来自 watcher 的 `identity_forbidden`（token 落到了别的身份），说明信任关系确实变了。锁存属于 fail-closed，没有副作用。
3. **锁存态只有下一次成功验证才能清除**。我没有找到任何一条路径能让"非 fresh"经由锁存变成 fresh：超时和 5xx 不能解除；worker 重启回到 `cold`，仍然要一次成功验证才行。可用性代价有上限：watcher 修好后，最多一个退避周期（≤ 15s）加 2s 请求就能恢复。轮换时如果误操作（watcher 先清掉 `_PREVIOUS`），受影响的 worker 会拒绝开仓直到重启并验证成功，这也是正确的方向。见 💭-2，重启会丢失"同 revision 异摘要"的检测记忆，但这是逐 worker 缓存本身的设计属性，不是这三条解读引入的。

另外：wac-013（C-0）的 `watcher_config_snapshot.py:330-404` 已经有 `unauthorized`/`invalid`/`schema_mismatch` 的阻断原因，看起来与这三条一致。wac-014 审查时请按 WGW-1.0.1 §9.11 逐条核对（特别是 403 和超时不解锁）。

## 🟡 建议

**🟡-1 秘密键正则在 Python 与 JS 下并不完全同义：U+0130/U+0131 有分歧，§9.15 的说法与事实不符（C-1 和 wac-015 开工前处理）。**
- 位置：`backend-api.md:614`（"Python `re.IGNORECASE` 与 JS `iu` 都做 Unicode 简单大小写折叠"）、S-20(g) `:550`、YAML `:110-112`。
- 实测，同一个 pattern，Python 用 `re.search(..., re.I)`，node 用 `new RegExp(p,'iu')`：`'apı_key'`、`'apİ_key'`、`'APİ_KEY'`、`'sessıon'`、`'SESSİON'` 在 Python 下命中，在 JS 下不命中。原因是 Python 的 IGNORECASE 在 `i` 上额外匹配 İ/ı（Python 文档明确列出这 4 个例外字符），而 JS `u` 模式只用 CaseFolding 的 C+S，İ/ı 只有 T/F 映射。
- 安全影响目前为零。Python 一侧（网关，第一层）更严；watcher 第二层虽然漏判，但 W7 的未知键检查会用 `invalid_body` 拒绝，因为 allow 全是 ASCII；响应删除只在网关做。
- 为什么还要处理：R5 的要求是"同义"，而 S-20(g) 的固定探针恰好没有覆盖这类字符。C-1 实现者如果按"至少含"的精神自己加上 ı，S-20 就会失败，最容易发生的反应是删掉这个探针，也就是"为绕开报错改造输入"。
- 建议写成规范（二选一，推荐第一种）：
  - (a) 秘密键判定只对 ASCII 键名跑正则，**含任何非 ASCII 字符的键一律按命中处理**：请求侧 `secret_field_rejected`，响应侧删除。两层结论完全相同，也是 fail-closed。
  - (b) 把 İ/ı 加进 S-20(g) 的探针，并写明预期是两边一致，迫使实现选 (a)。
- 同时改掉 `:614` 那句不准确的话。

## 💭 Nit / 备忘

1. 生成物的包名 `generated` 太通用，而控制面在 `host/` 平铺、测试会把 `api/`、`db/`、`tests/control-plane/` 都放进 `sys.path`。现在没有冲突（我查过，没有其他 `generated` 包），将来容易撞名。可以考虑 `watcher_gateway_generated`，改动只涉及 §9.14.3 一处。
2. "同 revision 异摘要"的 invalid 检测依赖 worker 内存里的缓存。operator-query 重启后，冷启动的 worker 会把绕过写入者写出的 (rev N, d2) 直接当作 fresh，检测记忆就丢了，而"重启"恰好是运维最常用的处置。数据本身仍经过 §9.10 服务端校验，所以不算安全缺口。建议 C-0 在首次加载和锁存时记一条带 `(revision, content_sha256)` 的日志，O-0 确认 `db_manager.py` 的写命令已经停用（§9.12 `:493`）。
3. §9.11 `:418` 把 invalid 定义为"拿到 200 但未通过成功验证"，`:421` 又把"200 + 非 JSON / 超过 4 MiB"列为不锁存。两处的边界靠括号里的枚举区分，读起来有张力。建议在 `:421` 加一句"传输层不完整的 200 视同 unavailable"。
4. §9.3 把 G5 `gateway_disabled` 排在 G4 请求校验之后。网关未配置时，已认证请求仍会被读取和校验 body，然后才返回 503。这符合 R3，无害，只是记一下。
5. `watcherAuth` 用 `Object.freeze(v)` 已经够了（对象是扁平的）；`watcherRoute` 是嵌套结构，契约要求深冻结。wac-015 的测试应该验证嵌套层的写入也会抛错（严格模式）或者不生效。
