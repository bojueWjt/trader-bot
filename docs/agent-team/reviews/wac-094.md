## 3.3 黑盒差分：前缀空间判定对真实 Caddy（我自己写的 `scratchpad/r095/spacediff/sd.py`，没有复用执行者的程序）

做法：对每个模式，用工具的 `_path_pattern_may_hit_space` 或 `_regexp_may_hit_space` 给出判定；再给真实 Caddy v2.10.2 每个模式单独配一个 host 和一条路由，发 60 到 120 条前缀空间内的请求。这些请求覆盖：清单各行填入 33 个取值（大小写、后缀、`(`、`]`、`|`、长值等），按模式里的字面片段定向拼出的路径，任意更深的路径，以及 `\n` 形式。正则先用 Go `regexp.Compile` 过滤掉非法的（`rechk/`），合法的才交给 Caddy。**工具判"不命中"、Caddy 却命中了某条空间路径，就记为漏判。**

| 种子 | 模式数（path + re） | 请求数 | path 漏判 | re 漏判（函数层面） |
|---|---|---|---|---|
| 1 | 150 + 150 | 27,862 | 0 | 4 |
| 2 | 1,500 + 1,500 | 289,114 | **0** | 61 |
| 3 | 1,500 + 1,500 | 289,479 | **0** | 58 |
| 7 | 1,500 + 1,500 | 288,638 | **0** | 30 |
| 11 | 1,500 + 1,500 | 290,922 | **0** | 63 |

- **`path`：6,150 个模式、约 116 万次请求，0 漏判**，其中约 1,860 个模式被判为"不命中"。
- **`path_regexp`**：函数层面共 216 个漏判模式，全部属于同一个解析缺口：字符类的第一个成员是 `]`（`[]…]`、`[^]…]`），或者出现 `\Q…\E`、`[[:alpha:]]`。这让扫描器算错了括号深度，漏看了一个顶层的 `|`。其中 `\Q` 和 POSIX 类的写法，verify 在样本步骤就兜住了，因为 Python 无法编译它们，会判为 UNCOMPARABLE。**真正整条 verify 都放过的有 54 个，全是以 `]` 开头的字符类。**见 🟡-3。
- 执行者自报"197,361 请求 0 漏判"。这个数字本身没有问题，只是它的生成器没有产生这种字符类写法。

## 7. 🟡 建议

1. **面板的 `/v1/*` 和其他通往 operator-query 的公网入口，会把 `/v1/watcher/*` 连同注入的 observer token 一起转发**。这个缺口早就存在，不是本分支引入的。它**挡 O0-A08**，也挡在它之前、会被修法改动的 O0-A05P 和 O0-A05。
   - **事实**：仿生产夹具 `scripts/ops/o0/tests/fixtures/caddy/Caddyfile.prodlike.in:20-24` 写的是 `handle /v1/* { reverse_proxy 127.0.0.1:8183 { header_up Authorization "Bearer {env.SYSTEM_OBSERVER_TOKEN}" } }`。生产的情况与之一致，有两份文档记录：`docs/reports/2026-09-15-trading-reliability-local-implementation.md:47`（"网页 `/v1/*` 无条件使用 `SYSTEM_OBSERVER_TOKEN` 转发"）、`docs/operations/trading-reliability-cutover.md:7`。
   - **后果**：operator-query 收到的 `/v1/watcher/...` 来自哪条路由，它是分辨不出来的。移动端的 `/m/v1/watcher/*` 剥掉 `/m` 之后，和面板 `/v1/*` 原样转发过来的，是同一个路径。O0-A08 让网关生效之后，公网上**不带任何凭据**的请求会经过 G2 被识别为 `system_observer`，再通过 G3。按 `contracts/watcher-gateway-routes.yaml`，P0–P2 有 11 条读路由对 `system_observer` 开放：`status`、`trading/messages`、`trading/briefings`、`media/{filename}`（GET 和 HEAD）、`trading/orders`、`trading/orders/active`、`dialogs`、`trading/accounts`、`trading/channels`、`trading/risks`。也就是说，Telegram 会话列表、频道消息、媒体文件都会变成公网匿名可读。写路由只对 `risk_admin` 开放，observer 只会得到 403。
   - **为什么工具没有报**：§9.14.3 的合并规则（`backend-api.md:690`）和 verify 的转发检查（`o0_caddy_watcher_routes.py:1204-1252`）只管 **Caddy 这一侧**的 `/m/v1/watcher` 前缀。R11"`/media` 与其他公网入口没有绕过"（`o0-requirements.md:60`）只落实成了"转发到 9090/9100 的路由必须带认证"。探针也只发 `/m/...` 路径。所以 verify 和探针都把夹具判为"好配置"（g19）。同一个形状还有 g18：`handle_path /x/*` 剥掉前缀后转发到 8183。O-3 的验证（`o0-runbook-deploy.md:197`）也只测了公网的 `/m/v1/watcher/status`。
   - **修法**（交 Architect 定，涉及契约修订，并需要用户认可）：
     - 规则改成：**除片段以外，任何路由都不得把一个会触发网关中间件的上游路径交给 operator-query 端口。**中间件的触发条件是：不区分大小写地以 `/v1/watcher` 开头，且其后是 `/`、`%`，或者什么都没有，见 `backend-api.md:276`。
     - 最小的 Caddy 侧改法：在片段里（或站点顶层、所有 handle 之前）再加一条兜底，对 `^(?i:/v1/watcher)(?:[/\n]|$)` 直接回 `respond 404`；或者把面板的匹配器收窄，排除 `/v1/watcher*`。
     - verify 增加一步：对 `/v1/watcher/status`、`/V1/WATCHER/status`、`//v1/watcher/status`、`/v1/watcher/media/x.png` 做模拟，断言它们不到达 8183。
     - 探针的活体检查加同样几条，期望 404，并且不到任何桩。
     - O-3 加一条公网检查：`/v1/watcher/status` 不带 token 时应得 404，不能是 200。
     - 如果 Architect 选择只改 operator-query 一侧（比如网关拒绝某种来源），候选 Caddyfile 不变，A05P 可以不受影响。但我看不出 operator-query 有什么可靠的依据来区分这两类来源。
   - **顺带提醒（本任务范围外，仅供用户知悉）**：同一条面板路由意味着，现在的 `/v1/accounts` 等只读交易数据在公网上已经是匿名可读的，除非生产在这个站点前面还有别的认证层。
2. **路径改写把前缀外的请求带进了前缀空间，而注入发生在改写之前**。verify 和探针都放过，真实 Caddy 会注入（g16、g17）。
   - 位置：`_shadow_check`（`o0_caddy_watcher_routes.py:1082-1116`）只判断"匹配器能不能命中前缀空间"，不判断"处理器改写之后的路径会不会落进前缀空间"。
   - 为什么会注入：Caddy 会把指令不同、但命名匹配器相同的相邻路由（`uri` 和 `request_header`）合并成一条路由，按原来的路径匹配一次，然后依次执行这两个处理器（见 g16、g17 的 adapt 结果）。
   - 修法：在片段之前的各层里，只要一条路由的处理器会改路径（`rewrite` 带 `uri`、`strip_path_prefix`、`strip_path_suffix`、`uri_substring` 或 `path_regexp`），**无论匹配器是什么，都算命中**。它不在白名单里，所以 verify 会失败。唯一的例外是：`uri` 是常量，不含占位符，而且这个常量不在前缀空间内（例如 `rewrite /healthz /api/status`）。把 g16、g17 加进 selftest 和 `caddy_real_test`；U-6 的审阅要点加一条"站点顶层的 `uri strip_prefix`、`uri replace`、`rewrite`，不论匹配器是什么，都写明改写之后会不会落进 `/m/v1/watcher`"。
   - 生产里出现这种写法的可能性很低，但它和 v15–v19 属于同一类。建议与 🟡-1 同批修。
3. **`_regexp_may_hit_space` 的扫描器不认得"以 `]` 开头的字符类"**。
   - 位置：`o0_caddy_watcher_routes.py:674`。`in_class = c != "]"` 把 `[]`、`[^]` 之后紧跟的第一个 `]` 当成了类的结束。按 RE2 的规则，这个 `]` 是字面字符。于是类里的 `(` 被当成开括号，把深度加一，后面那个顶层的 `|`（`:681`）就被当成了组内的 `|`。
   - 实证：`^/static[](]|account-a$`、`^/static[](]|\.png$`、`^/static[^](]|account-a$` 在 verify 里都判为通过，真实 Caddy 会注入（g01c、g04c、g04d）。探针只是因为 `PROBE_PARAM_VALUES` 里恰好有 `account-a` 和 `x.png` 才抓住。换成 `a\.bmp$`，两处都会放过。差分里整条 verify 放过的有 54 个。
   - 讽刺的是，同一个文件里的 `_re2_compile`（`:350-360`）已经正确处理了这种写法。
   - 修法：照搬 `_re2_compile` 的规则，把 `[` 或 `[^` 之后紧跟的 `]` 当作字面字符；遇到 `\Q` 或 `[:`，直接算命中。更省事、也更保守的做法是：模式里只要有 `|`，同时又有 `[` 或 `\Q`，就算命中。
   - 这种写法几乎不会出现在生产里，单独不挡授权。建议与 🟡-1、🟡-2 同批修；U-6 的审阅要点加一条"`path_regexp` 里含 `[]` 或 `[^]` 的"。

## 8. 💭 Nit

1. `caddy version` 子进程虽然记进了 pid，但扫描时认领不了。它的命令行里既没有临时目录路径，也没有 `.o0probe`（`:2107`）。真实的 `caddy version` 瞬间就退出，所以实际无害（K02 是用包装脚本人为让它挂住的）。可以只对"pgid 等于 pid、且命令行以记录中的 caddy 二进制开头"的记录 pid 放宽认领条件；也可以不改，只在文档里写明。
2. F8：`.o0probe` 是符号链接时，扫描输出 `o0probe=absent`（`:2133`），但文件其实还在，只是随后被拒绝运行。建议改成 `kept(symlink)`，免得证据误导人。
3. 扫描信任属主记录，没有核对记录文件和目录的属主 uid 与权限（`:2087`）。macOS 的 `$TMPDIR` 是每个用户私有的 0700 目录，所以没有跨用户的风险。但如果在共享 `/tmp` 的 Linux 上运行，别的用户可以伪造一份记录，诱导运行者杀掉自己命令行里含某个字符串的进程。建议加上 `st_uid == os.getuid()`，以及目录权限为 0700 的检查。
4. p03：`rewrite /healthz /api/status` 这种常量改写会让 verify 判为 UNCOMPARABLE。原因是浏览器样本的模拟器 `_apply_rewrite`（`:786`）只支持 strip 类改写。这个问题早就存在。生产如果有这种写法，verify 会失败，要人工处理。可以与 🟡-2 一起，让模拟器支持常量 `uri`。
5. 扫描在 `try` 之外执行（`:2356`）。这期间按 Ctrl-C，`_ProbeInterrupted` 没有被捕获，会打出 Python 堆栈。此时探针自己还没有创建任何东西，所以是安全的；可以把扫描包进一个小的 `try`，让输出统一成 `CADDY_PROBE_INTERRUPTED`。
