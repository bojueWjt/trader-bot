### 专项：缺 Content-Length 的媒体会不会一律显示占位

**会，但生产链路上不会出现缺头的情况，所以这是可接受的失败即关闭。**

1. **RN 的 fetch 不支持 body 流。** RN 0.82.1 的 `Libraries/Network/fetch.js` 就是 whatwg-fetch。它的 Response 没有 `.body`（`fetch.umd.js` 里没有 `body` getter 或 `getReader`），`readBoundedStream` 在 `watcherApi.ts:141-143` 必然抛出 `media_too_large`。流式计数的代码和测试只在 Jest 的自造 Response 上有意义。
2. **网关保证 GET 200 一定带 Content-Length。**
   - watcher 端：`bridge/services/telegram-watcher/lib/media.js:108` 对 200 和 206 都设置 `Content-Length`。
   - 网关端：`services/control-plane/api/watcher_gateway.py:445-449` 在 GET 时要求上游 content-length 是数字且等于期望长度，否则返回 503 `watcher_unavailable/malformed_response`。
   - `contracts/watcher-gateway-routes.yaml:224` 的 media 响应头白名单包含 Content-Length。`_response_headers`（`:415-418`）会原样转发，StreamingResponse 带着显式长度，不会改成 chunked。
   - 仓库内 Caddyfile 对这条路径没有 `encode`。生产 Caddy 是否会压缩或去掉这个头，我没有核对（铁律 1），列为 Tester 的检查项。
3. **还有一个更要紧的事实（写进 🟡2）。** whatwg-fetch 在 `xhr.onload`（`fetch.umd.js:546-562`）之后才 resolve Response，并且用 `responseType='blob'`（`:599-601`）。所以在 RN 上，**JS 能看到 Content-Length 的时候，整个 body 已经下载到原生 BlobModule 了。** "不读 body"在 JS 层成立，它真正避免的是 base64 膨胀（约 4–5 份拷贝），并没有避免下载本身。

## 🔴 Blocker

### 🔴1 翻页后轮询会在列表中段永久丢消息（任务书第 3 项修法错误）

**位置**

- `SignalsScreen.tsx:334-339`（`mergePolledPage`）
- 调用处 `:152`、`:155`
- 测试 `__tests__/signalsScreen.test.tsx:308-335`

```ts
function mergePolledPage(old, next) {
  if (old.length <= 500) { return next; }
  return mergeRows(old.slice(500), next);   // 默认 old 的前 500 条就是"首页"
}
```

**为什么错**

`old.slice(500)` 默认"已加载列表的前 500 条"与"本次轮询返回的 500 条"覆盖同一段时间，但两者之间差了 N 条新消息。

举例：已加载 1000 条（id 1000..1），这时来了 10 条新消息，轮询返回 1010..511。合并结果是 1010..511 加上 500..1，**501..510 消失**。之后每次轮询只要带回 N 条新消息，就再丢 N 条。

`cursorFor` 取的是最旧一行，所以翻页永远不会把这段缺口补回来。结果是用户在信号列表里看不到一些历史信号，界面上也没有任何提示。这比上轮的"截断"更糟：截断是看得见的，重新滚动就能恢复。

**实跑复现**

探针用例：首页 500 条，翻页再加 500 条，轮询返回最新 500 条，其中 10 条是新的。

```
Expected {count: 1010, missing: []}
Received {count: 1000, missing: [501, 502, …, 510]}
```

**现有测试为什么没发现**

`:308-335` 的轮询 mock 只返回 1 行（`[{id: 999}]`），用例只断言 id 0 和 id 999 在列表里。按那组数据，轮询之后列表只剩 `{999, 0}` 两行，首页的 500 行全没了，用例照样是绿的。

**建议修法**

1. 翻过页（`old.length > 500`）之后，轮询结果按 id 并入整张已加载列表：`mergeRows(old, next)`。
2. 没翻过页时，保持现在的 `return next`。
3. 测试改用真实形状：每页 500 条、时间和 id 连续、轮询返回最新 500 条且其中 N 条是新的。断言 id 连续、总数为 1000+N；再轮询一次，断言仍然连续。

## 🟡 建议

### 🟡1 Fresco 位图缓存的键持有完整 data URI（R15 没有覆盖的原生保留路径，需要 Planner 或用户决定，Tester 真机把关）

**证据（Fresco 3.6.0，用 javap 反汇编 Gradle 缓存里的 aar）**

- `DefaultCacheKeyFactory.getBitmapCacheKey` 用 `request.getSourceUri().toString()` 构造 `BitmapMemoryCacheKey`。这个 key 的字段 `sourceString` 就是整条 `data:image/jpeg;base64,…` 字符串。
- `DefaultBitmapMemoryCacheParamsSupplier` 的参数：
  - `MAX_CACHE_ENTRIES = 256`
  - 淘汰队列的大小和条目数都是 `Integer.MAX_VALUE`
  - 总量只按位图字节计算（`memoryClass/4`，典型值 64 MB）
- RN 没有覆盖 CacheKeyFactory 或缓存参数（在 `ReactAndroid` 里 grep 不到）。

**后果**

行滚出视口后，JS 已经按 R15 释放了 uri，但 Fresco 的"可淘汰"缓存仍然保留这张缩略图的小位图，连同它那个约 1.34S 字节的键字符串。

缩略图经过 resize 后，位图约 0.2–0.3 MB，64 MB 的预算能放下 200 多张。所以 **200 条含图消息滚完一遍后，大约 200 个完整 data URI 仍然留在 Java 堆上**，而且只受 256 这个条目上限约束，不受字节约束。

**上界估算**见下一节。结论是：最坏情况（缩略图都接近 1 MiB）超过 300 MB，Java 堆有 OOM 风险；典型情况（Telegram 照片 150–300 KB）接近预算。

**可选方向（Planner 裁定）**

1. 采用 R15 暂缓的长期方案：注册 BlobProvider，改用 `URL.createObjectURL` 得到 `content://` 短 uri。键会变得很短，`resizeMethod` 用 auto 也会自动缩放。需要改 manifest，要用户授权。
2. 过渡方案：把缩略图上限从 1 MiB 降到 256–512 KiB，最坏情况的键保留降到约 70–140 MB。
3. 不改代码，以真机实测为准。

### 🟡2 在 RN 上，"Content-Length 超限不读 body"并没有省下下载；超限路径也不 close

**位置**：`watcherApi.ts:183-185`（抛出 `tooLarge`，但没有释放 Response 里已经存在的 Blob）。

**原因**：见上面的专项。RN 的 fetch 在 body 全部下载进 BlobModule 之后才 resolve。超限时 JS 没有调用 `blob()`，那份原生 `byte[]`（网关允许最大 20 MiB）只能等 Hermes GC 回收 BlobCollector 时才释放。

失败会被记住，所以每个文件在每个档位最多下载一次。但快速滚过一批大图时，原生内存会随 GC 的时机堆积，流量也白白浪费了。

**建议（需要 Planner 调整 R15 措辞，因为"不读 body"只是 JS 层的概念）**

- 方案一：在超限分支里执行 `response.blob().then(closeBlob)`。在 RN 上这一步不产生新的读取，只是立即释放。
- 方案二（更好）：`mediaBlob` 带上 `Range: bytes=0-{maxBytes}`。watcher 和网关都已经支持 Range 和 206（`media.js:100-107`，`watcher_gateway.py:426-435`）。如果 `Content-Range` 里的总长超过上限，直接判定过大，最多只下载 maxBytes+1 字节。这样 RN 不支持流式读取的问题也一并解决了。

## 💭 Nit

1. **M15b 以进程崩溃的方式被抓住。** `watcherApi.test.ts:371-390` 在 `advanceTimersByTime(4_999)` 之后才挂上 `.catch`。期限被改成 1s 时，reject 在推进过程中发生，变成 unhandled rejection，整个进程退出。建议在推进时钟之前先写 `const settled = result.catch(v => v)`。上轮的 💭2 也是同一个形状。
2. **缺 Content-Length 或值不合法时报 `media_too_large`，占位显示"图片较大，点开查看"**（`watcherApi.ts:141-143`），会误导用户。建议单独给一个 `media_length_unknown` 码，占位写成"图片暂不可用"。
3. **N7c：瞬时失败按 `filename@maxBytes` 记住。** 这个写法本身是对的，缩略图超时不应该拦住详情大图，但没有测试锁住。
4. **转换阶段不受并发 2 的约束。** 已开始的任务在最后一个观察者离开时，会立刻 `finish` 并释放槽位（`watcherMediaQueue.ts:158-165`），但原生 FileReader 还在继续转换。快速滚动时，原生侧同时进行的转换可能超过 2 个。影响有限，建议在注释里说明，或者让槽位等转换真正结束再释放。
5. **泛型错误（比如解码失败）不会被记住**（`:221-224`），重新挂载就会重新下载。这是可接受的，但损坏的图片每次滚回来都会再下载一次，建议把 `media decode failed` 归入确定性失败。
6. **翻页请求和轮询共用 `requestId`**（`:126`、`:139`）。翻页请求还在进行时，如果轮询到点，翻页的结果会被丢弃，而 `onEndReached` 在内容长度不变时不会再次触发，用户需要再滚动一次才会加载。另外 `listError` 在三个区段之间共用，切到空区段时可能显示其他区段的错误。

## 内存上界重估：200 条含图消息，快速滚动

**假设**

- 每屏可见约 V=10 行
- 缩略图原文件 S ≤ 1 MiB（R15），data URI 约 1.34S 字符
- Hermes 对 ASCII 字符串按 1 字节/字符存储
- ART 的压缩字符串按 1 字节/字符估算；如果不压缩，Java 字符串那几项要乘 2
- 并发为 2

| 项 | R15 之前（上轮） | 本轮最坏情况（S≈1 MiB） | 本轮典型情况（S≈250 KB） |
|---|---|---|---|
| JS：LRU 缓存 | 上限约为 2 条，但行 state 无上限 | ≤ 24 MiB | 60 条 × 0.33 ≈ 20 MiB |
| JS：可见行持有的 uri（多数与缓存共用） | 约 200 条 | ≤ 10 × 1.4 = 14 MiB | 可忽略 |
| JS：详情大图（≤ 8 MiB，不缓存） | 无上限 | ≤ 11 MiB | 小于 1 MiB |
| 原生：可见 Image 的 prop（Java 和 C++ 各一份） | 无上限 | ≈ 28 MiB | 约 7 MiB |
| **原生：Fresco 位图缓存的键（🟡1）** | 上轮漏算 | **200 × 1.4 ≈ 280 MiB**（Java 字符串不压缩时约 560） | 200 × 0.33 ≈ 67 MiB |
| 原生：位图（resize 后，缓存上限为 memoryClass/4） | 每屏 160–315 MB | ≤ 64 MB 加详情约 4 MB | 约 60 MB |
| 原生：进行中的转换（≈5S × 2），转换阶段可能超过 2 个（💭4） | 无上限 | 缩略图约 10 MiB，详情约 40 MiB | 约 3 MiB |
| 原生：超限文件在 GC 之前的残留（🟡2） | 不适用 | 每个文件 ≤ 20 MiB，累积量取决于 GC | 约 0 |
| 应用基线（RN release 构建） | 约 80–120 MB | 约 100 MB | 约 100 MB |

**结论**

- 上轮 🔴1 在 R15 的范围内**关闭**。JS 侧持有的 data URI 从"约 200 条、没有字节上限"降到"≤ 24 MiB 缓存加可见行"；缩略图位图从全尺寸降到约 0.3 MB。
- §5.2 的"内存峰值 < 300 MB"**不能在纸面上判定通过**：
  - 典型数据下估算约 250–280 MB，接近预算。
  - 缩略图普遍接近 1 MiB 时，仅 Fresco 键就约 280 MiB。它占用的是 Java 堆，而平板的 heapgrowthlimit 常见为 256–512 MB，所以有 OOM 风险。
- 结论必须由 Tester 在真机上实测给出（下面的指标）。如果实测超标，按 🟡1 的方向 1 或方向 2 处理。

## Tester 真机验收指标（只在用户明确说"现在可以用"之后执行）

**数据集**

200 条含图消息，按下面的比例混合：

- 约 70% Telegram 压缩照片（100–400 KB JPEG）
- 约 15% 接近上限的图（0.9–1.0 MiB）
- 约 10% 超过缩略图上限的图（1.5–8 MiB）
- 约 5% 超过 8 MiB 的图
- 其中包含一部分 PNG 文档

**脚本**

release 构建、Wi-Fi，按 §5.2 执行 60 秒滚动脚本：快速上下滑动 3 个来回，然后依次打开 10 个详情再返回。**平板和手机各跑一次。**

**需要采集的数据**

1. **内存。** 每秒执行一次 `adb shell dumpsys meminfo <pkg>`，记录 TOTAL PSS、Java Heap、Native Heap、Graphics。
   - 峰值 PSS 必须小于 300 MB。
   - 同时记录 `getprop dalvik.vm.heapgrowthlimit`；Java Heap 峰值占 heapgrowthlimit 的比例应小于 60%。
   - 停止滚动并静置 60 秒后再采一次。如果 Java Heap 基本不回落，就是 🟡1 所说的 Fresco 键保留在起作用。
2. **崩溃和 OOM。** 检查 `adb logcat -b crash` 以及 logcat 中的 `OutOfMemoryError`、`Canvas: trying to draw too large bitmap`。
3. **GC 压力。** 统计 logcat 中 `concurrent copying GC` 的频率，以及每次 GC 前后的 Java 堆。
4. **帧率。** 用 `dumpsys gfxinfo <pkg>` 统计掉帧率（< 3%）和超过 100 ms 的长帧（< 5 次）。
5. **Content-Length 是否真的到达客户端。** 正常大小的图都应该显示图片，而不是"图片较大，点开查看"。如果大面积出现这个占位，说明生产 Caddy、HTTP/2 或压缩把 Content-Length 去掉了。另外核对网关的 media 响应头。
6. **流量。** 超过缩略图上限的文件，每个在每个档位只应下载一次；记录下载的总字节数（`dumpsys netstats` 或网关访问日志），用来评估 🟡2。
7. **并发。** 网关的 media 访问日志中，同一时刻不应超过 2 个请求。
8. **焦点。** 切到交易 Tab 停留 2 分钟，网关日志中不应出现 status 或列表请求。在紧凑布局下打开信号详情后切换 Tab，按一次返回键应当立即生效。
9. **翻页和轮询（针对 🔴1 修复后的版本）。** 翻到第 2 页后，等待期间让新消息进来，然后核对第 500 条附近没有缺口。

**禁止**

- 不要执行 `am dumpheap`。heap dump 中含有 bearer token，违反铁律 3。
- 不要把设备日志原样提交。
