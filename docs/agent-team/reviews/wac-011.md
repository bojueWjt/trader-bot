## 总评

主体扎实，值得点名表扬：

- `transactWrite`（`lib/config-store.js:407-483`）把查重、版本比较、业务校验、业务写、`revision+1`、审计和成功响应体都放在同一个 `BEGIN IMMEDIATE` 里（`transaction.immediate()`），事务外只发响应。顺序与 §9.12 第 1–6 步逐条一致，重放判断先于版本比较。
- 秘密字段在事务之前被拒绝，拒绝的请求不写审计、不占幂等键（实测：先 400 后同 ref 合法请求得 200）。
- 快照在一个读事务里完成，字段白名单构造，数值用 `String(Number(x))`，排序 `COLLATE BINARY`；`content_sha256` 与 Python `json.dumps(sort_keys, separators, ensure_ascii=False)` 逐字节一致（实测含中文 account_id、`1e-7`、NULL `default_risk`）；表缺失返回 `snapshot_unreadable`，列缺失返回 `snapshot_invalid`，空表返回空数组，三者可区分。
- 用 `BEFORE INSERT` 触发器模拟审计写失败来验证回滚，是很好的 crash-before-commit 夹具。

需要退回的问题集中在两处契约规范性条款：R7 部分更新，以及站点"按资源保存 revision"。

## 🔴 Blocker

### 🔴-1 R7 部分更新未落实：主子结构校验无条件执行，app 改启用、addon 等字段会被存量结构状态卡住
- 位置：`lib/config-store.js:313`（`validateHierarchy(db, row)` 无条件调用）；`:207-235`（其中"父账号必须已启用""主子环境一致"都按合并后的整行判定）。
- 契约：§9.12 R7（规范性，E-07，Planner 裁定 R7）要求跨行约束只在它的输入键被提交时评估，即提交了 `account_type`、`parent_account_id` 或 browser 的 `is_testnet` 之一；并且"存量越界值不阻止启用/停用等其他字段的修改"。
- 实测（gateway 身份，只提交一个字段）：
  - 主账号先被停用，再对其子账号 `PUT {is_enabled:false}`：得到 400 `invalid_body` "parent must be an enabled main account"。
  - 同样条件下 `PUT {risk_capital_addon:5}`：得到 400。
  - 存量主子 `is_testnet` 不一致时，`PUT {is_enabled:false}`：得到 400 "subaccount environment must match parent"。
- 为什么是 blocker：这偏离了规范性契约（红线 5），而且后果在操作上最糟：先停主账号、再停子账号是自然顺序，停主账号之后，app 就无法再停用或调整它的子账号。现有 R7 测试（`config-store.test.js:259`）只覆盖主账号上的 `default_risk_ratio` 越界，没有覆盖结构约束，所以没抓到。
- 修法建议：只有 `input` 含 `account_type`、`parent_account_id` 或 `is_testnet` 时才调用 `validateHierarchy`；执行账号唯一性只在提交 `execution_account_id` 时检查（现在 `:314` 也是无条件的，因为有唯一索引所以无害，但应一并收敛）。补测试：父账号停用、主子环境不一致，两种情况下 gateway 与 browser 各做一次只改 `is_enabled` 的请求，期望 200；同时提交 `account_type` 时仍然按规则拒绝。

### 🔴-2 站点用一个全局 `configRevision`，没有按资源分别保存，条件写可能丢失更新
- 位置：`public/index.html:900`（单一 `let configRevision`）；`:937-943`（任意资源的 GET 都会覆盖它）；`:953-955`（任意写响应的 `revision` 也会覆盖它）；`:924`（所有资源的写都用它作 `expected_revision`）。
- 契约：§9.12"客户端取用 revision 的规则（站点与 app 相同）"要求按资源（accounts、channels、risks）各存一份，"不得用其他资源读到的更大值（那会让用户没看到的账号改动被覆盖）"；§9.13 站点 JS 清单第 1 项"按资源各存一份"逐项作为验收。
- 丢失更新路径：站点加载账号页，accounts 为 v5，用户打开账号 X 的编辑表单 → app 修改账号 X，revision 变为 v6 → 站点用户先加一条风控，POST risks 带 5，得到 409，自动重新加载 risks，全局值变为 6 → 用户保存账号 X 的旧表单，PUT 带 6，与当前值相等，写入成功，app 的改动被静默覆盖。条件写本来就是为了挡住这种情况（红线 5、6）。
- 现有 UI 测试 `account-config-ui.test.js:50` 断言的正是 `expected_revision: configRevision` 这个全局写法，会把错误行为锁死，需要一起改。
- 修法建议：使用 `configRevisions = {accounts, channels, risks}`，按 path 前缀取值和更新；写成功后只更新该资源的值，并重新 GET 该资源。`loadChannels` 同时 GET accounts 与 channels，两个值各自记录。

## 🟡 建议（不阻塞本轮，但请随修复一起处理或登记）

1. **测试漏过"幂等查重移出事务"**：`config-store.test.js:283` 的"并发同 ref"用例在同一个 Node 进程里用 `Promise.all` 发两个请求，better-sqlite3 是同步的，两个 handler 实际上串行执行，测不到锁竞争。建议加跨进程用例：子进程 `BEGIN IMMEDIATE`，插入同键、同摘要的审计行并持锁 1 秒，同时发 HTTP 请求，断言 200 `replay:true`。我的探针（scratch `w011/__probes__/xproc.test.js`）可以直接改造使用。这条很重要：该变异会把"已提交的成功"报成确定性 409，客户端随后会换新 `client_ref`，正好违反 §9.12 的重试规则。
2. **测试漏过"快照排序"**：所有夹具都按主键升序插入。建议用乱序插入加大小写和非 ASCII 主键（如 `S`、`M`、`a-lower`、`账户α`），断言 `COLLATE BINARY` 顺序。
3. **旧测试断言被不必要地削弱**：`trading-api.test.js:662、666、680` 把 `subaccount_count`、`channel_count`、`active_order_count` 的断言换成了只查 `code`。实现仍然输出这些计数（`config-store.js:88-92`），原断言本来能通过。站点 `accountApiError`（`index.html:1594-1608`）依赖 `error === 'Account has subaccounts'` 等文案做本地化提示，现在没有测试锁定。请恢复计数断言，并补上 browser `error` 文案断言。
4. **SQLite CHECK 违约映射错误**：`config-store.js:99-106` 把 `SQLITE_CONSTRAINT_CHECK` 映射为 409 `constraint_conflict`，§9.12 R7 第 4 点要求 CHECK → 400 `validation_failed`；`SQLITE_CONSTRAINT_NOTNULL` 没有映射，会落到 500。
5. **未知异常不写日志**：`sendError` 的兜底分支（`config-store.js:107-111`）直接返回 500，不再像旧的 `sendServerError` 那样经 `safeErrorMessage` 记日志，线上排障会失明。§9.5 R8 要求堆栈只写经 safe-log 过滤的日志，而不是完全不写。
6. **启动迁移只跑一次的设计**（回答派发问题）：`trading-api.js:131-150`。现状下既不会漏迁移也不会重复迁移：老库首次启动时，`TRADING_SCHEMA_SQL`、`migrateAccountSchema` 与建 `config_revision` 在同一个 IMMEDIATE 事务里原子完成（SQLite 的 DDL 可回滚）；之后跳过迁移，避免迁移里的 `UPDATE ... is_enabled=0` 成为绕开 revision 的写入。遗留两个隐患：(a) 以后往 `migrateAccountSchema` 加的新步骤，在已版本化的库上会被静默跳过，建议改为带版本号的迁移，且任何改数据的迁移都在同一事务里 `revision+1`；(b) 如果回滚到旧版 watcher（旧版每次启动都跑迁移，站点写也不涨 revision）再升回来，库里会出现"同 revision 异摘要"，C-0 锁存为 `invalid`，要等下一次配置写才能解除。db_manager.py 的直写也是同样的效果。这一点应写进 O-0 回滚 runbook。
7. **启动失败改为抛出**：`trading-api.js:151-154` 新增了 `throw err`。`server.js:863` 在顶层调用它，而 `uncaughtException` 守护只记日志，结果是进程以 0 退出（实测），在 `restart: unless-stopped` 下进入重启循环，Telegram 采集也跟着停。fail-closed 方向本身可以接受，但属于行为变化：首次上线时迁移事务如果拿锁超过 5 秒（例如 db_manager.py 正在写），watcher 整体起不来。请写进 O-0 清单。
8. **站点清单第 6 项未做**：`index.html:1096`（reconnect）与 `:1169`（groups）没有带 `client_ref`。可重入行（`groups.save`、`telegram.disconnect`、`telegram.reconnect`）的幂等审计在 server.js 里也没有实现，W-0a 和 W-0b 的文件范围都不含这部分。请登记进 wac-015（见下方补充清单）。
9. **gateway 角色不足的错误码**：`config-store.js:415` 返回 `insufficient_scope`。按 §9.5，这个码只由网关产生，watcher 对应的是 `identity_forbidden`（W4 已先行拦截，这里只是纵深防御），建议统一。
