## 7. 🟡 建议（本轮新增，都不阻塞）

1. **P2 只由测试锁定，校验脚本不锁。** `check_watcher_gateway_routes.py:23-37` 从已提交产物里读出 phase_max，再按这个值重新生成并比对。所以如果有人用 P3 重新生成并同时提交两份产物，校验脚本仍会输出 `ROUTES_DIFF_EMPTY`，这时只有 pytest 和 node 两处 `== "P2"` 的断言能拦住（R13 变异已证实能拦住）。建议 O-0 的部署门禁在跑校验脚本之外，也跑这两份测试，或者核对 `phase_max=P2` 这一行输出。等 A-6 召回落地、需要放开 P3 时，应同时修改两处断言和本条门禁，这也是一个显式的审批点。
2. **沿用上一轮的 🟡-8**：`asyncio.timeout_at` 需要 Python 3.11 或更高版本。O-0 部署前必须确认 jp-24 上 `.venv-cp` 的解释器版本，否则网关的每个请求都会 500（进程能起来，因为这个名字只在调用时才解析）。

## 8. 💭 Nit

1. 三处测试都通过系统的 `python3` 加 PyYAML 读取真源：`test_watcher_gateway.py:30`、`:473`，JS 测试 `:14`。在缺少 PyYAML 的环境里，这些测试会直接报错而不是跳过。按 R9，这只影响开发环境，可以接受，但报错信息不如校验脚本的 `ENVIRONMENT_ERROR` 清楚。
2. 校验脚本输出的 `rows=63` 统计的是 YAML 真源的行数，而产物只有 59 行。建议输出里同时列出产物行数，避免误读。
3. G5 在配置错误时每个请求都打一条告警（`watcher_gateway.py:312`），错误配置期间日志会被刷屏。可以考虑做限频，或者同一原因只打一次。
4. 上一轮的 💭-2（JSON 行的 Content-Type 应固定为 `application/json`）、💭-3（httpx 客户端在 shutdown 时关闭）、💭-4（import 时做最小的形状自检）、💭-5（S-12 反方向没有检查）仍未处理。

## 9. 值得点名的好代码

- h11 协议层测试（`:418-447`）：让服务端协议机实际发送一遍响应，Content-Length 与 body 不一致时会在生产出问题的那一层直接报错，不依赖测试客户端的宽容。
