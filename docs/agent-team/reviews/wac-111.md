值得点名表扬的几处：
- **"最近消息"用服务端时间差推算**（`SignalStatusCard.tsx:19-29`）：`syncedAt - max(0, observed_at - last_message_ingested_at)`，设备和服务器之间的时钟偏差不会混进来；负值被截到 0，解析失败返回 `false`，界面上就不显示这一项，不会凭空编一个时间。
- **共享时钟只让时间文字重绘**：每个行卡片里的 `RelativeTime` 自己订阅 `useSyncExternalStore`，行组件本身的 memo 不受影响，M25 的渲染预算保持不变。最后一个订阅者卸载时定时器随之清除。变异自测确认这条用例真能拦住回归（§3 M1）。
- **下拉刷新、重试、加载更多都复用同一条 `refresh`**，不另开端点，也不引入新游标，并发时由原有的 `requestId` 序号兜底。
- `listErrorCopy` 覆盖了 `signalErrorText` 的三种输出和两条启动期文案，列表为空时状态卡不重复显示错误。
- antd `Button` 渲染成 `Pressable`，并带上 `accessibilityRole="button"` 与 `accessibilityState.disabled`（antd 5.4.3 源码已核对），所以原用例"未配置时两个按钮禁用、标签为 disabled 色"依然有效。

## 3. 分级意见

### 🔴 Blocker
无。

### 🟡 建议（建议在平板测试前修）

**🟡-1 打开全屏查看器时，同一张大图会同时在内存里存两份，而且会再下载一次。** `SignalDetail.tsx:42` 和 `SignalMedia.tsx:124-129`
- 查看器里又挂了一个新的 `SignalMedia`，它会重新 `queue.load(filename, 8 MiB)`，而详情里的内联大图（`SignalDetail.tsx:70`）同时还挂着。
- R15 规定单条超过 2 MiB（按 data URI 字符数）不进 LRU（`watcherMediaQueue.ts:195`），所以原文件大于约 1.5 MB 时缓存不命中。结果是：重新下载最多 8 MiB，JS 堆里同时存在两份约 11M 字符的 data URI，原生层还要按 320dp 和全屏尺寸各解码一次。
- 单次加载的上限仍然有效，但峰值内存大约翻倍，这正是 R15 要防的情况。这类图片在信号频道里很常见（截图）。
- 建议：让 `onOpen` 把已经加载好的 `uri` 传给查看器，查看器直接渲染这个 uri，不再调 `load`；或者查看器打开时把内联图的 `visible` 置为 false，保证同一时刻只有一份。再补一条用例：打开查看器后 `load` 调用次数不增加。

**🟡-2（存量缺陷，这次重构正好碰到）平板双栏下切换记录时，新记录的图会停在上一条的错误占位上。** `SignalsScreen.tsx:392`、`SignalMedia.tsx:36`
- `SignalDetail` 没有 `key`，切换记录后 `SignalMedia` 复用同一个实例，`error` 状态被带了过去，而 effect 在 `error && !retryRef.current` 时直接 return。
- 我写了一个临时探针用例（跑完已删除）来验证：记录 A 的图返回 `media_too_large`，切到记录 B 后，`load` 只被调用过 `['1-1.jpg']` 这一次，B 显示的是"图片过大，暂不预览"。如果 A 是加载成功的，那么在 B 加载完之前，会先闪一下 A 的图。
- 手机档不受影响，因为关闭详情时组件会卸载。基线里的逻辑完全一样，所以不算本次引入。但只需一处改动，而且还能顺带重置查看器的 `viewing` 状态，建议在这次一起修：给 `<SignalDetail key={`${section}-${selected.id}`} …>` 加上 key，并补一条"切换记录后重新加载"的用例。

**🟡-3 "+" 徽标会在还有更早数据时显示成确切条数。** `SignalsScreen.tsx:358`
- `more` 是按 `length % 500 === 0` 猜出来的。已经加载 500 条后，一次轮询合并进 3 条，就变成 503，"+" 随之消失，但更早的一页其实还在。
- 反过来，24h 内恰好 500 条时会一直显示 "500+"（误报的代价不大）。徽标在向用户陈述"一共多少条"，漏报等于把"不知道"说成了"就这么多"。
- 建议：用一个明确的状态记录"最后一次 append 是否返回了满页"，或者只要触发过 500 条的上限就一直保留 "+"。

**🟡-4 连续触发 `onEndReached` 时，"正在加载更早的记录"会提前消失。** `SignalsScreen.tsx:374-383`
- 回调没有检查 `loadingMore`。如果连续触发两次，第一个请求会被 `requestId` 作废，但它的 `finally` 已经把 `loadingMore` 置回 false，而第二个请求还在进行，页脚就提前消失了。
- 重复发请求本身是存量行为，但这个页脚是本次新增的。建议加上 `&& !loadingMore` 守卫，这也顺带去掉了重复请求。

### 💭 Nit

1. **"全组合 ≥4.5:1"说得略满。** 按下"断开"时，critical 文字落在 `ghostHighlight` 的 surfaceRaised 底上，只有 **3.89:1**（`signalButtons.ts:22`）。这是按下时的瞬态，影响很小，但可以改成用 surface 底，或者在用例里写明是豁免。另外，未知方向的订单标签是 muted 填充配 onAccent 文字，我补算为 7.87:1，达标，只是没进用例（`signalFormat.ts:78`）。
2. 行卡片上的相对时间用的是设备时钟减服务端的 `created_at`，时钟偏差会混进来。状态卡已经规避了这一点，行卡片没有。未来时间会显示成"刚刚"，不会出错，但如果设备时钟慢几分钟，新消息会一直显示"刚刚"。可以考虑复用状态卡的偏差校正（`syncedAt - observed_at`）。
3. 底部 tab 不会卸载信号页，所以切到别的 tab 时，已挂载的 `RelativeTime` 每 30s 仍会重绘一次。开销很小，可以接受；想省的话，可以在失焦时暂停订阅。
4. `SignalMediaStrip` 用 `key={file}`，以后后端给出多图时，如果文件名重复会产生重复的 key。可以改成 `${index}-${file}`。
5. 行卡片是 `accessibilityRole="button"`，内部的"点按重试"是嵌套的可点元素，TalkBack 没法单独聚焦到它。基线也是这样，这次没有变差，记录一下，后续可以在行的 `accessibilityActions` 里加一个重试动作。
