## 自主扩展评估

### 1. 错误映射不再采用服务端的自由文案，只用结构码对应的固定文案：合理，保留

- 契约 §9.5 写的是 `message` 为"人读文本，非契约"，"客户端只按 code 分流"。改成固定文案是在收紧实现，没有偏离契约。
- 服务端的 message 虽然经过网关过滤（不超过 200 字符、不含控制字符），但内容仍来自上游。只用固定文案，就把"服务端回显的东西出现在 UI 或错误对象里"这条路径整条关掉了，这也是第 6 项 token 扫描能稳定成立的前提（N7 能证明）。
- 代价：兜底分支只显示"请求失败 (400)"之类的文案，看不出原因。A-0 目前只有只读的设置页，没有影响。A-2 做交易配置表单之前，必须把相关码映射成固定文案，见 🟡3。

### 2. 拒绝"含 bearer 的 client_ref"：合理，保留

- client_ref 会进入 `X-Request-Id` 请求头、请求 body，以及 watcher 的 `config_audit`（§9.12）。如果调用方误把 token 当作 client_ref，token 就会落进审计表，这是凭据红线。CLIENT_REF 的正则 `[A-Za-z0-9._:-]` 并不能排除形似 token 的字符串。
- 检查放在所有网络动作之前（`:224-226`），抛出的是不含 token 的普通 `Error('invalid client_ref')`，并且有测试（`:170-176`，N10 能抓住）。
- 局限：只拦得住包含完整 token 的子串，拦不住 token 片段或其变形。它是纵深防御，不能代替"client_ref 由随机 UUID 生成"这条规则。A-2 的任务书应写明：client_ref 用 `crypto.randomUUID()` 或等价方式生成，在用户确认时生成一次并持久化，结果未知时重试沿用同一个号。
- 误伤风险：只有在 token 极短（比如只有几个字符）这种配置错误时才会发生，表现是写操作被拒（fail-closed）。可以接受。

## 🟡 建议

1. **媒体时限只覆盖到 `fetch()` 的 Promise 完成为止，拿到 Response 之后的 body 读取没有客户端时限；调用方也无法取消请求。** 位置 `watcherApi.ts:258-298`：定时器在 `finally` 中清除，controller 是局部变量，返回 Response 之后外部拿不到它。
   - 执行者的说法按 fetch 规范是对的，但需要补充一个运行时事实：RN 0.82 的 `fetch` 就是 `whatwg-fetch`（`node_modules/react-native/Libraries/Network/fetch.js` → `whatwg-fetch` 在 `xhr.onload` 时才 resolve），也就是**整个 body 下载完成后 Promise 才完成**。所以在真机上，现在这 60 秒实际上覆盖了整个下载过程。但这依赖 polyfill 的实现细节：只要 A-1 启用流式 fetch，或者换用其他取图方式，这个保障就没了。Jest 里的 mock 也测不出这一点。
   - 更实际的影响在 A-1 信号 Tab：列表中滚出视口或已卸载的图片无法取消，每个请求最多占住一个网关 media 槽 60 秒。每个 worker 只有 4 个槽（§9.7），快速滑动就可能把 media 预算打满，后续图片会拿到 503 `gateway_busy`。预算是隔离的，所以不影响 JSON 接口，但会出现成片缺图。
   - **A-1 任务书应写入的约束：**
     1. A-1 的范围要包含 `watcherApi.ts`。`media()` 增加可选参数 `signal`，外部 abort 时联动内部 controller 并清除定时器，抛出可区分的 `cancelled`（不能算作 `timeout`，也不能算作连接失效）。组件卸载或滚出视口时必须 abort。
     2. body 读取必须收进服务层，例如新增 `mediaBlob()`：同一个 60 秒定时器从发起请求开始计时，覆盖到 body 读取完成（blob、arrayBuffer 或落盘）后才清除，超时 abort 同一个 controller。调用方不得在服务层之外自己读裸 Response 的 body。测试要用一个 `blob()` 永不 resolve 的 Response 断言会超时、会 abort、定时器数为 0。不得依赖 whatwg-fetch 的缓冲行为来证明有时限。
     3. 客户端媒体并发不超过 2（低于网关每 worker 的 4 个槽），其余排队；同一文件去重；失败（404、416、`media_too_large`、`timeout`、`watcher_unavailable`、`gateway_busy`）显示占位图，不阻塞文本（§9.5"缺图不阻塞文本"），不做自动重试风暴。
     4. 所有媒体请求都经过 `WatcherApi`，不得用 `<Image source={{uri, headers: {Authorization}}}>` 直连。直连会同时绕开客户端时限、401 禁写和 `isConnectionInvalid`，还会把 bearer 交给原生层的请求与缓存。如果 A-1 确实需要原生 Image 管线，必须先由 Planner 裁定，并单独满足上面三条。
     5. bearer 只放在请求头里，URL 不带 token（沿用 M7 的测试）。媒体的 401 和 403 invalid_token 都要走 `isConnectionInvalid`，并触发 `WatcherApi` 禁写（补上 🟡2）。
2. **媒体遇到 403 `invalid_token` 时的禁写没有测试。** 代码 `:292-295` 是对的，但把它改成不禁写（N15）不会让任何测试失败。经过网关的媒体请求在控制面 token 失效时拿到的正是 403 `invalid_token`（§9.5），这条路径和 JSON 那一条同样重要。建议：在 `:273-280` 旁边加一个 `reply(403, {code: 'invalid_token'})` 的媒体用例，断言之后的 `write()` 以 `unauthorized` 拒绝，并且 fetch 调用次数仍为 1。可以放在 A-1 修改 `media()` 时一起补上。
3. **兜底分支改成固定文案之后，A-2 需要一张完整的 code → 文案映射表。** 目前 `validation_failed`、`secret_field_rejected`、`constraint_conflict`、`idempotency_conflict`、`not_found`、`payload_too_large`、`invalid_body`、`invalid_query`、`route_not_found`、`method_not_allowed`、`range_not_satisfiable` 都显示为"请求失败 (N)"（`:154-157`）。A-2 做交易配置表单时，应当按 §9.5 为这些码配固定中文文案，`validation_failed` 用 `details.field`、`details.rule` 定位到字段。不得恢复使用服务端的 `message`（N7 的测试会拦住）。`idempotency_conflict` 按契约"显示错误，不自动重试"处理。

## 💭 Nit

1. 测试没有把媒体超时值锁定在 60 秒：改成 1 秒（N14）仍然全绿。任务书允许"与其他请求一致或按 §9.9"两种取值，所以不算缺陷。建议在 `:282` 的用例里先推进 59 999 毫秒，断言请求仍在进行、signal 没有被 abort，再推进到 60 001 毫秒。
2. token 扫描（`:239-261`）的超时用例是通过 mock 一个 `AbortError` 进入 catch 分支的，没有覆盖 `Promise.race` 里定时器 reject 的那条文案（`:330`）。把 token 拼进那条文案（N19）不会被发现。目前那里是固定字面量，风险很低。建议加一个假时钟下的真实超时用例，纳入扫描。
3. `isConnectionInvalid` 里的 `error.code === 'unauthorized'`（`:90`）是必需的，因为 403 `invalid_token` 被 `mapError` 改写成了 `unauthorized`（N23 能证明）。但它也会把服务端某个未知的、原始值就是 `unauthorized` 的非 401 错误码判成连接失效，而且这种情况不会触发禁写，两边口径不一致。服务端目前不会产生这个码（§9.5 表里没有，网关也只透传表内码），所以只是记一笔。以后如果要收紧，可以在 `mapError` 的兜底分支把原始 `unauthorized` 改写成 `request_failed`。
4. `expectedRevision` 为负数或非整数的情况（`:234`）没有单独测试，目前只测了缺失的情况。
5. 上轮的 💭2（`getStatus` 没有校验时间字段的类型）、💭3（没有保留 rawCode）、💭5（`load` 把采集状态请求串在 `captureCapabilities` 后面）都维持原状，仍然不阻塞。

- 媒体超时测试同时检查了 signal 是否被 abort 和定时器数是否为 0，而不是只看 Promise 是否 reject。
- 设置页"连接失效"用例故意用了空 message 的 403 `invalid_token`。只有使用 `isConnectionInvalid` 才能显示正确文案，所以 R14"不得自行比较 status"这条规则真正被测试守住了（N3、N22）。
