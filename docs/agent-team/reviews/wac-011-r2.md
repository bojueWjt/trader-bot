## 🔴 Blocker

### 🔴-1 "数据库初始化失败非零退出"在真实入口不成立：进程不退出，也不监听端口，成为僵尸
- 位置：`lib/trading-api.js:152-154`（`process.exitCode = 1; throw err;`）；调用点 `server.js:863`（integ 合并后同样位于 `registerTradingApi(app, priceMonitor)`）；`server.js:35-38` 的 `uncaughtException` 守护只记日志；`server.js:207` 的模块级 `setInterval(checkWatcherHealth, 5000)` 没有 `unref`，事件循环不会结束。
- 实测（在 scratch 副本中运行真实 `server.js`，没有 config.json，没有 Telegram 连接，DB 路径指向目录）：
  - 7edcf6e：日志先出现 `[db] Failed to ensure trading tables`，再出现 `[FATAL] uncaughtException`，之后进程一直存活，25 秒后被 alarm 杀死（142）。
  - integ + auto/wac-011 合并后（带 W-0a，使用假 token）：结果相同，20 秒不退出，日志中没有 `listening`。
  - 1763305（上轮版本）：结果相同。
  - 对照：把 `process.exitCode = 1` 换成 `process.exit(1)` 后，合并版的 `server.js` 立即以 1 退出。
- 为什么是 blocker：`exitCode` 只在事件循环自然排空时才生效，而 `server.js` 在调用点之前已经挂上常驻定时器，所以进程永远不会退出。结果是：`app.listen` 没有执行，站点、`/healthz` 与 API 全部不可用；Telegram 监听在 listen 回调里启动，也不会开始，信号采集静默中断。compose 的 `restart: unless-stopped` 只在进程退出时重启，healthcheck 变成 unhealthy 也不会触发重启。基线（21b0615）在同样情况下只记日志、继续采集 Telegram；wac-011 引入的 `throw` 把它变成了静默的全量停摆。本项目出过多次信号链断流事故，这属于正确性与可用性回归。同时，`__tests__/startup-failure.test.js:10-16` 用一个没有常驻定时器的 `-e` 替身脚本证明"退出码 1"，测的并不是真实入口，绿灯宣称了产品不具备的性质（红线 7 的精神：测试把要测的那件事建模掉了）。
- 修法建议（都在 wac-011 的文件范围内）：
  1. `lib/trading-api.js` 的 catch 中记完日志后显式调用 `process.exit(1)`（已实测有效）；或者由 `registerTradingApi` 返回失败，交给调用方退出，但那需要改 `server.js`，超出范围，不建议。
  2. 把 `startup-failure.test.js` 改为 spawn 真实的 `server.js`：`cwd` 设为临时拷贝或原目录；`env` 只给 `PATH`、`TRADER_TRADING_DB_PATH=<临时目录>`、`WATCHER_MEDIA_DIR=<临时目录>`、`WATCHER_HOST=127.0.0.1`，以及合并 W-0a 后需要的三个 `WATCHER_*_TOKEN`（用夹具生成的 ≥32 字节随机值；在 wac-011 分支上这些变量会被忽略，不影响）；确认没有 config.json，所以不会连接 Telegram；设 10 秒超时，断言 `status === 1` 且 `signal === null`。这样测试就锁住了真实入口的行为。

## 🟡 建议（不阻塞，请随修复一并处理）

1. **browser 身份的 R7 没有测试**（`config-store.test.js:302-346` 只覆盖 gateway）：变异"只在 gateway 身份下放宽"和"去掉 `is_testnet` 触发"都漏过了。建议补两条：主账号停用后，browser 只提交子账号的 `{is_enabled:false}`，期望 200；对有子账号的主账号，browser 提交 `{is_testnet:true}`，期望 409 `constraint_conflict`。本报告的 E8 已经验证实现正确，可以直接照抄。
2. **写响应"只更新本资源"没有测试**：变异"写响应 revision 写入全部资源"漏过。这也是一条真实的丢失更新路径：accounts 停在 v5，app 把账号 X 改到 v6，站点在 v6 读取 risks 并写入风控成功（v7）。如果写响应覆盖了所有资源，旧账号表单会带着 7 写入并覆盖 app 的改动。建议在 vm 用例里加这个序列，断言账号 PUT 仍然带 5。
3. **快照排序只测了 accounts**：channels、risks 单独去掉排序不会被抓住。建议对 `channel_routing` 与 `symbol_risk_configs` 也做一次乱序和反序插入，比较顺序与 `content_sha256`。
4. **R7 结构负例只断言 `status` 与 `code`**（`config-store.test.js:325-327、339-341`）：任何 400 都能让它们通过。建议断言 `message`，例如 "parent must be an enabled main account"、"subaccount environment must match parent"，确保拒绝来自主子结构规则，而不是别的校验。
5. **残余风险（契约的字面要求已满足）**：站点的 revision 取自"该资源最近一次 GET"。`loadChannels`（`index.html:1641-1646`）也会 GET accounts，所以账号编辑表单打开期间，只要触发一次 accounts GET，accounts 的 revision 就会前进，而表单里的数据仍是旧的。更稳妥的做法是在打开表单时记下该行的 revision，用它作为这次提交的 `expected_revision`。app 端也有同样的问题。建议交给 Architect，决定是否把"按表单记 revision"写进 §9.12，不在本任务范围内。
6. **O-0 清单**：CHECK 用例（`config-store.test.js:393`）说明，存量行如果违反 SQLite CHECK，会让同一行上无关的开关修改得到 400。这符合 §9.12"SQLite 约束照常生效"。旧库的表是否带 CHECK 取决于建表历史，O-0 的数据基线应当列出这类行。
