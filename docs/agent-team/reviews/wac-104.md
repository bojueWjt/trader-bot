### 2.3 BindRequestRoleMiddleware 与 `bind_request_role` 是否等价

- 语义等价：两者都只处理 `http` scope（`BaseHTTPMiddleware` 本身也只处理 http），都在进入时 `bind_app_role`，在 `finally` 中 `reset_app_role`（`app_roles.py:212-220`）。
- 顺序：`add_middleware` 插在最外层，实测顺序是 `[BindRequestRoleMiddleware, GatewayPathMiddleware]`，因此前缀中间件的 503/404 以及 endpoint 都运行在绑定之内。
- 流式响应与并发：我用 `asyncio.gather` 同时发出媒体 GET（上游用逐块生成器）、status、health、非网关路径与未知路径。上游 handler 与每个 chunk 生成时，`current_app_role()` 都是 `watcher-gateway`。请求结束后，调用方上下文中 `_ACTIVE_APP_ROLE` 为 `None`，没有泄漏。纯 ASGI 实现要等 `await self.app(...)` 返回、也就是整个 body 发送完之后才 reset，比 `BaseHTTPMiddleware` 更稳。
- sync 健康检查 `role_database_health` 在线程池中执行时，能读到绑定的角色（不设 env 时仍返回 watcher-gateway 分支；这由 `test_b10b` 覆盖，我的探针也复现了）。
- 变异验证：删掉 `add_middleware(BindRequestRoleMiddleware…)` 后，`test_b10b`、`test_b12_*` 两项共 3 个用例失败，说明测试确实在检测这一点。

- **🟡-3 `gateway_route_names` 与 `register_routes` 的阶段口径不一致。** `gateway_route_names`（`watcher_gateway.py:178`）按 `phase ≤ phase_max` 过滤，而 `register_routes`（`:628-640`）是既有代码，会注册 payload 中所有 gateway 行，不看 phase。目前生成器只输出 `≤ phase_max` 的行（实测 payload 中 gateway 行为 P0 1、P1 8、P2 11，没有 P3），所以两者相等，`test_b10b` 的集合断言也会拦住偏差。建议在 P3 启用或改动生成器时，让 `register_routes` 复用同一个过滤函数，只保留一个口径。
