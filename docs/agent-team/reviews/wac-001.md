## 🟡 建议（请写进对应任务书的验收项）

**🟡-1 快照 `invalid` 和 `401` 何时拒绝开仓，契约取了宽松读法，需要 Planner 裁决（C-0 开工前）。**
位置：`backend-api.md:353-357` 与计划 `:117`、`:119` 以及 T0-3 `:171`。
- 计划 `:119` 写的是"`expired` / `cold` / `invalid` / `401`：依赖快照的 `open_position` 归因一律拒绝"，T0-3 也把 invalid 和 401 列为状态机的状态。
- 契约把它们降格为 `last_refresh_error`，状态仍是 `fresh`，直到 age 超过 60 秒才拒绝。也就是说，watcher 开始返回 401 之后（例如旧 token 被撤销），或检测到"同 revision 异摘要"（有绕过审计的写入者）之后，开仓还会用旧快照最多 60 秒。
- 计划 `:117` 的"刷新失败不改变状态"让两种读法都说得通。所以我不判 🔴：60 秒的上限仍然成立，不存在无限期沿用。
- 建议：记为 A-8 交给 Planner 裁决。我推荐 `invalid`（尤其是同 revision 异摘要）和 `unauthorized` 立即进入拒绝态，理由是这两种情况说明真源或信任关系已经变了，这和普通的刷新超时不是同一类。若采纳，出一版 WGW-1.0.1 勘误改 `:353-357`。

**🟡-2 轮换用的 `*_PREVIOUS` 为空时，存在"空 token 命中空值"的隐患。**
位置：`backend-api.md:174`、`:179`。
- 启动时只约束三个当前值长度 ≥ 32。第 2 步写的是"规范化后命中当前/上一值"。
- 如果按字面实现，`Authorization: Bearer `（规范化后为空串）和未设置的 `WATCHER_*_PREVIOUS`（空串）做恒定时间比较会相等，直接拿到 gateway 或 snapshot 身份。这正是红线 3 说的"缺 token 降级免鉴权"。
- W-0 任务书必须写明三点：空串 token 在任何身份下都是 401；未设置或空的 `_PREVIOUS` 不参与匹配；`_PREVIOUS` 一旦设置也要满足 ≥ 32 字节和两两互异。
- T0-1 要增加两个负例："`Bearer ` 空值"和"`Bearer` 后只有空白"，在 `_PREVIOUS` 未设置时都应返回 401。

**🟡-3 网关的校验顺序没有写全。**
位置：`backend-api.md:208`、`:212-216`、`:277`。
- 契约只写了"404/405 先于鉴权"和"准入在 §9.3/§9.4 之后"。鉴权、角色与 query/body 校验之间的先后没有定义。
- 建议固定为：路由匹配（404/405）→ 鉴权（401/403/503）→ 角色（403）→ query/body/秘密字段（400/413）→ 准入（503）→ 上游。
- 理由有两点。一是未认证请求不应让网关读取并解析最多 64 KiB 的 body，也不应拿到 `secret_field_rejected` 或 `invalid_body` 这类反馈。二是 T0-1b 里"viewer 带 `api_key` 写"应该稳定地返回 403 `insufficient_scope`，而不是看实现先做哪一步。

**🟡-4 尾斜杠和 404/405 的处理只能作用于 `/v1/watcher/` 前缀。**
位置：`backend-api.md:207`、`:209`。
- 如果 C-1 图省事，在角色 app 上全局设 `redirect_slashes=False`，既有 `/v1/*` 的尾斜杠行为会从 307 变成 404，违反 §9.13 和红线 5。
- 另一个约束：§9.14.4 的运行时 diff 要求 `/v1/watcher/` 下的 `APIRoute` 集合和 YAML 恰好相等，所以不能用 catch-all `APIRoute` 来实现。
- 建议 C-1 用前缀限定的中间件，把它和异常处理器一起装到 `create_app()` 返回的角色 app 上。验收要加一条回归：既有 `/v1/accounts/` 的尾斜杠行为保持不变。
- 同时把 `:209` 的"实现提示"改成规范性要求，写进 C-1 任务书。

**🟡-5 `secret_key_pattern` 的正则方言。**
位置：`watcher-gateway-routes.yaml:84`。
- `(?i)` 前缀是 Python 语法。JS 的 `new RegExp('(?i)…')` 会直接抛 SyntaxError。
- 如果 W-0 为了消掉这个报错去掉 `(?i)`，watcher 第二层就会丢掉大小写不敏感。
- 建议 C-1 生成器把它输出为 `{pattern, flags: "i"}`，并在生成物的 diff 里锁住。同类问题：`path_params.account_id.browser_pattern` 在原 JS 里带 `/u` 标志（`trading-api.js:12`），生成物也要保留这个标志。

**🟡-6 `never_allowed` 按方法列出，比计划窄。**
位置：`watcher-gateway-routes.yaml:214-219`。
- 计划 §3 写的是"永不放行 `/api/config`、`/healthz`……"，不区分方法。YAML 对 `/api/config` 只列了 `[POST]`，对 `/healthz` 只列了 `[GET]`。

- 建议把 `never_allowed` 改成不区分方法（`methods: "*"`），S-18 同步修改。凭据面要靠两道独立防线，不能只剩覆盖预言一道。

位置：`watcher-gateway-routes.yaml:544-555`。

## 💭 Nit / 备忘

1. `secret_key_pattern`（`:84`）没有锚定，`api[_-]?id` 会误删含 `apid` 的键（例如 `rapid_*`）。现在没有这样的列，将来加列时要留意。
2. 快照校验比控制面现有 reader 严格：`account_type` 在控制面是 `lower(trim())` 宽松比较（`read_api.py:6368-6370`），启用值接受 `1/active/enabled/true`（`:6302-6308`）。`default_risk_ratio` 为 NULL 时，现有 `_symbol_risk_ratio` 实际会 `float(None)` 并返回 503，而不是回落到环境变量默认值（`:8509-8517`）。C-0 做 B/C 对照和 O-0 做数据基线时要把这几点列为预期差异或逐一核实。
3. gateway 的 `account_id` 路径正则（`:113`）比站点允许的凭据账号 ID 窄。O-0 基线要确认现存所有 `account_id` 都能匹配，否则这些账号在 app 里无法编辑（只影响功能，不影响安全）。
4. `assert_token_catalog_unique`（`principal.py:67-97`）不覆盖 `WATCHER_*`。建议 O-0 的发行侧互异校验把 gateway/snapshot token 与四个 reader token、signal token、节点 token 放在一起比对。
5. 容器健康检查（A-1）要在 node 脚本里读 `process.env.WATCHER_BROWSER_PROXY_TOKEN`，不要用 compose 的 `$VAR` 插值，否则 token 会以字面值写进 `docker inspect` 的 Healthcheck 字段。脚本也不能打印响应或请求头。
6. `groups` 没有条件写，站点和 app 同时编辑会互相覆盖。计划 §2.3 已接受这一点（可重入、以回读为准）。"截断到 100 条时不丢原已选"要写进 A-2 的验收。
