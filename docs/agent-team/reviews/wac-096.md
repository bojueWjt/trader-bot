### 2.4 L-1 为什么成立（逐步核对源码）

- Caddy `MatchPathRE.MatchWithError` 只对 `cleanPath(r.URL.Path)` 做匹配（`modules/caddyhttp/matchers.go:701`，v2.10.2），`cleanPath` 等于 `path.Clean` 再保留尾斜杠（`caddyhttp.go:302-308`）。
- Caddy 转发的路径是 Go 的 `URL.EscapedPath()`：原文是合法编码时用原文，否则对 `Path` 重新编码。凡是 `validEncoded` 拒绝的字节，`shouldEscape` 都为真，所以重新编码后的路径**必含 `%`**，G1 会拒绝。这一点实测可见：`\` 被转发为 `%5C`，`#` 被转发为 `%23`。
- 因此，转发路径若能通过 G1（不含 `%`、`//`、点段，也没有尾斜杠），它的解码结果就等于原文，clean 也不改变它，于是 Caddy 判定的正是这个 `/v1/watcher/…`。
- 前缀大小写：网关用 Python `str.lower()` 判断是否触发。全码点穷举显示，没有任何非 ASCII 字符经 `lower()` 后落进 `v1/watcher` 的字母集（`İ`→`i̇`，`K`→`k`，都不相关）。守卫的 `(?i:)` 在 Go 与 Python 下，对这段前缀也只接受 ASCII 大小写变体（§3）。网关的路由匹配（`_match_template`，`re.escape` 加 `fullmatch`）区分大小写，所以能通过 G1 的路径一律是小写原文。

## 4. 问题

### 🔴-1 N-3 的"改路径 handler"定义漏掉了 `reverse_proxy.rewrite`；按字面实现，V-1 至 V-5 对这类转发全部失明，RS-6 的一条期望也与 N-3、N-4 自相矛盾

**位置**：`contracts/backend-api.md` §9.14.6 N-3："改路径 handler 指 `rewrite` handler 带 `uri`、`strip_path_prefix`…（`handle_path`、`uri`、`rewrite`、`try_files`、`forward_auth` 都会生成它）"；N-3 (b) 的例子"`forward_auth` 生成的 `uri /v1/auth`"；§9.16 RS-6"`forward_auth 127.0.0.1:8183 { uri /v1/auth }` → PASS"。

**事实**：`forward_auth` 和 `reverse_proxy { rewrite … }` 都**不会**生成 `rewrite` handler，它们生成的是 `reverse_proxy` handler 自身的 `"rewrite": {…}` 字段。`caddy adapt` 实测如下：

```
forward_auth /bar/* 127.0.0.1:8183 { uri /v1/auth }
  -> {"handler":"reverse_proxy", "rewrite":{"method":"GET","uri":"/v1/auth"}, "upstreams":[{"dial":"127.0.0.1:8183"}], ...}
handle /foo/* { reverse_proxy 127.0.0.1:8183 { rewrite /v1/watcher/status  header_up Authorization "Bearer {env.SYSTEM_OBSERVER_TOKEN}" } }
  -> reverse_proxy.rewrite = {"uri": "/v1/watcher/status"}
```

**旁路实测**（`rw.test` 站点已 import 直连守卫，`handle /foo/* { reverse_proxy 18183 { rewrite /v1/watcher/dialogs; header_up Authorization "Bearer {env.SYSTEM_OBSERVER_TOKEN}" } }`）：

```
GET rw.test /foo/x              -> 200 body=4 upstream=[(18183, 'GET /v1/watcher/dialogs HTTP/1.1', 'injected=yes')]
GET rw.test /v1/watcher/status  -> 404 body=0 upstream=[]          (守卫照常生效)
G1: '/v1/watcher/dialogs'       -> 通过 G1，route_id=gw.dialogs.get  (上线后即以 observer 读到 dialogs)
```

**为什么每一道检查都会放行**：按字面，V-1 找不到 `rewrite` handler，于是把这条路由当作"不改写"交给 N-4；它的匹配器 `/foo/*` 不可能命中 D，N-4 判通过。V-2、V-3、V-5 只发 `/v1/watcher…` 的探针，全部由守卫应答，也都通过。现有 o0 脚本识别改写靠的正是 `handler == "rewrite"`（`o0_caddy_watcher_routes.py:1275`、`:1471`、`:1649`），RS 按文字扩展时会把这个盲区原样继承下来。

**自相矛盾**：站点顶层不带匹配器的 `forward_auth 127.0.0.1:8183 { uri /v1/auth }` 在 adapt 后是站点子路由的第 0 条，排在 `wgw_direct` 之前（实测：`0 null ['reverse_proxy'] rewrite={"method":"GET","uri":"/v1/auth"}`，`1 … wgw_direct`）。按字面它"不改写"，走 N-4：匹配器为空，可能命中 D，又排在守卫之前，判**失败**。RS-6 却期望它 PASS。只有把 `reverse_proxy.rewrite` 也算作改写，它才能按 N-3 (b)（常量 `uri`，不在 T 内）通过。

**修法建议**（WGW-1.0.3 第二轮）：
1. 定义改为：改路径 = `rewrite` handler，**或** `reverse_proxy` handler 的 `rewrite` 对象，只要其中带 `uri`、`strip_path_prefix`、`strip_path_suffix`、`uri_substring`、`path_regexp` 中的任一字段（只有 `method` 时不改路径）。同时更正括号中"`forward_auth` 生成 `rewrite` handler"的说法。
2. N-3 (b) 明确同样适用于 `reverse_proxy.rewrite.uri`。改写发生在转发这一步本身，所以它的"匹配器可能命中 D"不再按 N-4 判定。
3. RS-6 增加以下用例：`handle /foo/* { reverse_proxy 8183 { rewrite /v1/watcher/status } }` → FAIL；`reverse_proxy 8183 { rewrite /v1/watcher{path} }`（带占位符）→ FAIL；站点顶层不带匹配器的 `forward_auth 8183 { uri /v1/auth }`（排在守卫之前）→ PASS；`forward_auth 8183 { uri /v1/watcher/status }` → FAIL（已有）。

### 🟡-1 I-1、V-1 的枚举范围没有写明 `errors.routes`、`named_routes`（`invoke`）与 `handle_response[].routes`；`handle_errors` 旁路已实测

**实测**（`err.test` 站点：import 直连守卫；`forward_auth` 指向一个不存在的鉴权端口；`handle /v1/* { invoke obs }`；`handle_errors { reverse_proxy 18183 { header_up Authorization observer } }`）：

### 🟡-2 V-5 的 HEAD 探针判据形同虚设

**位置**：§9.14.6 V-5："期望全部为 404 且 `size_download == 0`"，五个请求中包括 `HEAD /v1/watcher/media/1700000000000-1.png`。

**理由**：HEAD 响应本来就没有 body，`size_download` 恒为 0。网关上线后如果没有守卫，这个 HEAD 会以 observer 通过 G1，文件不存在时上游返回 404，结果同样是"404 且长度 0"，被误判为通过。实测守卫的空 404 **没有** `Content-Type`（`HEAD guard 404 ct=[]`；GET 同样是 `ct=` 空），FastAPI 或网关的 404 则带 `application/json`。

**修法建议**：五个请求一律加上判据 `content_type` 为空，或者把媒体探针改成 GET。

### 🟡-3 V-5"生产公网"的发起位置没有定义

### 4. 问题

#### 🔴-A N-3 (b) 的"常量 `uri`"没有要求路径部分真的存在；路径为空的常量按豁免 PASS，但实际转发原路径（q1、q2、q4 实测旁路）

**位置**：§9.14.6 N-3 (b)："常量 `uri`（不含 `{`），且其路径部分（`?` 之前）不在 T 内……当常量 `uri` 位于该 `reverse_proxy` 自己的 `rewrite` 对象中时，发往 8183 的路径就是这个常量……**不再适用 N-4**"；N-5 错误链"只能按 N-3 通过"。

**Caddy 语义**（`modules/caddyhttp/rewrite/rewrite.go:158` 起）：`uri` 按第一个 `?`/`#` 切分，路径分量只在第一个字符既不是 `?` 也不是 `#` 时才存在（`:185` `case pathStart < 0 && qsStart < 0`）；只有这时才改 `r.URL.Path`（`:244` `if pathStart >= 0`）。所以 `uri ?a=1`、`uri "#frag"` 都**不改路径**，发往上游的仍是原路径，或者是前面改写过的路径。

**契约的判定**：(b) 取"`?` 之前"的部分，分别是 `""` 与 `"#frag"`，都不在 T 内，不含 `{`，于是判 PASS，并且"不再适用 N-4"。q1（`handle_path /x/*` 加 `rewrite ?a=1`）、q4（`rewrite "#frag"`）、q2（错误链，没有其他改写）因此都会被 V-1 放行。V-2、V-3、V-5 发的都是 `/v1/watcher…` 探针，由守卫应答，也会放行。整套检查对这类配置失明，与首轮 🔴-1 的形状相同。

**附带**（只能用 JSON 构造，Caddyfile 的 `reverse_proxy { rewrite }` 只能设置 `uri`）：同一个 `rewrite` 对象里，`strip_path_prefix`/`strip_path_suffix`/`uri_substring`/`path_regexp` 在 `uri` **之后**执行（`rewrite.go:260`、`:281`、`:286`）。`{"uri":"/v1/auth","uri_substring":[{"find":"auth","replace":"watcher/dialogs"}]}` 最终发往上游的是 `/v1/watcher/dialogs`。按现在的文字，这种组合是否仍算"自身 `rewrite` 对象里的常量 `uri`"而享受豁免，说不清楚。

**修法建议**：
1. 常量 `uri` 的"路径部分"按 Caddy 的规则取：第一个 `?` 或 `#` 之前的部分。它必须非空、以 `/` 开头（否则判 UNCOMPARABLE），才算"改路径"并适用 (b)。
2. 路径部分为空的 `uri`（只改 query 或 fragment）不改路径。这种对象不算改写，该转发器按"不改路径"走 N-4；在错误链、未被调用的命名路由里，直接判失败。
3. N-3 (b) 的豁免只适用于键集合 ⊆ `{uri, method}` 的 `rewrite` 对象（`query` 字段是否放行另行写明）；其他组合判失败。
4. RS-6 补用例：`handle_path /x/* { reverse_proxy 8183 { rewrite ?a=1 … } }` → FAIL；`handle_errors { reverse_proxy 8183 { rewrite ?a=1 } }` → FAIL；`rewrite "#frag"` → FAIL；合成 JSON `{"uri":"/v1/auth","uri_substring":[…]}` → FAIL。

#### 🔴-B N-5 把外层 `reverse_proxy` 的 `rewrite` 算进 `handle_response` 路由的链上，与 Caddy 语义相反（q3 实测旁路）

**位置**：§9.14.6 N-5："`handle_response[].routes`：按外层路由的上下文判定，**外层 `reverse_proxy` 的 `rewrite` 对象也算在链上**"；N-3 的范围中"外层路由中的"改写。

**Caddy 语义**：`reverse_proxy` 的 `rewrite` 只作用于发往上游的副本（`reverseproxy.go:157-167` 注释写明 "applied to the copy, it does not persist past the reverse proxy handler"；`:630-637` 先 `cloneRequest` 再改写）。`handle_response` 的路由收到的是**原请求**（`:982` `rh.Routes.Compile(next).ServeHTTP(rw, origReq.WithContext(ctx))`）。

**后果**：q3 中，内层转发器的链上按契约有一个常量改写 `/ping`，它不在 T 内，按 (b) 判 PASS。实际上内层转发的是原路径 `/v1/watcher/dialogs`，并被注入 observer。它在错误链里，本应失败。

**修法建议**：`handle_response` 路由的链，等于外层路由链**去掉外层 `reverse_proxy` 自身的 `rewrite` 对象**。外层链上位于该 `reverse_proxy` 之前的独立 `rewrite` handler 仍然有效。它与守卫的先后按外层路由的位置计算；在错误链里，按 N-5 的错误链规则判定。`intercept` 的 `handle_response` 同样作用于原请求，写法一致。RS-6 补 q3 用例 → FAIL。

#### 🟡-A O-1 的外部 V-5 证据没有新鲜度，也没有和当时的 Caddy 配置绑定

#### 问题 2："互斥"的定义

- **同一非空 `group`：正确。** 同组中先命中的路由会让后面的组员整体跳过（`routes.go:272` 起，`routeGroupCtxKey`），所以排在前面的组员不可能与 F 在同一请求上都执行。`handle_path` 与 `handle` 共用一个 group（实测 `hp2.test`：三者都是 `group82`），面板因此不受 `handle_path /grafana/*` 影响，判 W-1。
- **字面 host 列表不相交：不成立，见 🔴-1。** Caddy 的 host 匹配不区分大小写，并做 IDNA 归一（`matchers.go:261-265` 的 `idna.ToASCII` 与 `ToLower`，`:360` 的 `EqualFold`）。`headers` 在链白名单内，而它能改写 `r.Host`（`headers/headers.go:346-361`）。所以字面不相交的两条非 terminal 路由，可以在同一请求上先后都执行。
- **没有 host 匹配器的 server**（`http://:port`）：不会被判为互斥，属于保守失败。例如同一端口上 host 站点之后的兜底站点，其面板的链上会计入前面各站点的 handler，判 FAIL（`ca.json`：`srv0 | FAIL | chain has static_response, rewrite{strip /w}, reverse_proxy`）。见 🟢-1。
- **同 host、不同监听端口的多个 server**：每个 server 单独判定，结论正确（`b.test:18593` 带守卫判 W-1；`b.test:18594` 没有守卫判 FAIL）。

#### 问题 3：链上 handler 白名单

- **会改路径的标准 handler 都不在白名单内。** 包括 `rewrite`（`uri`、`handle_path`、`try_files`、`method` 生成的都是它）、`reverse_proxy.rewrite`、`invoke`、`intercept`、`static_response`、`file_server`，以及插件。
- **`map`、`vars` 不影响路径。** 它们只产生占位符，而会消费占位符的位置已被其他条款封住：W-3 的 `uri` 禁止 `{`；W-2 的模式禁止 `{`；dial 中出现占位符判 UNCOMPARABLE。`vars` 匹配器只能决定链内哪些路由执行，而链内的 handler 本来就全部计入。
- **`request_body`、`encode`、`log_append`、`tracing`、`authentication` 不影响路径。** `authentication` 失败会进入错误链，错误链中的转发器已经按容器规则判 FAIL。
- **`headers` 会改变路由判定。** 它能改写 `r.Host`，于是 host 匹配器的结果会变。它本身不改路径，但与"host 不相交即互斥"一起就构成旁路（🔴-1）。此外它能改写 `Authorization`（🔴-3）。
- **`subroute` 另有 `errors` 字段**（`subroute.go:44`、`:75-77`），也是一条错误链，契约的容器清单里没有它。见 🟡-1。

#### 🔴-2 "转发器"的识别漏掉 `dynamic_upstreams`（以及没有静态上游）的 `reverse_proxy`：它不进 V-1 的枚举，整套白名单看不见它（实测旁路）

**位置**：§9.14.6"operator-query 转发路由"："且某个 dial 的端口等于 operator-query 的端口 … 解析不了按 UNCOMPARABLE 判失败"；N-3："'转发器'指上游端口是 operator-query 端口的 `reverse_proxy` handler"；RS-2："转发器：`reverse_proxy` 且某个 dial 的端口等于 `--upstream` 的端口，沿用 `dial_endpoint`；解析不了判 UNCOMPARABLE"。

**事实**：`reverse_proxy { dynamic a { name 127.0.0.1; port 8183 } }` adapt 后只有 `"dynamic_upstreams": {"source":"a","name":"127.0.0.1","port":"18283"}`，没有 `upstreams`，也就没有任何 dial。`dynamic srv …` 连端口都没有。条文判定的是"某个 dial 的端口"，一个 dial 都没有时，既不是"等于"，也不是"解析不了"，于是被当成非转发器跳过。`dial_endpoint` 根本不会被调用。

**实测**（`dyn.test`：`handle /foo/* { reverse_proxy { dynamic a { name 127.0.0.1  port 18283 }  rewrite /v1/watcher/dialogs  header_up Authorization … } }`）：

```
wl_arch.py adapted.json | grep -c dyn   -> 0      （V-1 原型根本没有列出它）
GET dyn.test /foo/x              -> 200  upstream=[(18283, 'GET /v1/watcher/dialogs', 'injected=yes')]
GET dyn.test /v1/watcher/dialogs -> 404 body=0 upstream=[]   （守卫照常生效，P_D、V-5 都会通过）
```

现行代码其实知道这个形状：`_forwarder_check`（`o0_caddy_watcher_routes.py:1241`）写的是 `if "dynamic_upstreams" in h or not dials: UNCOMPARABLE`，`pin_probe_config`（`:1782-1786`）也拒绝钉住这种上游。但前者只检查可能看到 `/m/v1/watcher` 前缀的路由；后者只作用于被探测的 server。如果这个转发器单独放在另一个监听端口上，V-1 不列它，V-3 不认为那个 server"含转发路由"，所以不探测；逐转发器探针依赖 V-1 的列表，也不会触发；V-5 只发 `/v1/watcher…`。结果是整套检查都看不见它。

**修法建议**：在"operator-query 转发路由"与 RS-2 中写明：**任何** `reverse_proxy`（含 `forward_auth`），只要带 `dynamic_upstreams`、`upstreams` 为空，或有任一 dial 解析不了，一律判 UNCOMPARABLE（FAIL），与端口无关。V-3 选择 server 时，含这类 handler 的 server 也要纳入，或者直接判 `DIRECT_ENTRY_NOT_PROBED`。RS-6 的 UNCOMPARABLE 组补两例：`dynamic a { name 127.0.0.1 port 8183 }` 与 `dynamic srv …`。端口范围不需要特别处理：Caddyfile 会把 `127.0.0.1:18280-18285` 展开成 6 个 dial（实测），现行规则已经覆盖。

#### 🔴-3 W-2 没有约束 `Authorization`（Planner 判据 (a)）；而且 W-2 与 L-1 一样依赖 G1，这一点没有写明

**位置**：§9.14.6 N-3 W-2 的五个条件；链白名单中的 `headers`。

**事实**：W-2 既不看 F 自身的 `headers.request`，也不看链上的 `headers` handler，所以带 `header_up Authorization "Bearer {env.SYSTEM_OBSERVER_TOKEN}"` 的 `@mobile` 块判 W-2 PASS（`mobinj.test`：`wl_arch.py` 输出 `PASS | W-2`；活体 `GET /m/v1/accounts` 以 `/v1/accounts` 到达桩，`injected=yes`）。

**为什么要把它补上**（按 Planner 判据列 🔴；这里也说明它在 I-1 中的实际分量）：
- 单看 I-1，(c) 保证 clean 空间内的路径不落入 T，所以注入本身不直接暴露网关。但问题 1 已经证明，W-2 也有 raw 形状的残余：`/m/v1/watcher/..%2F..%2Fv1/accounts` 以在 T 内的 `/v1/watcher/..%2F..%2Fv1/accounts` 到达 8183，靠 G1 拒绝。允许注入，就等于让 W-2 在"G1 先于认证"之外再没有任何余量，而 W-2 的条文连这层依赖都没有写。
- 🔴-1 的 hmut2 是现成的组合旁路：一个判 W-2 PASS 的转发器，因为允许注入，把 observer 带到了 `/v1/watcher/dialogs`。只要 W-2 禁止触及 `Authorization`，那一例即使在 🔴-1 修好之前也会 FAIL。

#### 🟡-1 `subroute.errors.routes` 没有列入容器清单，只能靠"未知字段 → UNCOMPARABLE"兜住；Architect 自己的原型漏掉了它（实测旁路）

**位置**：§9.14.6 枚举范围与 N-3 容器规则；RS-2"遍历"。

**事实**：`Subroute` 有 `Errors *HTTPErrorConfig` 字段（`subroute.go:44`）。子路由内出错时，会执行它自己的错误路由（`:75-77`）。合成 JSON `se.test` 的子路由内容是：先有一个 `reverse_proxy` 发往不可达的 18299（带 `rewrite{method,uri:/auth}`），再是守卫，`errors.routes` 中放 F（注入）。

#### 🟡-2 "已认定的 `@wgw_direct` 守卫"在 N-2 站点中没有认定条件；原型把仿冒守卫当真（实测旁路）

**位置**：N-3"链"第 (1) 部分与 W-1 中的"已认定的 wgw 路由/守卫"。只有片段转发路由写了认定条件（`backend-api.md:808`）；RS-1 的结构检查只覆盖 app 站点的 wgw 连续块。

**实测**（`fg.test`：`@wgw_direct path_regexp ^/zzz$`，`handle @wgw_direct { respond 404 }`，然后是面板加注入）：`wl_arch.py` 判 `PASS | W-1`；`GET /v1/watcher/dialogs` → 200，`injected=yes`。V-2 会发现它，因为 `P_D` 必须由守卫的静态 404 应答，所以不是单点失守。但 V-1 的判定本身不能建立在名字上。**修法**：写明认定条件——匹配器集合恰为一个 `path_regexp`，`name` 为 `wgw_direct`，`pattern` 逐字等于规定正则；处理链恰为 `static_response` 404（允许外包一层只含它的 `subroute`），没有其他 handler。兜底同理。名字以 `wgw_` 开头却认定不了的路由判 FAIL，不得排除出链。RS-6 增加"仿冒守卫"一例。

#### 🟡-3 逐转发器标记探针的"其他匹配器已在 V-1 判 FAIL"对 W-1 不成立

**位置**：V-3"逐转发器标记探针"第 4 条："其他匹配器（这类转发器在 V-1 已判 FAIL）不构造"。

**理由**：W-1 明文规定"F 的匹配器不限"。所以带 `host`、`header`、`not`、`path_regexp` 等匹配器的 W-1 转发器会判 PASS，同时又得不到任何标记探针。🔴-1 的 hcase、hmut 正是这样：它们的匹配器是 `host`，第二道防线没有覆盖。**修法**：只含 `host` 的匹配器，带该 Host 发"没有匹配器"那一对请求；其他匹配器构造不了触发请求时，输出 `DIRECT_ENTRY_NOT_PROBED` 并判失败。另一个办法是在 W-1 中收窄匹配器种类。

#### 🟡-4 W-2 的"站点的 host 路由除外"无法机械判定

**位置**：W-2 第 3 条。hmut2 中 F 最近的带匹配器路由是内层的 `@a2 host hmut2.test`。原型把所有含 `host` 的匹配器都跳过，于是一直上溯到 `@mobile`，判 PASS。按"站点的 host 路由"的本意，只应跳过 server 顶层的站点路由；这样内层 host 就算一个匹配器，不是纯 `path`，应判 FAIL。**修法**：写明"只跳过 server 顶层 `routes` 中、匹配器集合只含 `host` 键的路由；其他层级的 host 匹配器照常计入"。

#### 🟡-2 "指向"的保守规则会误拦三种常见而无害的写法（用户要求"不要限制得那么死"）

**位置**：I-2 第 2、3 条（`:827-828`）；PC-6 (i)；RS-15 的 FAIL 组。

- unix socket 上游只能连本机 socket。要借它到达 8186，得有本机进程转发，而这已经由 PC-6 (iii) 覆盖；
- 主机名是占位符、端口是字面数字（`{env.X}:8183`）时，无论占位符解析成什么，端口都固定为 8183；
- `dynamic a`/`aaaa` 带字面 `port` 时，解析出的每个地址都用这个端口。

**修法**：放宽为以下规则。
- unix socket：不算"指向"，由 PC-6 (iii) 兜底。
- 占位符只出现在主机名、端口是字面数字：按端口判定。
- `dynamic a`/`aaaa` 的 `port` 是字面数字：按端口判定。
- 下面几种继续判 FAIL：端口是占位符、`srv` 或其他动态源、端口范围、非字符串。
